# 15　系统架构、协议内核与外部连接器

## 15.1 四个平面与一个联邦事件图

系统架构分为四个逻辑平面：

1. **主体与权威平面**：Entity、Authority Root/Locus、Mandate、Standing、Commitment；
2. **认识与形成平面**：Assertion、Unknown、Evidence、Boundary Oracle、PFE、CRA；
3. **协调与编译平面**：RelationVersion、JAA、Router、Stability Gate、Compiled World；
4. **操作与效力平面**：Operation、Attempt、Effect、Adoption、Acceptance、Settlement。

四平面通过联邦事件图连接。每个主权域维护自己的权威事实，跨域系统保存可验证引用、版本和事件，不要求一个全局数据库成为所有事实的最终来源。

## 15.2 六个 canonical roots

当前最小权威对象保持六类：

### Entity

外部身份、信任根和责任关系。

### Mandate

范围化、版本化、可撤销委托。

### RelationVersion

具体共同关系的版本化 Schema、参数、参与者、条件和依赖。

### Assertion

带来源、置信、证据、有效期和可反驳性的主张。

### Commitment

产生未来义务、资源和补救的规范对象。

### Operation

可执行、幂等、可观察 Effect 的动作规范。

其他结构应优先表示为事件、属性、溯源边、策略或派生视图。只有出现独立权威和生命周期需求时才提升为 root。

## 15.3 统一事件包络

事件最小包络：

```json
{
  "event_id": "uuid",
  "event_type": "STANCE_RECOGNIZED",
  "entity_id": "...",
  "authority_locus": "...",
  "relation_version": "sha256:...",
  "subject_ref": "...",
  "mandate_ref": "...",
  "payload_ref": "...",
  "evidence_refs": ["..."],
  "previous_event_hash": "...",
  "timestamp": "...",
  "signature_or_attestation": "..."
}
```

包络保证来源、顺序和引用，但事件语义由具体类型和相称 Authority 决定。哈希链有助于审计，不等于去中心化账本，也不替代真实身份和目标域 witness。

## 15.4 关键事件类型

事件至少覆盖：

- `ASSERTION_CREATED / CHALLENGED / SUPERSEDED`；
- `BOUNDARY_ASSESSMENT`；
- `SCHEMA_REVISION_PROPOSED / MATERIALIZED`；
- `STANCE_RECOGNIZED / REJECTED / CONDITIONAL / WITHDRAWN`；
- `MANDATE_ISSUED / NARROWED / REVOKED / EXPIRED`；
- `RESOURCE_RESERVED / RELEASED / CONSUMED`；
- `COMMITMENT_CREATED / ACTIVATED / FULFILLED / BREACHED`；
- `OPERATION_SPECIFIED / ATTEMPTED`；
- `EFFECT_CONFIRMED / PARTIAL / UNKNOWN / REVOKED`；
- `ADOPTION_RECORDED`；
- `ACCEPTANCE_RECORDED / CONTESTED`；
- `SETTLEMENT_RECORDED`；
- `DEFEATER_RAISED / SCOPE_REOPENED`；
- `DATA_USED / DERIVED / RETAINED / DELETED / LEARNING_UPDATED`。

## 15.5 Boundary Oracle 接口

```text
assess(
  task_family,
  relation_version,
  candidate,
  requested_claim,
  disclosure_budget,
  mandate_ref
) -> OracleAssessment
```

返回：

```text
status: ACCEPT | SEPARATE | WITNESS | COLUMN |
        MODEL_OBJECTION | HUMAN_REFUSAL | UNKNOWN | COUNTERCONDITION
scope
evidence_refs
cut_or_condition
validity
confidence        # 仅认识语义
authority         # 是否具有规范效力
disclosure_cost
reconstruction_risk
```

`confidence` 和 `authority` 必须分别记录。模型高置信异议不能被编码成有权拒绝；真实主体拒绝可以没有模型解释。

## 15.6 Context Compiler

Context Compiler 将主体本地世界编译为任务相关上下文包，而不是上传全部历史。其职责包括：

- 按 Mandate 和用途选择信息；
- 保留来源和有效期；
- 区分事实、推断、偏好和模型建议；
- 生成未知项和冲突；
- 对敏感内容输出证明、摘要、区间或本地 Oracle；
- 防止“上下文越多越好”的无界复制。

Context Compiler 是 Harness 的核心组件，因为 Agent 的行动质量取决于可用上下文和权限，而不是模型参数 alone。

## 15.7 Coordination Runtime

Coordination Runtime 维护 RelationVersion、JAA、候选、Stance、Commitment 和机制图。它不拥有各主体的全部本地世界，也不自行产生最终权威。其功能包括：

- 版本差异与 materiality 检查；
- Unknown 和形成算子管理；
- Router 与 Stability Gate；
- 资源预留和并发控制；
- explain-back、冷静期和逐项认领；
- 依赖图与 scoped reopen；
- 对 A2A、MCP、人类工作台和外部 TrustAdapter 的协调。

## 15.8 Effect Gateway

Effect Gateway 把 Operation 连接到目标世界。它负责：

- 验证 Mandate 和 RelationVersion；
- 生成 idempotency key 和 AttemptID；
- 执行 pre-effect validation；
- 调用工具、API、人类或物理流程；
- 从目标域获取 authoritative readback；
- 记录 Effect、撤销、恢复和补偿；
- 将模型输出与目标事实分开。

Effect Gateway 可以由支付、代码托管、日历、ERP、CRM、文件系统、区块链、法律签署或人工回执实现。

## 15.9 Event Ledger 与 Compiled World

Event Ledger 保存不可覆盖的因果和权威历史；Compiled World 提供当前可运行视图。二者关系类似：

\[
CompiledWorld_t = Fold(EventLedger_{\le t}, valid\ policies, local\ facts).
\]

若事件被撤销或新 Defeater 出现，视图重算或局部失效。Compiled World 不能绕过原始 Authority 直接修正事实。

## 15.10 外部协议适配

### A2A Adapter

用于 Agent 发现、Task、Message、Artifact 和长任务状态。A2A Task 可以承载 Operation 或形成任务，但其 `completed` 状态不能自动映射为业务 Acceptance。

### MCP Adapter

用于工具、资源和本地服务访问。MCP authorization scope 映射到 Mandate 的资源动作子集；RelationVersion 仍提供目标、数据派生、Effect 和接受语义。

### OAuth / Mandate / VC Adapter

OAuth 和新型 Agent Mandate 草案可绑定令牌、任务和委托链；VC 可承载身份、资格和授权声明。适配器必须保留发行者、持有者、受众、有效期和撤销，并避免把可验证声明误写成真实世界充分证据。

### WoWok / TrustAdapter

WoWok 一类可编程信任对象可以承担托管、权限、服务、Treasury、仲裁和 Repository 等 Effect 基础设施。本文把它视为可替换 TrustAdapter，而非理论前提或唯一实现。

## 15.11 生产栈

![从主权节点、协调运行时、概率语义、权威保证、外部信任到编译世界的生产栈。](figures/production_stack.png){width=82%}

建议的生产栈包括：

1. 主权节点 SDK；
2. Context Compiler 与本地 Oracle；
3. Coordination Runtime 与 JAA；
4. Authority/Mandate/Commitment 服务；
5. Capability/Assurance 服务；
6. Effect Gateway 与 TrustAdapter；
7. Event Ledger 与 Compiled World；
8. 人类工作台、explain-back 和争议界面；
9. A2A/MCP/OAuth/VC 等连接器；
10. 红队、模拟、诊断和可观测性套件。

## 15.12 最小实现顺序

正式系统不应从“搭一个通用 Agent 市场”开始。最小纵向闭环为：

1. 一个 OPC Entity 与两个 Authority Locus；
2. 一个范围化 Mandate；
3. 一个非标准 RelationVersion；
4. 一个 Boundary/Countercondition 循环；
5. 一个可逆现实 probe；
6. 一个资源预留；
7. 一个可见目标 Effect；
8. 一个独立 Adoption/Acceptance；
9. 一个 Defeater 和局部 reopen；
10. 一个稳定子图编译为确定性运行。

只有该闭环真实运行后，横向扩展发现市场和开放协议才不会失去现实语义。

## 15.13 安全边界

生产系统至少需要：

- 强身份、密钥和凭证管理；
- 细粒度、短期、可撤销 Mandate；
- 不可逆动作的人类或双重 Gate；
- Effect readback 与幂等；
- 资源预留与限额；
- 私有上下文隔离和最小披露；
- 事件溯源和争议保全；
- 模型升级、工具变化和 prompt injection 的 Defeater；
- 安全默认拒绝，但允许结构化 countercondition；
- 面向第三方外部性的 Standing 与审查。

当前 Fieldkit 只验证研究对象和状态机，不具备生产级上述能力。
