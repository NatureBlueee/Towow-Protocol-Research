# 11. 工程构造蓝图

## 11.1 最小内核

一个可用实现至少需要：

1. 追加式事件存储与版本哈希；
2. Principal、Execution 与 AuthorityGrant 管理；
3. Objective、CoordinationCase 和 SharedArtifact 版本；
4. Claim—Evidence—WitnessPolicy—Defeater 图；
5. 边界调用接口：query、witness、countercondition、refuse、unknown；
6. 形成策略接口与本地 probe 执行器；
7. Recognition 与 Commitment 编译器；
8. Effect Gateway、LogicalActionKey 和 Attempt ledger；
9. Target-domain Adoption、Verification 与 Acceptance Adapter；
10. 派生视图：CapabilityEnvelope、AssuranceCase、Compiled World；
11. 监测与 formation reopen 机制。

## 11.2 上下文编译

共享上下文不应是全企业大仓库。Harness 应针对每个任务编译最小工作环境：目标版本、相关对象、有效 Claim、证据、工具、权限、接受规则、风险、未知和升级路径。Problem IR、Design IR、Engineering IR 与 Consensus 的分离，避免把设计假说过早冻结成工程事实 [@flowness2026; @prse2026]。

## 11.3 风险触发物化

并非每个低风险工具调用都需要完整 Commitment、Recognition 和 Settlement 对象。系统可以根据后果等级物化：

- L0：只读观察；
- L1：可恢复本地动作；
- L2：代表他人或跨边界动作；
- L3：承诺、稀缺资源或不可逆 Effect；
- L4：多 Principal 生成式协调。

高风险层保留完整对象与审计；低风险层可以在不丢失语义的前提下编译成轻量运行记录。

## 11.4 一致性与分布式状态

草稿、注释和候选证据可以使用最终一致或 CRDT；稀缺资源、付款、唯一席位、正式承诺和不可逆 Effect 需要事务、租约、共识、托管或同等强度的串行门。协调避免原则不能越过不可交换的不变量 [@bailis2014; @kleppmann2017]。

跨服务长事务可以使用 Saga 和补偿，但补偿不是时间倒流，必须保留原 ActionAttempt 和 Effect 轨迹 [@garciamolina1987]。线性化和端到端论证提醒我们：中间层成功不能代替最终消费者验证 [@herlihy1990; @saltzer1984]。

## 11.5 参考部署拓扑

一个最小跨主体部署可以包含：

```text
Principal A domain                    Shared coordination plane                 Principal B domain
------------------                    -------------------------                 ------------------
Local context store                   Case / Artifact / Claim index             Local context store
Local AgentExecution  <------------>  A2A transport / coordination API  <---->  Local AgentExecution
Local probe/tool runtime              Formation policy / solver providers       Local probe/tool runtime
Local authority service               Version/event ledger                       Local authority service
Local evidence store                  Compiled shared views                      Local evidence store
Effect/adoption adapter               Monitoring / reopen controller             Effect/adoption adapter
```

共享面不拥有双方完整上下文，也不拥有未委托权威。它可以缓存已授权投影和共享制品；本地域可以随时返回 `REFUSE`、`UNKNOWN`、Defeater 或撤销。

## 11.6 实现次序

为了避免先造一座过度抽象的平台，工程应按纵向切片展开：

1. 选一项真实、低风险但存在不可折叠属性的协调 Case；
2. 先实现 Principal/Execution/Authority、Objective、SharedArtifact 和 Claim/Evidence；
3. 接入一个本地 probe 与一种 Countercondition；
4. 形成一个可运行候选，并加入 Recognition；
5. 经 Effect Gateway 写入一个可恢复目标域；
6. 实现 DomainAdoption、Verification、Acceptance；
7. 加入留出、Defeater 和重开；
8. 只有真实重复路径出现后，才提取通用 Skill、Provider 和协议扩展。

这一顺序与 Harness 的认知工程原则一致：先建立真实闭环，再从重复轨迹结晶基础设施，而不是先冻结一个假想通用平台 [@flowness2026]。
