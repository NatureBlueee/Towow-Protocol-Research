# 21　可执行权威语义：从论文对象到单一运行内核

## 21.1 为什么必须建立可执行语义

在前几轮研究中，Principal、Mandate、RelationVersion、Commitment、Operation、Effect 和 Acceptance 已经被区分，但如果论文、Schema、Fieldkit 和实验各自实现不同语义，系统仍会在边界处重新折叠。v1.1 因此将六个 canonical roots 与必要派生对象压进一个无依赖参考内核，并要求所有关键状态迁移由同一 gate 执行。

参考内核不是生产身份、支付、法律签署、密码学或隔离边界。它的研究任务是：让理论中的“不应当发生”变成可以被程序拒绝、可以被 mutation suite 反驳的状态转换条件。

## 21.2 状态与动作

抽象状态写成：

\[
S = \langle E, M, \Gamma, A, R, C, O, X, Z, L \rangle,
\]

其中 \(E\) 是 Entity/Authority 注册表，\(M\) 是 Mandate，\(\Gamma\) 是 RelationVersion 历史，\(A\) 是 Assertion/Stance，\(R\) 是资源容量与预留，\(C\) 是 Commitment，\(O\) 是 Operation，\(X\) 是 Effect，\(Z\) 是 Acceptance 与状态，\(L\) 是事件链和编译视图。

主要动作包括：注册 Entity 与 Authority Locus；签发/撤销 Mandate；创建 RelationVersion；记录 exact-version Stance；注册容量并预留资源；激活 Commitment；准备和执行 Operation；从目标域 witness Effect；记录 Acceptance；material change；dependency-closure reopen；局部编译。

## 21.3 核心安全不变量

参考内核把以下不变量作为可执行拒绝条件：

1. **Mandate containment**：动作、数据用途、单次预算和累计预算均在有效 Mandate 内；
2. **Authority match**：Operation actor、Authority Locus 和 Mandate 发行域一致；
3. **Exact version**：Stance、Reservation、Commitment 和 Operation 引用当前精确 RelationVersion；
4. **Recognition before irreversible action**：不可逆动作需当前关系被相称主体认领；
5. **Resource before commitment**：承诺前有真实资源预留，注册容量不被超卖；
6. **Attempt before Effect**：目标域没有 readback 时不得生成 Effect；
7. **Effect before Acceptance**：Acceptance 必须引用一个存在的 Effect；
8. **Revocation at use time**：撤销、过期和累计限额在执行时再次检查；
9. **Material invalidation**：material change 失效旧 Commitment 和 compiled version；
10. **Scoped reopen**：由依赖图计算受影响后代，不全局清空，也不遗漏；
11. **Event integrity**：事件形成 hash chain，篡改可检测；
12. **Derived view discipline**：snapshot/Compiled World 不成为第二事实源。

## 21.4 参考实现与测试

v1.1 内核实现 Entity continuity、Authority Locus powers、Mandate、RelationVersion、ResourceCapacity、Reservation、Commitment、Operation、FileSandbox Effect adapter、Acceptance、material change、reopen、compile、event chain 与派生 snapshot。17 项单元测试覆盖：完整闭环、撤销、数据权、Acceptance 权威、material invalidation、编译阻断、依赖闭包、idempotency、资源超卖、释放预留、actor mismatch、累计限额、陈旧 hash、事件篡改、路径逃逸和派生视图。

全部测试通过只表明实现满足当前测试，不等于不变量已经在所有并发、分区和攻击下成立。为避免“测试写成什么，系统就证明什么”的自洽，本文增加独立抽象状态探索与 mutation suite。

## 21.5 TLA+ 规格与有界状态探索

`TowowCore.tla` 给出 Mandate、Recognition、Reservation、Commitment、Operation、Attempt、Effect、Acceptance、Compile 和 MaterialChange 的有限状态规格 [65]。当前运行时无法取得官方 TLC JAR，因此本文不声称已执行 TLC；TLA+ 文件作为独立复核制品发布。

同一生命周期被另行编码为无依赖 Python 有界探索器。正确模型在深度 12 内探索 374 个唯一状态和 1,084 个转移，在所列不变量中未发现反例。随后逐一注入九类错误：Effect 无 Attempt、Acceptance 无 Effect、累计超限、material change 保留旧状态、撤销后执行、无预留承诺、资源超卖、数据权绕过和错误 Authority。每个 mutation suite 都在较小状态空间中产生至少四条反例。

| 模型 | 状态 | 转移 | 反例数 |
|---|---:|---:|---:|
| 正确模型 | 374 | 1,084 | 0 |
| Effect without Attempt | 35 | 56 | ≥4 |
| Acceptance without Effect | 58 | 114 | ≥4 |
| Aggregate overspend | 113 | 248 | ≥4 |
| Change keeps old state | 120 | 204 | ≥4 |
| Attempt after revocation | 196 | 487 | ≥4 |
| Commitment without reservation | 61 | 109 | ≥4 |
| Resource oversubscription | 64 | 122 | ≥4 |
| Data-rights bypass | 108 | 239 | ≥4 |
| Wrong Authority | 108 | 239 | ≥4 |

结果的价值不在“零违规”本身，而在于 mutation 能被同一探索器稳定区分，说明不变量具有非平凡的错误检测能力。

## 21.6 从形式结果到系统 Design Delta

第一，Authority 与数据权必须在 Operation 准备和执行时再次验证，而不能只在 Agent 获得凭证时检查。第二，资源容量属于承诺语义；若只在业务层事后统计，系统仍可产生多个逐项合法、合计超限的承诺。第三，Acceptance 必须有独立 power 和目标 Effect 引用。第四，material change 必须使旧 Stance、Commitment 和 compiled version 显式失效。第五，事件链和派生 snapshot 使审计可行，但不能替代生产签名、可信时间和安全存储。

## 21.7 尚未形式化的部分

当前模型尚未覆盖拜占庭主体、密钥盗用、网络分区、乱序和重复消息、跨法域效力、复杂多资源死锁、战略性 Oracle、选择性披露攻击和长期学习状态。Progress properties 也只获得设计约束，尚未证明所有 Unknown 最终进入 probe/defer/reject。下一版形式研究应把多主体并发、两阶段/补偿式 Commitment、撤销传播和 scoped reopen 的最小性纳入 TLC 或同等级工具。
