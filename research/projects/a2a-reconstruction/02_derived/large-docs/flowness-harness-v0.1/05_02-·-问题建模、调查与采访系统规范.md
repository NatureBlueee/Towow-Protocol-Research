# 02 · 问题建模、调查与采访系统规范

## 1. 为什么采访前还需要 Problem Model

当用户能清楚说出目标和约束时，可以直接进入采访。但很多复杂任务中，连“问题是什么”本身都不清楚：

- 用户只看见一个症状；
- 使用了一个可能误导设计的名词；
- 多个问题被压成一句抱怨；
- 系统现状与文档不一致；
- 用户有强烈感受，却没有可操作表达。

此时直接整理需求，会把用户当时的描述冻结成错误边界。

因此正式管线应允许：

```text
模糊现象
  → Sensemaking / Investigation
  → Problem IR
  → Interview / Requirement IR
```

调查解决“真实发生了什么”，采访解决“人在这些事实与可能性面前究竟要什么”。

## 2. Problem IR

Problem IR 至少包含：

- 委托与主体；
- 原始现象；
- 已验证事实；
- 有证据推断；
- 假设；
- 未知；
- 竞争解释；
- 受影响对象；
- 出现条件；
- 因果候选；
- 证据与反证；
- 当前规避方式；
- 风险与紧急度；
- 可改变和不可改变条件；
- 下一步信息价值最高的调查动作。

Problem IR 不应过早包含唯一解决方案。

## 3. 调查方法

### 3.1 用户的词是探针，不是边界

用户说“可观测性不足”，应继续调查：

- 系统是否有稳定身份；
- 状态是事实还是自我报告；
- 事件是否完整；
- 不同数据源是否矛盾；
- 运行结果是否被消费；
- 当前状态能否由历史重建；
- 错误是否真实改变生命周期；
- 用户能否从观测做出正确行动。

### 3.2 从真实系统重建，而不是从架构图复述

重要判断需要沿证据链追踪：

```text
定义
→ 注册
→ 调用方
→ 真实运行是否调用
→ 写入什么状态
→ 下游是否消费
→ 用户是否能观察
```

文档、代码、日志、账本和测试都可能单独失真，承重判断至少使用两个独立来源。

### 3.3 覆盖显式化

每次大型调查维护覆盖表：

- 已检查区域；
- 只有文档证据的区域；
- 有代码无运行证据的区域；
- 尚未检查区域；
- 版本和时间范围；
- 每个区域置信度。

### 3.4 每个问题独立建档

问题档案至少包含：现象、条件、影响、代码位置、运行证据、可能原因、竞争解释、反例、相关问题、验证实验、修复候选、风险和完成标准。

没有竞争解释和反例的“根因”只是主张。

## 4. 采访的本质

采访不是问卷，也不是把原话整理成 PRD。它是将人的高维判断转化为下游可工作的结构，同时尽量不损失人的价值、直觉和隐性边界。

采访应完成：

- 找到用户真正想改变的现实；
- 区分手段和目的；
- 发现未说出的冲突和反目标；
- 给出具体草样让用户对“东西”作判断；
- 用场景撞出信息缺口；
- 将可由行业知识、历史判例和系统事实回答的问题先自答；
- 只把真正需要价值裁决的问题交还用户。

## 5. 推荐采访循环

1. **预研究**：读取历史判断、当前系统、外部成熟实践。
2. **主动推测**：用自己的话说明理解，并标注可撤销。
3. **构造草样**：给出两到三个机制或场景真正不同的样例。
4. **场景推演**：从用户、系统、异常和长期维护视角走一遍。
5. **缺口图**：记录哪些信息仍无法自答，以及它们的依赖关系。
6. **按信息价值提问**：优先问能消除最多下游不确定性的上游问题。
7. **一致性检查**：找出用户不同回答之间的冲突。
8. **回读确认**：用可进入的语言复述最终理解，由用户确认。
9. **发布 Requirement IR**：保留原话、推断、假设和待定项。

## 6. Requirement IR

需求对象至少包括：

- `requirement_id`；
- 来源与原话；
- 类型：目标、功能、质量、约束、反目标、风险、体验、治理；
- 适用主体和场景；
- 优先级与理由；
- 决策权归属；
- 成功场景；
- 失败场景；
- 可量化响应；
- 依赖和冲突；
- 置信度；
- 是否已由用户确认；
- 哪些事实会使它失效。

## 7. 从抽象价值到设计要求

用户说“要美”“要可靠”“要像一个活的世界”，不能直接进入实现。

先转化为质量场景。例如：

```text
当用户第一次进入系统时，
在没有阅读说明文档的情况下，
应在 30 秒内识别主要对象、当前状态和可执行动作，
且不把装饰性元素误认为真实控制入口。
```

质量场景至少包含：刺激源、刺激、环境、对象、响应和可测指标。

## 8. 采访完成门

采访完成不是“用户没有更多要说”。应满足：

- 主要目标有来源；
- 关键冲突已暴露；
- 反目标明确；
- 价值判断与工程判断分开；
- 高风险隐性需求已被确认或拒绝；
- 成功和失败具有可观察表现；
- 下游设计者无需重新猜测用户意图；
- 仍未知的问题显式存在；
- 用户知道自己确认了什么。

## 9. 失败与回流

- 发现事实理解错误：回调查；
- 用户目标发生变化：重采访；
- 设计发现不可调和冲突：回用户裁决；
- 执行才发现核心信息缺失：登记 Interview Gap，并分析为什么入口未发现；
- 同类缺口重复发生：升级采访方法、场景库或验证器，而不是只补当前需求。
