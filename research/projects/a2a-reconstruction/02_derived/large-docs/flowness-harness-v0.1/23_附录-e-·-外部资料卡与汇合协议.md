# 附录 E · 外部资料卡与汇合协议

## 1. 为什么需要汇合协议

框架、论文和大厂实践不断出现。若每次看到好内容就直接改 Harness，会产生概念污染、重复机制和方向摆动。

外部资料先被当作证据和候选，不直接成为内部事实。

## 2. 资料卡模板

```yaml
source_id: source-xxx
title: ...
type: paper | framework | company_practice | incident | standard
published_at: ...
reviewed_at: ...

problem_addressed: ...
context:
  organization_size: ...
  domain: ...
  constraints: ...

objects:
  - ...
mechanisms:
  - ...
evidence:
  type: benchmark | production | case_study | claim
  strength: low | medium | high

same_as_flowness:
  - ...
different_from_flowness:
  - ...
conflicts:
  - ...

adopt_candidates:
  - mechanism: ...
    reason: ...
    adaptation_needed: ...

reject_or_defer:
  - item: ...
    reason: ...

validation_plan: ...
```

## 3. 吸收规则

- 吸收问题和机制，不盲目吸收术语；
- 先映射到现有对象；
- 外部运行时不得成为内部语义内核；
- 生产案例优先于营销描述；
- 论文 Benchmark 不能自动代表组织环境；
- 开源项目要读代码、测试、Issue 和历史；
- 冲突不通过模糊整合消失；
- 新机制先进入 Evolution Track。

## 4. 冲突处理

当外部方案与 Flowness 冲突时，分别判断：

- 目标不同；
- 适用规模不同；
- 约束不同；
- 抽象层不同；
- 一方缺少证据；
- Flowness 的设计确实需要被推翻。

输出不是“取长补短”四个字，而是明确采用、适配、并存、延后或拒绝。

## 5. 合并后的追溯

被吸收的机制应记录：

- 来源；
- 内部对应对象；
- 修改内容；
- 适用范围；
- 实验证据；
- 是否已进入生产；
- 后续与原来源不同的演化。
