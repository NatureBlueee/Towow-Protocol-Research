# 01 · Harness 认知工程总纲

## 1. 核心判断

一个工业级 Harness 不是 Agent 调度器、Prompt 集合、工作流图或代码生成器。它是一套将人的意图和组织判断逐层编译为可验证现实的系统。

它面对的根问题是：

> 大模型具备强大的局部生成能力，但缺少稳定身份、长期记忆、统一事实世界、明确责任、可靠边界和自然的一致性。怎样让大量局部智能体在长周期复杂工作中，既能自主发挥，又不改写共同世界？

因此 Harness 的职责不是让 Agent “更聪明”，而是建立：

- 正确的问题表示；
- 分阶段的认知生产；
- 可追溯的决策；
- 作用域明确的共识；
- 可编译的上下文；
- 可恢复的执行；
- 独立的验证；
- 正确层级的回流；
- 可观测、可审计、可演化的组织制度。

## 2. 完整生命周期

```text
0. 委托与准入
1. Sensemaking / 调查
2. 采访与需求建模
3. 设计
4. 工程方案
5. 工程共识
6. 计划编译
7. 执行
8. 独立审查与验证
9. 修复与多级回流
10. 发布、运行与持续学习
```

并非每项工作都必须走全部阶段。系统先按风险、复杂度、影响范围和不确定性选择流程强度。

## 3. 为什么必须分层

需求、设计、工程、共识、计划和实现不是同一种信息的不同写法，而是不同性质的判断：

| 层级 | 回答的问题 | 主要失败 |
|---|---|---|
| 委托 | 谁要改变什么现实，谁能拍板 | 范围与权力不清 |
| 调查 | 真实系统发生了什么 | 把猜测当事实 |
| 采访/需求 | 人究竟想要什么 | 意图丢失、隐性需求未发现 |
| 设计 | 应创造怎样的系统 | 方案不自洽、功能堆砌 |
| 工程方案 | 如何在真实约束下实现 | 技术不可行、不可维护 |
| 工程共识 | 所有执行者必须共同服从什么 | 局部漂移、接口分裂 |
| 计划 | 怎样切成可执行、可合并的工作 | 任务不闭包、依赖错误 |
| 执行 | 如何产生真实改变 | 越权、假完成、局部正确 |
| 验证 | 怎样独立证明结果成立 | 自证、指标投机、漏检 |
| 回流 | 问题应回到哪一层 | 所有问题都变成重新执行 |

把这些层压缩成一份 Spec 或一个 Architect Agent，会把未解决的上游判断偷偷交给下游执行者。

## 4. 两类编译和一种冻结

完整管线的关键不只是阶段，而是三种性质不同的转换。

### 4.1 设计编译

```text
Problem / Requirement IR
    → Design IR
```

将目标、约束、价值和场景编译成主体、对象、机制、行为、状态、权限、体验与失败恢复。

设计编译具有创造性，不存在唯一正确结果，必须产生候选方案、比较并接受攻击。

### 4.2 工程编译

```text
Design IR
    → Engineering IR
```

将设计对象和机制编译为组件、接口、数据、状态机、任务、运行时、SLO、测试、发布与运维结构。

工程编译受现实技术、成本、团队和运行环境约束，必须提供证据和实验。

### 4.3 共识冻结

```text
Engineering IR
    → Scoped Consensus
```

从完整工程方案中提取跨任务稳定、必须共同遵守的事实与约束，并计算其作用域、版本和变更规则。

共识不是另一轮设计。它不负责继续发散，而负责明确：哪些可以自由实现，哪些不得漂移。

## 5. 根原则

### 5.1 事实和方案分离

当前系统的真实行为、对真实行为的解释、未来建议不得混写。

### 5.2 上下文最小充分

不给 Agent 最多的信息，而给它完成当前合法判断所需的最小充分上下文，并保留可按需展开的路径。

### 5.3 局部自治，全局一致

执行者可以决定局部实现，但不能私自修改公共契约、产品目标和全局不变量。

### 5.4 证据优先于语言流畅

方案写得完整不代表成立。重要结论需要代码、数据、运行、实验或用户行为支持。

### 5.5 任何关键方案必须可被推翻

方案应写明假设、反例、失败条件和重开触发器。

### 5.6 错误回到正确层级

执行错误修执行；计划错误重计划；工程假设失效重做工程方案；设计结构错误重设计；意图理解错误重采访。

### 5.7 验证器拥有真实权力

规则只有被验证器、权限、Schema、CI 或运行门执行时，才是制度。只写在提示词里的规则是建议。

### 5.8 人是价值与授权的源头

系统可以发现事实、形成候选、推演后果，但不能擅自创造组织价值标准或跨越不可逆权力边界。

### 5.9 生产和演进分轨

稳定版本负责交付；新机制在 shadow 和 dogfood 中证明价值后才进入生产。

### 5.10 复杂度也需要被治理

新 Agent、新事件、新对象、新 Gate、新文档都有维护成本。增加机制前必须证明它解决的风险大于引入的协调成本。

## 6. Harness 的五个平面

### 6.1 语义平面

定义系统中的主体、对象、关系、规则、状态和版本，是世界模型。

### 6.2 认知平面

负责调查、采访、设计、工程推理、评审和知识生成。

### 6.3 控制平面

负责生命周期、路由、调度、权限、审批、回流和资源分配。

### 6.4 执行平面

负责模型调用、工具、工作区、代码、浏览器、沙箱和外部系统操作。

### 6.5 证据平面

负责事件、Trace、测试、运行指标、审计、归因和完成证明。

外部 Agent 框架通常覆盖控制和执行平面；Flowness 的独特价值应当集中在语义、认知和证据平面，并通过适配器使用外部基础设施。

## 7. 任务强度分级

建议至少建立五级工作模式：

| 等级 | 典型任务 | 必需流程 |
|---|---|---|
| L0 | 格式、局部机械修改 | 执行 + 机械验证 |
| L1 | 小功能、低风险修复 | 轻量 Spec + 执行 + Review |
| L2 | 新模块、中等影响 | 采访 + 设计 + 工程方案 + 完整闭环 |
| L3 | 跨模块、公共契约、高风险 | 多方案、红队、共识冻结、分批迁移 |
| L4 | 跨系统、生产关键、长期迁移 | 专家委员会、实验、灰度、长期治理 |

流程强度由风险和不确定性决定，不由“任务看起来正式”决定。

## 8. 完成定义

一个阶段完成，不是 Agent 声称完成，而是满足阶段合同。

整个项目完成至少需要：

- 目标有可观察结果；
- 关键需求有设计响应；
- 设计对象有工程实现；
- 公共实现遵守共识；
- 计划依赖和任务边界被验证；
- 代码、配置、数据和部署真实生效；
- 独立验证通过；
- 未验证部分明确可见；
- 变更历史和证据可以追溯；
- 运行一段时间后没有出现不可接受退化。

## 9. 本总纲的停止边界

本总纲不规定每个领域的具体语义，也不承诺对所有可讨论问题实现自动化。一个领域只有在具备可表示对象、可获取证据、可接受反馈和明确授权后，才适合进入 Harness 的自动闭环。
