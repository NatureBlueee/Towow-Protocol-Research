# 08 · 实时语义空间与上下文编译器设计

## 1. 核心命题

Agent 不应只在任务开始时拿到一份静态上下文。它每次阅读、修改、测试或审查一个对象时，所在的语义空间都发生变化。

因此上下文应当像增量编译结果，而不是固定 Prompt：

> 当前动作 + 当前对象 + 当前任务 + 当前世界状态 → 最小充分语义空间。

## 2. 为什么静态上下文不够

静态 `AGENTS.md`、`CLAUDE.md` 或项目说明存在四个问题：

- 太全：不相关信息稀释注意力；
- 太粗：只能定位到文档或模块，不能定位到字段和行为；
- 太旧：代码、共识和运行状态变化后不自动失效；
- 太早：任务开始时还不知道 Agent 后续会进入哪个对象。

实时语义空间应在动作发生时重新计算相关性。

## 3. 语义对象层

为了支持实时编译，以下对象需要成为一等实体：

- Repository；
- Module；
- File；
- Symbol；
- API；
- Data Entity；
- Event；
- Concept；
- Requirement；
- Design Decision；
- Engineering Decision；
- Consensus；
- Task；
- Test；
- Runtime Component；
- Finding；
- Owner；
- Governance Zone。

不能只依赖文件路径。文件只是语义对象的一种物理投影。

## 4. 关系层

需要支持：

- contains；
- defines；
- calls；
- reads；
- writes；
- implements；
- constrained_by；
- tested_by；
- consumed_by；
- owned_by；
- governed_by；
- changed_with；
- invalidated_by；
- historically_related；
- implicated_in_finding。

每条关系有方向、来源、版本、置信度和生命周期。

## 5. 编译触发器

### 5.1 Session Start

基于任务和计划编译初始胶囊。

### 5.2 Read

Agent 读取文件或 symbol 时，加载：

- 定义和所属概念；
- 上下游；
- 适用共识；
- 历史事故；
- 活跃 Finding；
- 相关测试；
- 代码治理区。

### 5.3 Edit

编辑前追加：

- 消费方；
- 契约；
- write set；
- 禁止改变的不变量；
- 必须运行的验证器；
- 影响分析预估。

### 5.4 Test

加载测试目标、相关需求、已知失败模式、环境约束和结果解释规则。

### 5.5 Review

加载需求、设计、工程方案、diff、相关契约和独立攻击清单，但不继承作者的全部推理惯性。

### 5.6 Deploy

加载真实环境、变更范围、迁移、回滚、审批、SLO 和运行观测。

## 6. 增量编译算法

```text
1. 接收动作事件
2. 解析目标实体
3. 计算与现有上下文的差量
4. 扩展类型化邻域
5. 拉取适用共识与证据
6. 检查版本和新鲜度
7. 计算信息价值、风险和 token 成本
8. 加入新相关内容
9. 降权或移除已不相关内容
10. 记录编译决策
11. 必要时触发 Agent 重新确认任务边界
```

## 7. 上下文不是纯文本

建议将上下文分成：

- 必须服从的规则；
- 已验证事实；
- 当前任务状态；
- 可按需读取的索引；
- 设计和工程理由；
- 风险和未知；
- 示例与判例；
- 工具和权限。

不同类型用不同格式和优先级，不把所有内容拼成一个长 Markdown。

## 8. 上下文预算

上下文选择可以表达为受约束优化：

```text
最大化：完成概率 + 风险覆盖 + 信息增益
最小化：token + 干扰 + 过期信息 + 重复
约束：关键红线不得遗漏，事实版本一致
```

需要记录：

- 注入了什么；
- 为什么注入；
- Agent 是否读取或使用；
- 是否帮助发现问题；
- 是否造成浪费；
- 后续结果如何。

## 9. 缓存和失效

缓存键不能只包含任务 ID。至少考虑：

- 目标对象 hash；
- 相关概念版本；
- 共识版本；
- 投影水位；
- 动作类型；
- 任务 read/write set；
- Agent 能力等级；
- 编译器合同版本。

任一承重输入变化时，相关缓存失效或进入 suspect。

## 10. “新法区、过渡区、旧法区”

每个代码区域应有治理标签：

- `current`：完全遵守最新规则；
- `transition`：允许有限兼容和迁移；
- `legacy`：默认保持现状，禁止顺带重构；
- `protected`：必须由特定所有者批准；
- `experimental`：规则和接口尚未稳定。

上下文编译器在 Agent 进入目录或 symbol 时自动加载该治理区的规则。

## 11. 与现有 Flowness Capsule 的关系

现有 Capsule 已具备概念邻域、obligation 作用域、任务 read/write set、投影新鲜度、缓存、known facts、must-not-do 和 token 截断等基础。

下一步不是重写 Capsule，而是：

- 将 File/Symbol/Governance Zone 纳入图；
- 将工具动作变成编译触发器；
- 把 Capsule 从一次性任务产物升级为 session 内的增量状态；
- 增加上下文使用和效果反馈；
- 将设计、工程方案和 Finding 纳入候选检索。

## 12. 风险

- 图关系错误导致错误上下文；
- 过度注入造成更严重干扰；
- 编译频率过高造成性能和成本问题；
- 语义裁决器不稳定；
- 旧代码关系难以自动恢复；
- Agent 可能不使用已注入信息；
- 实时变更造成上下文前后不一致。

因此先做 shadow：只生成建议胶囊和差量，不立即影响生产 Agent；通过历史回放和真实任务对比后逐步启用。

## 13. 第一版完成标准

选择一个真实模块，证明：

- Read/Edit 时能够发现相关概念、契约、测试和治理区；
- 公共接口修改前自动加载消费方；
- 共识变更后相关缓存失效；
- 与静态胶囊相比，遗漏减少且 token 成本可控；
- 编译决策可解释、可回放；
- 错误关系不会直接放行高风险操作。
