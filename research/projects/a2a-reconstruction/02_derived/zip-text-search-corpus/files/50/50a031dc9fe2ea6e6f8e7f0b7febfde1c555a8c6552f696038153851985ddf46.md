# PRSE AI 原生规格运行包 v0.2

这不是一个固定编排框架，也不是一个“大 Prompt”。它是一套独立于运行主体的规范包：

- 人可以执行；
- 单个 Agent 可以执行；
- 多 Agent 可以执行；
- 本地 Harness 可以执行；
- 未来未知的消费方也可以执行。

包里规定的是：**要理解什么、必须产出什么、什么算合格、失败时怎样暴露、何时升级**。  
它不规定：必须使用哪个模型、多少个 Agent、哪种 DAG、哪种数据库或哪种 UI 框架。

## 四个互相独立的东西

1. **PRSE Method**：如何研究、建模、设计、校验和迭代。
2. **AI-Native Spec Protocol**：规格怎样被切分、寻址、引用、版本化和消费。
3. **Harness Adapter Contract**：任意本地 Harness 怎样映射自己的 Agent、Skill、知识包和事件。
4. **Summon Reference Pack**：把召集台作为第一份参考实现和验证场。

## 安装到本地的最小方式

将本目录复制到项目，例如：

```text
your-repo/
  .spec/
    prse/
      package.manifest.yaml
      ...
  product/
  harness/
```

然后在本地 Harness 中只实现七个逻辑钩子：

```text
read_package()
resolve_context()
route_capability()
execute_method()
validate_artifact()
emit_method_event()
escalate()
```

不要求函数名一致；只要语义对应即可。详见：

- `03_harness_adapter/ADAPTER_GUIDE.md`
- `03_harness_adapter/adapter.contract.schema.json`
- `03_harness_adapter/local-harness.mapping.example.yaml`

## 最重要的变化

过去：文档是一段按顺序阅读的文字。  
现在：规格是一张可寻址、可验证、可编译的语义图。

过去：给“某个专家”一个角色 Prompt。  
现在：声明 concern、知识、Skill、工具、作用范围、权限与验证器。

过去：强调“要几个 Agent”。  
现在：强调独立性、覆盖度、证据多样性、停止条件与质量门。Agent 数量只是执行计划，除非数量本身有统计或对抗意义。

过去：PRD、UI、市场文案各自解释产品。  
现在：它们都是同一规范内核的受控投影。


# 本地 Harness 接入指南

不需要改造你们的 Harness 去“长得像 PRSE”。只需要建立一层薄适配。

## 第一步：复制包

推荐放置：

```text
repo/
  .spec/
    prse-core/
    summon/
  harness/
  product/
```

也可以放入你们已有的 Skill/Knowledge Pack 注册目录。

## 第二步：做语义映射

把本地概念映射到八个通用概念：

| PRSE | 本地可能叫法 |
|---|---|
| CapabilityProvider | agent / worker / role / node |
| Skill | skill / recipe / program / subflow |
| ContextPack | knowledge pack / context bundle / memory |
| WorkItem | task / job / issue / node |
| Artifact | output / file / object / result |
| Validator | checker / judge / eval / gate |
| MethodEvent | trace / event / log |
| EscalationCase | human request / approval / interrupt |

名称不重要，语义必须可对应。

## 第三步：实现七个逻辑钩子

见 `02_method_runtime/runtime.contract.yaml`。  
可以是函数、命令、DAG 节点、RPC、文件监听器，甚至人工操作。

## 第四步：把质量门置于执行拓扑之上

Harness 可以自由选择：

- 一个 Agent 处理全部；
- concern 并行；
- 多候选竞争；
- 迭代批判；
- 大规模采样；
- 人机混合。

但它必须证明输出满足同一 QualityRequirement 和 Conformance Profile。

## 第五步：记录 MethodEvent

至少记录：

- 读取了哪些节点；
- 装载了哪些 Context Pack；
- 路由了哪些能力；
- 生成了哪些 Artifact；
- 哪个 Validator 通过或失败；
- 为什么升级给人类；
- 最终发布了什么版本。

## 第六步：先跑 conformance smoke test

使用 `05_conformance/smoke_tests.yaml`。  
只有基本语义通过后，再接召集台项目包。

## 一个关键边界

本地 Harness 是这个规范的一个 Consumer / Reference Runtime，不是规范本身。  
以后即使换 Harness，产品和方法的规范内核也应保持可用。
