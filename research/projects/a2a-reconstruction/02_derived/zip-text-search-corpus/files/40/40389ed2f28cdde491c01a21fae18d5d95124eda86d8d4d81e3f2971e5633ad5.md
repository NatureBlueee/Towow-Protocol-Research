# 05 · 工程共识与上下文编译规范

## 1. 工程共识的定义

工程方案是当前系统的完整实现模型；工程共识是从中提取的、后续执行者必须共同服从的稳定工程事实和约束。

工程共识解决的不是“怎么设计”，而是：

> 在大量并行、分布式、局部工作的执行者之间，哪些共同前提必须保持一致，哪些部分可以自由实现？

## 2. 共识分类

### 2.1 全局不变量

所有任务必须知道，例如身份、版本、事实源、错误模型、安全红线和审计要求。

### 2.2 域级共识

只对特定领域生效，例如调度、账本、上下文、前端、计费或部署。

### 2.3 接口契约

生产者、消费者和审查者必须知道。

### 2.4 模块约束

某个目录、服务、包或治理区适用。

### 2.5 任务局部约束

仅对当前任务有效，不得自动升级为项目永久共识。

### 2.6 临时与实验规则

有有效期、评估条件和退出方式。

### 2.7 历史规则

明确适用于旧代码或旧数据，不应被最新规范静默覆盖。

## 3. 共识对象字段

每条共识至少包含：

- 唯一 ID；
- 类型；
- 定义；
- 来源决定；
- 作用域；
- 严重等级；
- 所有者；
- 消费方；
- 版本；
- 状态；
- 生效时间；
- 失效条件；
- 验证器；
- 冲突优先级；
- 替代关系；
- 迁移要求；
- 证据和判例。

## 4. 共识不是全部注入

“每个任务都带工程共识”不应理解为把完整共识文档复制到每个上下文。

正确做法是：

> 根据当前任务、动作、目标对象、写集、概念邻域和治理区，编译出适用共识切片，并保留到完整来源的引用。

这叫 Consensus Compilation。

## 5. 上下文胶囊

一个可执行任务包至少包括：

```yaml
task_identity:
  task_id: ...
  objective: ...
  completion_contract: ...

scope:
  allowed_paths: ...
  forbidden_paths: ...
  owned_objects: ...
  read_set: ...
  write_set: ...

applicable_consensus:
  global_invariants: ...
  domain_rules: ...
  interface_contracts: ...
  legacy_governance: ...

design_trace:
  requirements: ...
  design_decisions: ...
  engineering_decisions: ...

execution_context:
  current_state: ...
  upstream_outputs: ...
  expected_consumers: ...
  active_findings: ...

validation:
  required_tests: ...
  invariant_checks: ...
  acceptance_checks: ...

change_protocol:
  may_change: ...
  must_request_change: ...
  reflow_conditions: ...
```

## 6. 上下文编译输入

- 当前任务；
- 当前动作：Read、Edit、Test、Review、Deploy；
- 文件和 symbol；
- 概念锚点；
- read/write set；
- 关联接口；
- 适用治理区；
- 当前共识版本；
- 活跃 Finding；
- 最近变更；
- 模型能力和 token 预算；
- 会话已有上下文。

## 7. 编译过程

1. 确认事实投影新鲜；
2. 解析任务和目标对象；
3. 扩展类型化邻域；
4. 获取候选共识；
5. 机械过滤作用域；
6. 对无法机械决定的候选进行语义裁决；
7. 解决冲突和版本；
8. 按风险和信息价值排序；
9. 生成最小充分胶囊；
10. 记录编译输入、选择理由和来源版本；
11. 对截断和遗漏进行显式标记。

## 8. 共识变更

共识不是永久冻结，应具有状态：

```text
proposed
→ under_review
→ active
→ challenged
→ superseded / deprecated / retired
```

修改公共共识时：

- 识别所有消费方；
- 计算影响范围；
- 选择兼容、迁移或强制升级；
- 运行相关验证器；
- 通知或重新编译受影响任务；
- 保留旧版本以支持回放；
- 完成迁移后才允许退役。

## 9. 冲突处理

发生多条规则同时适用时，不允许由 Agent 临场自行挑选。冲突决策依据：

1. 权力和安全红线；
2. 项目级明确覆盖；
3. 更具体的作用域；
4. 更新且已完成迁移的版本；
5. 显式例外；
6. 无法决定则升级。

## 10. 共识验证器

- 作用域完整性；
- 版本可解析；
- 冲突检测；
- 消费方存在性；
- 引用无悬空；
- 状态机语法；
- 规则存在验证路径；
- 胶囊中的必要共识未缺失；
- 不相关信息没有显著挤压上下文；
- Agent 的真实行为与注入规则一致。

## 11. 共识的完成标准

一个新执行者拿到相关胶囊后：

- 不需要找 Owner 猜公共定义；
- 不会与其他任务实现不兼容接口；
- 知道哪些内容不能改；
- 知道变更应走什么协议；
- 知道如何证明自己的实现符合共识；
- 能追溯每条承重规则的来源。
