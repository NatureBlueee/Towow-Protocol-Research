## Research question

Do explicit `ActionAttempt → Effect → Verification → Acceptance` distinctions
classify and recover real Harness contradictions better than:

1. a naive command-text / outer-exit / terminal-event baseline; and
2. the existing Harness domain-specific events plus authoritative state readback?

If the distinctions help but the existing Harness representation already preserves
them, are four new top-level authoritative objects actually necessary?

## Why this can change a decision

This question decides whether v0.6 should add new durable protocol state, retain
only semantic distinctions and adapters, or merge the proposal into existing
Harness events. A wrong answer creates either false closure or a parallel truth
source.

## Original objective and value dimensions

Original objective: preserve truthful reality state and choose correct recovery
without inventing closure.

Critical dimensions: effect correctness, false accept, false reject, duplicate
work, recovery safety, provenance, human attention, wall time, and implementation
state burden.

No objective rewrite is allowed to turn "correct accepted outcome" into "the
command returned zero" or "an event exists."

## Acceptance contract

- Use original assertions, authoritative filesystem/Git state, or independent
  readback as the oracle; a green test alone is not the oracle.
- Record each scenario's attempt outcome, actual effect, verification result,
  acceptance/terminality, and recovery decision separately.
- Score false accept, false reject, unsafe retry, missed retry, and Unknown.
- Preserve raw command exit and state readback.
- Any proposed new authoritative object must prevent a concrete error that an
  event subtype/state/projection cannot prevent.

## Intervention / holdout / transfer design

- Development traces: fork timeout/retry and escalation answer/reflow.
- Seed trace, excluded from holdout: current `git worktree add` success + false
  branch warning + guard log side effect.
- Task-family holdouts: rollback/conditional-index freshness and semantic readback drift.
- Mutation: remove or corrupt one decisive signal at a time; measure whether each
  strategy safely abstains or silently closes.
- Transfer: repeat scoring on at least one unplanned trace selected after the
  initial analysis.

The unplanned transfer case is preregistered in
`inputs/transfer_case_preregistration.json`: a background poller can append raw
JSON bytes that satisfy the existing test while a fresh `EventLog` reader cannot
see a valid committed record. This case asks whether existing authoritative
readback already exposes the gap and whether any new top-level state is needed.
