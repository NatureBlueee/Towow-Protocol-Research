# Analysis

## Result

On nine cases, success-looking text and the outer tool invocation exit code
each produced five false acceptances (44.4% accuracy). A postcondition alone
reached 88.9% but incorrectly accepted `effect_then_failure`: the intended
state existed, yet the executor ended in failure. Combining action-aligned exit
status with the authoritative postcondition and keeping Acceptance separate
classified all nine cases correctly.

The actual workspace witness is especially important. The first Git branch
tool invocation contained:

- a `.git/HEAD.lock` permission error;
- a success-looking `Switched to a new branch` line;
- outer tool exit code `0`, inherited from later read-only commands;
- unchanged branch state (`main`) on read-back.

This is not a hypothetical model mistake. It is an executor-boundary mismatch
observed in the real workspace.

## What this changes

The current theory correctly separates Effect, Verification, and Acceptance,
but that separation is ineffective unless the Effect Gateway defines an
**action-aligned effect unit**. A composite shell invocation cannot donate its
last exit code to every earlier mutation. The adapter must record each
state-changing attempt atomically or mark the whole bundle `unknown`, then bind
verification to an authoritative state read.

This is best expressed as an executor/Gateway invariant, not a new top-level
protocol object:

> One effect claim must identify one authoritative action boundary, its own
> executor result, and a postcondition over the intended state.

## Object ablation

The minimal record and an eager projection containing CoordinationCase,
ObjectiveVersion, Claim, Evidence, RecognitionAction, AuthorityGrant,
Commitment, Effect, Verification, Acceptance, and Settlement had identical
classification on this task. The eager projection serialized to 8,476 bytes,
3.64 times the minimal record's 2,327 bytes.

This does **not** show those distinctions are globally useless. Recognition,
Authority, Commitment, ResourceReservation, and Settlement were not decision
variables in an L1 temporary-directory task. The result supports risk-activated
materialization or derived views for this task class and rejects mandatory
eager object ceremony as a source of local correctness.

## Remaining alternatives

- The eight executed holdouts are deliberately constructed mechanism tests,
  not a natural frequency estimate.
- Only one case is an actual repository failure.
- Serialized bytes are a narrow overhead measure; full implementations may
  cache, compress, or need the objects for high-consequence governance.

The next useful transfer is to apply the same invariant to a real Harness or
deployment adapter, where Authority and Commitment become live decision
variables.
