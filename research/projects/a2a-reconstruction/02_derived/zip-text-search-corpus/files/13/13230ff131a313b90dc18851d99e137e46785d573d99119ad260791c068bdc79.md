# Candidate comparison

The selection criterion is not implementation ease. It is the expected ability to
change D01/D02/D03/D06 while preserving real authority and producing a local,
reversible, independently adopted result.

| Candidate | Authentic non-collapse | Formation space | Local adoption / ablation | Answer leakage | Main blocker | Decision |
|---|---|---|---|---|---|---|
| Harness live session migration near quota | Strong: sessions own semantic safe points and unread messages; scheduler owns quota; owner owns interruption tolerance | readiness/veto, checkpoint, account reservation, recovery | local canary possible, but natural 95% event, production migration and 24h soak are still pending | medium: recent branch already implements much machinery | production and owner Acceptance | retain as later external holdout; not first flagship |
| Allbuddy count digest → grounded advisor | Strong privacy boundary, but only one target repository | dynamic query, local compute, typed evidence | fixtures make privacy and answer grounding testable | low | current user consumer still uses hard-coded outcomes, so an engine-only repair risks a side-path demo | use as a subcondition, not the flagship outcome |
| Towow customer-hosted runtime → Allbuddy | Strong cross-runtime authority and privacy | adapter contract, capability routing, tenant-local execution | possible but requires first freezing several proposed/untracked contracts | high because current design docs already propose much of the answer | setup and architecture acceptance exceed the first episode | defer |
| Allbuddy private execution → Agent World external observation and independent adoption | Strong: Allbuddy owns tenant data/business Acceptance; World owns event provenance/reality projection; neither can inherit the other's authority | boundary query, receipt/evidence design, freshness, redaction, independent verification, reverse adoption | two isolated worktrees, existing fixtures, missing-Acceptance/stale/wrong-tenant ablations, refusal holdout | low: OQ-004/OQ-009 are explicitly open and no adapter exists | technical Acceptance can close locally; business-value Recognition remains owner-scoped | **select** |

## Source evidence

- Allbuddy `1a70fb51bfbf58a614a47962ad50855b5f7e0a10` has a real advisor
  client and tenant-scoped substrate, but `app/_lib/workspace-runtime.ts`
  still constructs hard-coded `ADVISOR_OUTCOMES` and marks every step
  `completed`.
- Agent World `393b08ea5ccf9db72bff262b86800b0e883c36cd` drops any inbound H1
  event whose `correlation.commandId` is absent from the current backend.
- Agent World `OPEN-QUESTIONS.md` leaves both external events (OQ-009) and
  viewer-specific Source Map redaction (OQ-004) open.
- Canonical Agent World semantics distinguish `Claimed`, `Observed`,
  `Agreed`, and `System-confirmed`; an event-shaped record is not
  authoritative merely because it is shaped correctly.

## Non-claims

- This selection does not claim A2A is necessary. A least-privilege central
  adapter may match it and is a required baseline.
- A local fixture receipt is not production integration.
- Automated contract acceptance is not owner recognition of business value.
