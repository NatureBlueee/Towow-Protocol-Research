# Run 002 analysis — prospective Capability Claim holdout

## Outcome

The six-axis readiness claim was more informative than a static
installed/test-exists baseline, but its preregistered accuracy target failed.

Strict first-attempt results over the six ordinary executable tasks:

- six-axis coverage: 6/6 = 100%;
- six-axis accuracy: 4/6 = 66.7%;
- static installed baseline accuracy: 3/6 = 50%;
- six-axis false-capability rate: 2/6 = 33.3%;
- static baseline false-capability rate: 3/6 = 50%.

The two six-axis misses were not model or test-family failures. They were
formation-condition failures:

1. the declared pytest `basetemp` parent did not exist; and
2. `/private/tmp` was not the Python runtime's authoritative system temp root,
   so Harness's real-ledger test guard rejected the fixture ledgers.

After the commands were transferred to a pre-created path under
`tempfile.gettempdir()`, all six executable tasks matched their intended
outcomes. That 6/6 is an intervention result and is not counted as prospective
holdout accuracy.

## Claim updates

- `C-CAP-002-A` — falsified at the preregistered threshold. Accuracy was 66.7%,
  below 80%, despite full coverage.
- `C-CAP-002-B` — supported. The shared virtual environment exited zero while
  importing `towow` from the dirty main tree rather than the isolated research
  worktree. Installed and executable did not imply correct provenance.
- `C-CAP-002-C` — qualified. Explicit `PYTHONPATH` was necessary and made source
  provenance observable, but it was insufficient by itself. Reachability and
  resourcing also required exact filesystem preconditions and a
  policy-compatible temp root.

Updated Capability Claim:

> A task is prospectively ready only when source provenance, exact command and
> working directory, required parent paths, policy-compatible write roots,
> authority, observation oracle, and recovery path are all bound to a concrete
> environment snapshot.

The six abstract labels remain useful as headings, but they do not predict by
themselves. The predictive content lives in falsifiable formation conditions.

## Baseline and holdout details

The environment transfer was highly discriminating:

- explicit worktree `PYTHONPATH` imported
  `/private/tmp/harness-towow-a2a-r5-2/harness/src/towow`;
- the unqualified shared venv imported
  `/Users/nature/个人项目/Harness/harness/src/towow`.

Both commands exited zero. Only the provenance readback distinguished the
intended task from a false success.

The two task-family holdouts passed on first execution:

- cold-start/index freshness: 6 passed;
- semantic freshness recheck: 3 passed.

The negative authorization prediction also held: no canonical-ledger write was
attempted. It is not included in executable-task accuracy because non-execution
was the acceptance condition.

One preregistered tool-availability case was removed from the active scope after
the user explicitly excluded attack/defense-related work. It is not used in
coverage, accuracy, or any claim update, and its trace will not be included in
the return packet.

## Formation conditions that changed action space

These conditions materially changed what could execute correctly:

- exact source root in `PYTHONPATH`;
- command `cwd`;
- existence of the pytest basetemp parent;
- basetemp's identity under Python `tempfile.gettempdir()`;
- local-only authority and absence of canonical-ledger writes;
- observable import path and test assertions;
- a recoverable retry that changes only the missing environment condition.

By contrast, saying that Python, pytest, or the test file “exists” did not
change the action space enough to predict the outcome.

## Limits

- The sample is small and local.
- The same researcher selected and executed the tasks.
- Passing historical tests proves their asserted contracts, not all live
  product behavior.
- No production, remote environment, or external provider transfer was tested.
