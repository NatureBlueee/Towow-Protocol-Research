# Current-system patch to v0.6

## 1. Effect reality

Retain the four semantic questions:

1. what action was attempted;
2. what state changed;
3. what independent readback verified;
4. what outcome the acceptance contract permits.

Do not require four new top-level truth objects by default. First express the
questions as fields, lifecycle states, and readback adapters over the existing
Harness truth sources.

Authority order:

```text
authoritative readback
  > validated domain event
  > terminal-looking label
  > outer command exit or text
```

Missing authoritative readback leaves the outcome pending.

## 2. Event write acceptance

A producer-shaped JSON line is not an accepted Event effect. A Harness event is
accepted only when the canonical writer has stamped it and a fresh canonical
reader can return it.

Required fields include writer-assigned sequence, timestamp, event identity,
and record hash. Raw append helpers are not a substitute for `EventLog` at
business event emission points.

## 3. Escalation lifecycle

Do not equate durable park for future redispatch with verified session
consumption.

Recommended lifecycle:

```text
answer_recorded
  -> parked_for_redispatch | push_pending
  -> delivered_to_session
  -> consumed_by_execution
  -> accepted
```

Existing event types may be retained if their field semantics and consumers are
narrowed. A new object is justified only if this cannot be represented without
false closure.

## 4. Capability Claims

The six labels `Feasible`, `Reachable`, `Authorized`, `Resourced`, `Observable`,
and `Recoverable` are headings, not predictive content.

A prospective claim must bind:

- exact source provenance and version;
- command and working directory;
- required parent paths;
- policy-compatible write and temp roots;
- dependency/runtime identity;
- authority and excluded effects;
- observation oracle;
- recovery action and stop rule.

Intervention success must remain separate from first-attempt predictive
accuracy.

## 5. Coordination baseline

Do not presume sovereign coordination is better. Compare it against:

- full-access central;
- least-privilege central;
- existing Harness plus human owner;
- the sovereign proposal.

Use the same task and acceptance oracle, and measure token, latency, disclosure,
human attention, handoff failure, boundary maintenance, reconciliation, and
recovery. Retain the simpler winner.

For the current local task, least-privilege central plus existing Harness is the
provisional winner. No production or cross-organization claim follows.
