# Flowness Harness 认知工程与可靠交付体系 v0.1

本知识包沉淀了围绕 Flowness、Agent Harness、设计、工程方案、工程共识、计划执行、验证与持续演进的一整套研究。

它不是某一次升级的任务清单，也不是把若干最佳实践拼成一篇长文。它的目标是建立一套可继续研究、可实例化、可验证、可与外部资料汇合的工程知识体系。

## 核心命题

Harness 不是“让多个 Agent 自动写代码”的框架，而是一套把模糊意图逐层转化为可验证现实的认知—设计—工程—执行系统：

```text
委托与问题发现
  → 采访与需求建模
  → 设计
  → 工程方案
  → 工程共识
  → 计划编译
  → 执行
  → 独立审查与验证
  → 修复 / Replan / Re-engineer / Redesign / Re-interview
  → 运行证据与持续演进
```

## 阅读入口

1. `00-导航与使用说明.md`：本套文档如何使用、怎样继续合并资料。
2. `01-Harness认知工程总纲.md`：完整架构、阶段边界与核心原则。
3. `03-设计系统规范.md`：设计究竟是什么，以及如何系统地产生高质量设计。
4. `04-工程方案系统规范.md`：怎样把设计编译成可实现、可维护、可验证的工程系统。
5. `10-Flowness现状映射与升级路线.md`：现有 Flowness 已有什么、缺什么、下一轮应该做到哪里停止。
6. `ROADMAP.md`：可执行的分阶段建设路线。

## 文档状态标记

本文档体系使用四类内容标记：

- **已验证事实**：来自已查看的 Flowness 仓库代码、规范或运行记录。
- **有证据推断**：根据多个事实推导，但尚未通过完整运行实验确认。
- **设计建议**：建议未来采用的结构或机制，不伪装成当前能力。
- **开放问题**：目前没有足够证据或需要 Owner / 专家裁决的事项。

## 重要边界

本版本依据 2026-07-23 之前的对话、Flowness GitHub 仓库快照与公开行业资料整理。它没有读取服务器上当时的实时账本，也没有执行全量生产验证。因此，关于“当前是否已经真实启用”的结论必须在实施前重新用代码、账本和运行行为复核。

# 00 · 导航与使用说明

## 1. 这套文档解决什么问题

此前关于 Harness 的讨论已经产生了大量高质量判断，但这些判断容易散落在长对话、设计稿、代码注释、Skill、运行事故和临时修复里。后续每次进入新问题，都可能重新发明已有概念，或者只记住上一轮结论而忘记为什么。

本套文档要解决三件事：

1. **把思考对象化**：将“采访、设计、工程方案、工程共识、验证器、上下文、回流”等概念定义为有边界、有输入输出、有生命周期的对象。
2. **把方法过程化**：明确每一阶段如何工作、依赖什么证据、怎样发散、怎样收敛、怎样完成。
3. **把判断可验证化**：任何重要判断都应说明为什么、如何被证伪、怎样知道已经真实落地。

## 2. 文档体系不是新的事实源

Flowness 已经选择事件账本和投影作为正式事实源。本文档体系的定位是：

- 方法与设计的权威研究基线；
- 新对象和协议进入代码、Schema、事件类型前的设计空间；
- 给人和 Agent 阅读的可进入视图；
- 与外部研究汇合的承载层。

当文档与正式代码、Schema、账本或生产行为冲突时，不得通过“更新文字说法”掩盖冲突。应当创建冲突记录，判断是文档过期、实现偏差、设计变更还是运行故障，并经正式变更流程处理。

## 3. 推荐使用方式

### 3.1 开始一个新项目

按以下顺序实例化：

1. 建立项目委托与风险等级；
2. 选择需要启用的阶段强度；
3. 实例化 Problem IR、Design IR、Engineering IR；
4. 将稳定的工程事实编译为工程共识；
5. 生成任务图和上下文胶囊；
6. 执行、审查、收集证据；
7. 将新经验回流到设计、规则、判例或验证器。

### 3.2 调查 Flowness 自身

先使用调查型流程，不直接把发现的问题变成修复任务：

1. 枚举真实对象、代码入口、事件、投影、运行服务；
2. 维护覆盖表；
3. 为每个问题单独建档；
4. 区分症状、根因、竞争解释；
5. 在形成设计空间后再决定修补、重构或保持现状。

### 3.3 吸收外部资料

新论文、开源框架、企业实践或专家文章不直接“写进总纲”。先建立资料卡：

- 它解决的真实问题；
- 适用条件；
- 使用的对象和机制；
- 证据等级；
- 与 Flowness 同构的部分；
- 与 Flowness 冲突的部分；
- 可吸收机制；
- 不应吸收的外部假设。

然后把可吸收内容映射到现有对象。如果现有对象无法容纳，才提出新增本体或协议。

## 4. 文档目录

| 文档 | 作用 |
|---|---|

| 05 | 工程共识、作用域、上下文胶囊与动态加载 |
| 06 | 计划、执行、审查、修复与多级回流 |

| 08 | 实时语义空间与上下文编译器 |

## 5. 每份正式设计应具备的最小结构

无论主题大小，至少回答：

1. **问题**：现在什么会坏，证据是什么？
2. **目标**：要改变什么现实，不追求什么？
3. **对象**：系统里有哪些主体、对象、状态和关系？
4. **机制**：为什么该结构能稳定地产生目标结果？
5. **候选**：还有哪些不同机制的方案？
6. **选择**：为什么选择当前方案，放弃了什么？
7. **实现**：如何映射到代码、数据、协议和运行环境？
8. **验证**：怎样证明有效，哪些事实能推翻它？
9. **演化**：如何升级、迁移、回滚、废弃？
10. **边界**：本版本明确不解决什么？

## 6. 版本纪律

- 文档只追加新版本，不静默覆盖重大历史决定；
- 被替代的判断保留，标记 `superseded_by`；
- 每一轮升级必须给出基线、目标、实验证据和停止条件；
- 不以“还能继续优化”为理由无限延期冻结；
- 任何涉及真实生产的机制，先 shadow、再受控启用、再逐步扩大。

# 01 · Harness 认知工程总纲

## 1. 核心判断

一个工业级 Harness 不是 Agent 调度器、Prompt 集合、工作流图或代码生成器。它是一套将人的意图和组织判断逐层编译为可验证现实的系统。

它面对的根问题是：

> 大模型具备强大的局部生成能力，但缺少稳定身份、长期记忆、统一事实世界、明确责任、可靠边界和自然的一致性。怎样让大量局部智能体在长周期复杂工作中，既能自主发挥，又不改写共同世界？

因此 Harness 的职责不是让 Agent “更聪明”，而是建立：

- 正确的问题表示；
- 分阶段的认知生产；
- 可追溯的决策；
- 作用域明确的共识；
- 可编译的上下文；
- 可恢复的执行；
- 独立的验证；
- 正确层级的回流；
- 可观测、可审计、可演化的组织制度。

## 2. 完整生命周期

```text
0. 委托与准入
1. Sensemaking / 调查
2. 采访与需求建模
3. 设计
4. 工程方案
5. 工程共识
6. 计划编译
7. 执行
8. 独立审查与验证
9. 修复与多级回流
10. 发布、运行与持续学习
```

并非每项工作都必须走全部阶段。系统先按风险、复杂度、影响范围和不确定性选择流程强度。

## 3. 为什么必须分层

需求、设计、工程、共识、计划和实现不是同一种信息的不同写法，而是不同性质的判断：

| 层级 | 回答的问题 | 主要失败 |
|---|---|---|
| 委托 | 谁要改变什么现实，谁能拍板 | 范围与权力不清 |
| 调查 | 真实系统发生了什么 | 把猜测当事实 |
| 采访/需求 | 人究竟想要什么 | 意图丢失、隐性需求未发现 |
| 设计 | 应创造怎样的系统 | 方案不自洽、功能堆砌 |
| 工程方案 | 如何在真实约束下实现 | 技术不可行、不可维护 |
| 工程共识 | 所有执行者必须共同服从什么 | 局部漂移、接口分裂 |
| 计划 | 怎样切成可执行、可合并的工作 | 任务不闭包、依赖错误 |
| 执行 | 如何产生真实改变 | 越权、假完成、局部正确 |
| 验证 | 怎样独立证明结果成立 | 自证、指标投机、漏检 |
| 回流 | 问题应回到哪一层 | 所有问题都变成重新执行 |

把这些层压缩成一份 Spec 或一个 Architect Agent，会把未解决的上游判断偷偷交给下游执行者。

## 4. 两类编译和一种冻结

完整管线的关键不只是阶段，而是三种性质不同的转换。

### 4.1 设计编译

```text
Problem / Requirement IR
    → Design IR
```

将目标、约束、价值和场景编译成主体、对象、机制、行为、状态、权限、体验与失败恢复。

设计编译具有创造性，不存在唯一正确结果，必须产生候选方案、比较并接受攻击。

### 4.2 工程编译

```text
Design IR
    → Engineering IR
```

将设计对象和机制编译为组件、接口、数据、状态机、任务、运行时、SLO、测试、发布与运维结构。

工程编译受现实技术、成本、团队和运行环境约束，必须提供证据和实验。

### 4.3 共识冻结

```text
Engineering IR
    → Scoped Consensus
```

从完整工程方案中提取跨任务稳定、必须共同遵守的事实与约束，并计算其作用域、版本和变更规则。

共识不是另一轮设计。它不负责继续发散，而负责明确：哪些可以自由实现，哪些不得漂移。

## 5. 根原则

### 5.1 事实和方案分离

当前系统的真实行为、对真实行为的解释、未来建议不得混写。

### 5.2 上下文最小充分

不给 Agent 最多的信息，而给它完成当前合法判断所需的最小充分上下文，并保留可按需展开的路径。

### 5.3 局部自治，全局一致

执行者可以决定局部实现，但不能私自修改公共契约、产品目标和全局不变量。

### 5.4 证据优先于语言流畅

方案写得完整不代表成立。重要结论需要代码、数据、运行、实验或用户行为支持。

### 5.5 任何关键方案必须可被推翻

方案应写明假设、反例、失败条件和重开触发器。

### 5.6 错误回到正确层级

执行错误修执行；计划错误重计划；工程假设失效重做工程方案；设计结构错误重设计；意图理解错误重采访。

### 5.7 验证器拥有真实权力

规则只有被验证器、权限、Schema、CI 或运行门执行时，才是制度。只写在提示词里的规则是建议。

### 5.8 人是价值与授权的源头

系统可以发现事实、形成候选、推演后果，但不能擅自创造组织价值标准或跨越不可逆权力边界。

### 5.9 生产和演进分轨

稳定版本负责交付；新机制在 shadow 和 dogfood 中证明价值后才进入生产。

### 5.10 复杂度也需要被治理

新 Agent、新事件、新对象、新 Gate、新文档都有维护成本。增加机制前必须证明它解决的风险大于引入的协调成本。

## 6. Harness 的五个平面

### 6.1 语义平面

定义系统中的主体、对象、关系、规则、状态和版本，是世界模型。

### 6.2 认知平面

负责调查、采访、设计、工程推理、评审和知识生成。

### 6.3 控制平面

负责生命周期、路由、调度、权限、审批、回流和资源分配。

### 6.4 执行平面

负责模型调用、工具、工作区、代码、浏览器、沙箱和外部系统操作。

### 6.5 证据平面

负责事件、Trace、测试、运行指标、审计、归因和完成证明。

外部 Agent 框架通常覆盖控制和执行平面；Flowness 的独特价值应当集中在语义、认知和证据平面，并通过适配器使用外部基础设施。

## 7. 任务强度分级

建议至少建立五级工作模式：

| 等级 | 典型任务 | 必需流程 |
|---|---|---|
| L0 | 格式、局部机械修改 | 执行 + 机械验证 |
| L1 | 小功能、低风险修复 | 轻量 Spec + 执行 + Review |
| L2 | 新模块、中等影响 | 采访 + 设计 + 工程方案 + 完整闭环 |
| L3 | 跨模块、公共契约、高风险 | 多方案、红队、共识冻结、分批迁移 |
| L4 | 跨系统、生产关键、长期迁移 | 专家委员会、实验、灰度、长期治理 |

流程强度由风险和不确定性决定，不由“任务看起来正式”决定。

## 8. 完成定义

一个阶段完成，不是 Agent 声称完成，而是满足阶段合同。

整个项目完成至少需要：

- 目标有可观察结果；
- 关键需求有设计响应；
- 设计对象有工程实现；
- 公共实现遵守共识；
- 计划依赖和任务边界被验证；
- 代码、配置、数据和部署真实生效；
- 独立验证通过；
- 未验证部分明确可见；
- 变更历史和证据可以追溯；
- 运行一段时间后没有出现不可接受退化。

## 9. 本总纲的停止边界

本总纲不规定每个领域的具体语义，也不承诺对所有可讨论问题实现自动化。一个领域只有在具备可表示对象、可获取证据、可接受反馈和明确授权后，才适合进入 Harness 的自动闭环。

# 02 · 问题建模、调查与采访系统规范

## 1. 为什么采访前还需要 Problem Model

当用户能清楚说出目标和约束时，可以直接进入采访。但很多复杂任务中，连“问题是什么”本身都不清楚：

- 用户只看见一个症状；
- 使用了一个可能误导设计的名词；
- 多个问题被压成一句抱怨；
- 系统现状与文档不一致；
- 用户有强烈感受，却没有可操作表达。

此时直接整理需求，会把用户当时的描述冻结成错误边界。

因此正式管线应允许：

```text
模糊现象
  → Sensemaking / Investigation
  → Problem IR
  → Interview / Requirement IR
```

调查解决“真实发生了什么”，采访解决“人在这些事实与可能性面前究竟要什么”。

## 2. Problem IR

Problem IR 至少包含：

- 委托与主体；
- 原始现象；
- 已验证事实；
- 有证据推断；
- 假设；
- 未知；
- 竞争解释；
- 受影响对象；
- 出现条件；
- 因果候选；
- 证据与反证；
- 当前规避方式；
- 风险与紧急度；
- 可改变和不可改变条件；
- 下一步信息价值最高的调查动作。

Problem IR 不应过早包含唯一解决方案。

## 3. 调查方法

### 3.1 用户的词是探针，不是边界

用户说“可观测性不足”，应继续调查：

- 系统是否有稳定身份；
- 状态是事实还是自我报告；
- 事件是否完整；
- 不同数据源是否矛盾；
- 运行结果是否被消费；
- 当前状态能否由历史重建；
- 错误是否真实改变生命周期；
- 用户能否从观测做出正确行动。

### 3.2 从真实系统重建，而不是从架构图复述

重要判断需要沿证据链追踪：

```text
定义
→ 注册
→ 调用方
→ 真实运行是否调用
→ 写入什么状态
→ 下游是否消费
→ 用户是否能观察
```

文档、代码、日志、账本和测试都可能单独失真，承重判断至少使用两个独立来源。

### 3.3 覆盖显式化

每次大型调查维护覆盖表：

- 已检查区域；
- 只有文档证据的区域；
- 有代码无运行证据的区域；
- 尚未检查区域；
- 版本和时间范围；
- 每个区域置信度。

### 3.4 每个问题独立建档

问题档案至少包含：现象、条件、影响、代码位置、运行证据、可能原因、竞争解释、反例、相关问题、验证实验、修复候选、风险和完成标准。

没有竞争解释和反例的“根因”只是主张。

## 4. 采访的本质

采访不是问卷，也不是把原话整理成 PRD。它是将人的高维判断转化为下游可工作的结构，同时尽量不损失人的价值、直觉和隐性边界。

采访应完成：

- 找到用户真正想改变的现实；
- 区分手段和目的；
- 发现未说出的冲突和反目标；
- 给出具体草样让用户对“东西”作判断；
- 用场景撞出信息缺口；
- 将可由行业知识、历史判例和系统事实回答的问题先自答；
- 只把真正需要价值裁决的问题交还用户。

## 5. 推荐采访循环

1. **预研究**：读取历史判断、当前系统、外部成熟实践。
2. **主动推测**：用自己的话说明理解，并标注可撤销。
3. **构造草样**：给出两到三个机制或场景真正不同的样例。
4. **场景推演**：从用户、系统、异常和长期维护视角走一遍。
5. **缺口图**：记录哪些信息仍无法自答，以及它们的依赖关系。
6. **按信息价值提问**：优先问能消除最多下游不确定性的上游问题。
7. **一致性检查**：找出用户不同回答之间的冲突。
8. **回读确认**：用可进入的语言复述最终理解，由用户确认。
9. **发布 Requirement IR**：保留原话、推断、假设和待定项。

## 6. Requirement IR

需求对象至少包括：

- `requirement_id`；
- 来源与原话；
- 类型：目标、功能、质量、约束、反目标、风险、体验、治理；
- 适用主体和场景；
- 优先级与理由；
- 决策权归属；
- 成功场景；
- 失败场景；
- 可量化响应；
- 依赖和冲突；
- 置信度；
- 是否已由用户确认；
- 哪些事实会使它失效。

## 7. 从抽象价值到设计要求

用户说“要美”“要可靠”“要像一个活的世界”，不能直接进入实现。

先转化为质量场景。例如：

```text
当用户第一次进入系统时，
在没有阅读说明文档的情况下，
应在 30 秒内识别主要对象、当前状态和可执行动作，
且不把装饰性元素误认为真实控制入口。
```

质量场景至少包含：刺激源、刺激、环境、对象、响应和可测指标。

## 8. 采访完成门

采访完成不是“用户没有更多要说”。应满足：

- 主要目标有来源；
- 关键冲突已暴露；
- 反目标明确；
- 价值判断与工程判断分开；
- 高风险隐性需求已被确认或拒绝；
- 成功和失败具有可观察表现；
- 下游设计者无需重新猜测用户意图；
- 仍未知的问题显式存在；
- 用户知道自己确认了什么。

## 9. 失败与回流

- 发现事实理解错误：回调查；
- 用户目标发生变化：重采访；
- 设计发现不可调和冲突：回用户裁决；
- 执行才发现核心信息缺失：登记 Interview Gap，并分析为什么入口未发现；
- 同类缺口重复发生：升级采访方法、场景库或验证器，而不是只补当前需求。

# 03 · 设计系统规范

## 1. 设计是什么

设计不是把需求换一种更专业的写法，也不是列功能、画界面或选技术栈。

设计是在目标、约束和现实条件之间，创造一个能够稳定产生预期结果的人工秩序。

它回答：

> 系统应当由哪些主体、对象、关系、机制、状态、规则和体验组成，才能满足显性需求、隐性需求和长期演化要求？

需求描述“想改变什么”，设计定义“应该创造什么”。需求不会自然推出唯一设计，因此设计必须是方案空间搜索，而不是一次生成。

## 2. Design IR 的主要对象

Design IR 至少覆盖十二个设计域。

### 2.1 目的与价值

- 目标树；
- 反目标；
- 成功上限与最小成功；
- 价值冲突；
- 不做的后果；
- 可能出现的代理目标和指标投机。

### 2.2 主体

- 人；
- Agent；
- 组织；
- 外部系统；
- 决策者；
- 所有者；
- 消费者；
- 审查者；
- 受影响但无操作权的主体。

每个主体定义身份、职责、能力、知识边界、权限、责任和生命周期。

### 2.3 对象与本体

定义系统实际管理的东西，而不是先从界面组件出发。

每个对象至少包含：身份、类型、属性、所有者、来源、状态、版本、关系、生命周期、失效条件和验证状态。

### 2.4 场景

- 正常；
- 边界；
- 异常；
- 对抗；
- 恢复；
- 并发；
- 长周期维护；
- 信息不足；
- 外部系统失效；
- 人类延迟响应。

### 2.5 机制

功能说明系统能做什么；机制解释为什么它能稳定做到。

典型机制包括：选择、路由、共识、锁、租约、审批、冲突处理、回流、恢复、校准、激励、权限、失效传播和经验沉淀。

### 2.6 信息与认知

定义谁在什么时候知道什么，信息以事实、规则、建议还是假设出现，如何发现过期、冲突和缺失。

### 2.7 行为与交互

定义主体可执行动作、动作前置条件、结果、反馈、失败处理和不可逆边界。

### 2.8 权限与治理

定义谁可以创建、修改、批准、否决、绕过和废弃哪些对象；紧急操作如何追责与补偿。

### 2.9 生命周期

每类对象都有自己的状态机。通用框架只规定语法，不用一套固定状态替代领域语义。

### 2.10 失败与恢复

设计阶段就定义失败，而不是等实现后再补异常处理。

### 2.11 质量属性

性能、可靠性、安全、可维护性、可解释性、成本、体验、可扩展性必须转化为具体场景和响应指标。

### 2.12 表达与体验

界面、文档、协议和可视化是底层对象和状态的投影。设计应先决定世界如何运行，再决定如何让不同主体看见和操作。

## 3. 从需求到设计要求

设计编译不是简单映射，而是逐层推导：

```text
抽象价值
→ 可观察品质
→ 质量场景
→ 产生品质的机制
→ 承载机制的对象与关系
→ 行为与状态
→ 反馈与恢复
→ 验收证据
```

例如“避免 Agent 漂移”：

```text
需求：一百个执行者不会各自改写公共定义
→ 品质：跨任务一致性
→ 场景：多个执行者并发修改公共 API
→ 机制：公共契约身份 + 作用域 + 版本 + 所有权 + 变更审批
→ 对象：Contract、Consumer、ChangeProposal、ConsensusVersion
→ 行为：提出、评审、冻结、迁移、废弃
→ 验证：不兼容修改被阻止；所有消费方被识别；迁移完成后旧版本可退役
```

## 4. 设计工作的五种认知动作

### 4.1 建模

建立问题、目标、约束、主体、对象和场景模型。没有模型时不要急着发散方案，否则候选只是表面创意。

### 4.2 发散

候选方案必须在核心机制上不同，而不是同一架构换名称或配色。

每个候选说明：

- 核心机制；
- 适用条件；
- 关键假设；
- 优势；
- 未解决问题；
- 新增复杂度；
- 不可逆决定；
- 失败模式；
- 渐进实施方式。

### 4.3 推演

将候选放进正常、极端、并发、故障、资源不足和一年后维护场景中运行。必须追踪对象、信息、状态和责任如何变化。

### 4.4 对抗

红队不只找 Bug，而是尝试证明设计不成立：

- 需求未满足；
- 隐性需求被破坏；
- 用户可绕开机制；
- 权限结构不成立；
- 局部正确但全局错误；
- 指标可被投机；
- 维护成本超过收益；
- 组织现实无法执行；
- 失败恢复会制造更大风险。

### 4.5 收敛

形成明确的设计决定，而不是投票选“最受欢迎”的方案。

决定应记录：候选、评价维度、证据、选择理由、牺牲、风险、假设、证伪条件和重开触发器。

## 5. 设计参谋团

多 Agent 设计不应只是十个 Agent 各写一份方案。建议按认知职能组织：

- Problem Modeler：维护问题和需求模型；
- Domain Modeler：构造对象与关系；
- Mechanism Designer：提出不同机制；
- Scenario Simulator：推演场景；
- Quality Attribute Analyst：构造质量场景和权衡；
- Comparative Researcher：研究行业案例和失败史；
- Adversarial Reviewer：寻找反例；
- Synthesis Architect：综合并形成决定；
- Traceability Reviewer：检查需求覆盖和推导链。

不同职能可以由同一 Agent 在小任务中串行承担；复杂任务才需要隔离上下文和独立角色。

## 6. 设计产物

设计阶段至少输出：

1. Design Context；
2. 需求—设计覆盖矩阵；
3. 主体与权限模型；
4. 对象本体；
5. 关系图；
6. 状态机；
7. 关键场景和时序；
8. 机制目录；
9. 质量属性场景；
10. 候选方案对比；
11. 设计决定记录；
12. 风险与开放问题；
13. 证伪条件；
14. 交给工程方案的明确接口。

## 7. 设计验证器

### 7.1 需求覆盖

每个高优需求至少有一个设计响应；每个设计对象都能解释服务于什么目标，避免“无主设计”。

### 7.2 本体完整

关键主体、对象、动作、关系、状态、权限、失败和生命周期没有静默缺位。

### 7.3 场景闭合

关键场景可以从触发走到成功或恢复，不留下“交给系统自行处理”的空白。

### 7.4 一致性

状态、权限、关系和流程之间不矛盾；不同视图描述同一对象时语义一致。

### 7.5 可证伪

方案存在可观测的失败条件，不以“原则上可以”作为完成。

### 7.6 可工程化

工程团队无需重新发明产品结构，能够开始技术建模和实验。

## 8. 设计完成门

设计完成需要满足：

- 关键需求有设计响应；
- 候选机制经过比较；
- 重要假设有验证计划；
- 正常、异常、对抗和演化场景已推演；
- 权限与失败恢复明确；
- 质量属性可测；
- 红队问题已解决、接受或登记；
- 未决问题不阻塞下一阶段；
- 工程方案的自由度和不得改写的设计事实已明确。

## 9. 设计回流

- 工程发现不可实现但目标不变：回设计比较替代机制；
- 工程成本明显超出价值：回设计寻找更简单机制；
- 运行结果不满足真实需求：重设计；
- 需求本身被误解：重采访；
- 只是局部实现错误：不得借机重开设计。

# 04 · 工程方案系统规范

## 1. 工程方案是什么

工程方案是将 Design IR 编译为一个在真实技术、资源、组织和运行约束下可实现、可验证、可维护、可演化的系统模型。

它不负责重新定义产品目标，也不应暗中修改设计。如果工程约束迫使设计改变，必须显式回流，而不是由实现者静默替换。

## 2. Engineering IR 的主要内容

### 2.1 系统边界

- 系统与外部依赖；
- 信任边界；
- 数据边界；
- 部署边界；
- 责任边界；
- 故障隔离边界；
- 可替换与不可替换组件。

### 2.2 组件与模块

明确服务、包、Worker、Agent、队列、数据库、缓存、对象存储、策略引擎、审计系统和观测系统的职责、接口和所有权。

### 2.3 接口契约

每个接口至少定义：

- 身份和版本；
- 调用方与消费方；
- 输入输出类型；
- 必填、默认、范围和单位；
- 幂等键；
- 超时和重试；
- 限流；
- 错误模型；
- 兼容性；
- 权限；
- 审计；
- 弃用与迁移。

### 2.4 数据模型

包括实体、值对象、聚合边界、唯一性、一致性、索引、生命周期、归档、删除、版本、迁移、隐私和恢复。

### 2.5 状态与事务

- 哪些状态持久；
- 哪些状态可重建；
- 强一致和最终一致边界；
- 原子事务；
- Saga 和补偿；
- 并发写入；
- 锁、租约和乐观并发；
- 幂等和去重；
- 部分成功如何表达。

### 2.6 调度与资源

- 模型路由；
- Agent 池；
- token、CPU、内存和时间预算；
- 优先级和抢占；
- 背压；
- 并发帽；
- 超时；
- 熔断；
- 退避；
- 降级；
- 防止重试风暴。

### 2.7 安全与权限

- 身份认证；
- 最小权限；
- 文件、分支、工具和网络访问；
- 密钥；
- 沙箱；
- 多租户隔离；
- 高风险操作审批；
- 越权检测；
- 审计和追责。

### 2.8 可观测性

不仅监控进程和错误，还要记录：

- 当前任务和阶段；
- 使用的 Design/Engineering/Consensus 版本；
- 上下文编译输入；
- 工具和外部调用；
- 决策和证据；
- 产物和消费方；
- 阻塞与回流；
- 资源消耗；
- 完成判定。

### 2.9 测试与验证

至少考虑：

- 单元；
- 集成；
- 端到端；
- 契约；
- 状态机；
- 属性测试；
- 变形测试；
- 并发测试；
- 故障注入；
- 回放；
- 权限；
- 迁移；
- 漂移；
- Agent 行为；
- 追溯完整性。

### 2.10 发布、迁移与回滚

- feature flag；
- shadow；
- canary；
- 灰度；
- 双写；
- 数据迁移；
- schema 兼容；
- 旧版本退役；
- 回滚条件；
- 故障恢复演练。

### 2.11 运维和长期演化

明确所有者、SLO、报警、值班、容量、成本、依赖更新、技术债、灾难恢复和一年后的可理解性。

## 3. 工程方案的证据结构

每个承重技术决定应形成增强型 ADR：

```yaml
decision_id: ADR-042
question: 如何保证多个执行 Agent 不同时破坏公共协议
context: ...
candidates:
  - global_mutex
  - optimistic_concurrency
  - ownership_partition
  - proposal_approval_merge
evaluation:
  consistency: ...
  throughput: ...
  recovery: ...
  operational_cost: ...
decision: ownership_partition + optimistic_concurrency
reasons: ...
tradeoffs: ...
evidence:
  source_review: ...
  prototype: ...
  benchmark: ...
assumptions: ...
falsification_conditions: ...
reopen_trigger: ...
```

方案的可信度来自证据等级，而不是作者语气。

## 4. 技术研究方法

### 4.1 文献和权威资料

优先官方文档、标准、论文和成熟项目的设计记录。搜索只能找到入口，不能替代验证。

### 4.2 源码考古

研究开源项目时，不只读 README：

- 找核心类型和接口；
- 找注册和调用路径；
- 看测试如何表达不变量；
- 看故障和 Issue；
- 看历史设计为何改变；
- 建最小实验验证真实行为。

### 4.3 原型与基准

对性能、并发、上下文选择、模型行为和外部依赖进行可重复实验。记录环境、输入、次数、方差和失败样本。

### 4.4 生产证据

原型通过不代表生产成立。需要真实负载、长周期、故障恢复、运维成本和用户结果。

## 5. 以简驭繁

完整工程思考可以很长，最终实现不应因此自动复杂。

工程方案必须比较：

- 不改；
- 加观测；
- 最小修补；
- 局部重构；
- 适配层；
- 统一抽象；
- 渐进迁移；
- 完整替换。

最优方案不是对象最多、Gate 最多或文档最长，而是在风险可接受的前提下，用最少长期复杂度达到目标。

## 6. 工程方案审查

至少包含：

- 架构与质量属性；
- 数据和一致性；
- 并发；
- 安全；
- 性能和容量；
- 测试和可验证性；
- 可运维性；
- 迁移与回滚；
- 成本；
- 复杂度与技术债；
- 组织可执行性；
- 设计忠实度。

评审者不得只给“同意/不同意”，应提出具体风险、证据、反例和修改条件。

## 7. 工程方案完成门

- 设计对象均有工程映射或明确不实现；
- 关键接口和数据契约完整；
- 并发、错误和部分成功有处理方式；
- 安全和权限边界明确；
- 质量属性映射到指标和测试；
- 关键技术选型有证据；
- 发布、迁移、回滚和运维可执行；
- 主要风险经过攻击；
- 开放问题有所有者和触发条件；
- 可以从中提取工程共识和计划，而无需下游重新做架构设计。

# 05 · 工程共识与上下文编译规范

## 1. 工程共识的定义

工程方案是当前系统的完整实现模型；工程共识是从中提取的、后续执行者必须共同服从的稳定工程事实和约束。

工程共识解决的不是“怎么设计”，而是：

> 在大量并行、分布式、局部工作的执行者之间，哪些共同前提必须保持一致，哪些部分可以自由实现？

## 2. 共识分类

### 2.1 全局不变量

所有任务必须知道，例如身份、版本、事实源、错误模型、安全红线和审计要求。

### 2.2 域级共识

只对特定领域生效，例如调度、账本、上下文、前端、计费或部署。

### 2.3 接口契约

生产者、消费者和审查者必须知道。

### 2.4 模块约束

某个目录、服务、包或治理区适用。

### 2.5 任务局部约束

仅对当前任务有效，不得自动升级为项目永久共识。

### 2.6 临时与实验规则

有有效期、评估条件和退出方式。

### 2.7 历史规则

明确适用于旧代码或旧数据，不应被最新规范静默覆盖。

## 3. 共识对象字段

每条共识至少包含：

- 唯一 ID；
- 类型；
- 定义；
- 来源决定；
- 作用域；
- 严重等级；
- 所有者；
- 消费方；
- 版本；
- 状态；
- 生效时间；
- 失效条件；
- 验证器；
- 冲突优先级；
- 替代关系；
- 迁移要求；
- 证据和判例。

## 4. 共识不是全部注入

“每个任务都带工程共识”不应理解为把完整共识文档复制到每个上下文。

正确做法是：

> 根据当前任务、动作、目标对象、写集、概念邻域和治理区，编译出适用共识切片，并保留到完整来源的引用。

这叫 Consensus Compilation。

## 5. 上下文胶囊

一个可执行任务包至少包括：

```yaml
task_identity:
  task_id: ...
  objective: ...
  completion_contract: ...

scope:
  allowed_paths: ...
  forbidden_paths: ...
  owned_objects: ...
  read_set: ...
  write_set: ...

applicable_consensus:
  global_invariants: ...
  domain_rules: ...
  interface_contracts: ...
  legacy_governance: ...

design_trace:
  requirements: ...
  design_decisions: ...
  engineering_decisions: ...

execution_context:
  current_state: ...
  upstream_outputs: ...
  expected_consumers: ...
  active_findings: ...

validation:
  required_tests: ...
  invariant_checks: ...
  acceptance_checks: ...

change_protocol:
  may_change: ...
  must_request_change: ...
  reflow_conditions: ...
```

## 6. 上下文编译输入

- 当前任务；
- 当前动作：Read、Edit、Test、Review、Deploy；
- 文件和 symbol；
- 概念锚点；
- read/write set；
- 关联接口；
- 适用治理区；
- 当前共识版本；
- 活跃 Finding；
- 最近变更；
- 模型能力和 token 预算；
- 会话已有上下文。

## 7. 编译过程

1. 确认事实投影新鲜；
2. 解析任务和目标对象；
3. 扩展类型化邻域；
4. 获取候选共识；
5. 机械过滤作用域；
6. 对无法机械决定的候选进行语义裁决；
7. 解决冲突和版本；
8. 按风险和信息价值排序；
9. 生成最小充分胶囊；
10. 记录编译输入、选择理由和来源版本；
11. 对截断和遗漏进行显式标记。

## 8. 共识变更

共识不是永久冻结，应具有状态：

```text
proposed
→ under_review
→ active
→ challenged
→ superseded / deprecated / retired
```

修改公共共识时：

- 识别所有消费方；
- 计算影响范围；
- 选择兼容、迁移或强制升级；
- 运行相关验证器；
- 通知或重新编译受影响任务；
- 保留旧版本以支持回放；
- 完成迁移后才允许退役。

## 9. 冲突处理

发生多条规则同时适用时，不允许由 Agent 临场自行挑选。冲突决策依据：

1. 权力和安全红线；
2. 项目级明确覆盖；
3. 更具体的作用域；
4. 更新且已完成迁移的版本；
5. 显式例外；
6. 无法决定则升级。

## 10. 共识验证器

- 作用域完整性；
- 版本可解析；
- 冲突检测；
- 消费方存在性；
- 引用无悬空；
- 状态机语法；
- 规则存在验证路径；
- 胶囊中的必要共识未缺失；
- 不相关信息没有显著挤压上下文；
- Agent 的真实行为与注入规则一致。

## 11. 共识的完成标准

一个新执行者拿到相关胶囊后：

- 不需要找 Owner 猜公共定义；
- 不会与其他任务实现不兼容接口；
- 知道哪些内容不能改；
- 知道变更应走什么协议；
- 知道如何证明自己的实现符合共识；
- 能追溯每条承重规则的来源。

# 06 · 计划、执行、审查与修复闭环规范

## 1. 计划是编译，不是任务列表

计划将 Engineering IR 和 Scoped Consensus 编译为可执行任务图。

它需要同时优化：

- 认知闭包；
- 依赖正确；
- 并行度；
- 合并风险；
- 上下文成本；
- 验证成本；
- 失败隔离；
- 关键路径；
- 人工审批点。

## 2. 任务对象

每个任务至少包含：

- 任务身份；
- 交付物，而不是仅动作；
- 设计与工程来源；
- 完成合同；
- read/write set；
- 目标对象和文件；
- 上游依赖；
- 预期消费方；
- 所需共识；
- 权限和工具；
- 资源预算；
- 必须运行的验证器；
- 失败与升级路径；
- 合并方式。

## 3. 怎样判断要不要拆成多个 Agent

多 Agent 只有在以下收益大于成本时成立：

- 独立搜索空间；
- 上下文隔离；
- 并行速度；
- 专业化；
- 权限隔离；
- 独立验证；
- 故障隔离。

协调成本包括：

- 信息损失；
- 重复工作；
- 术语漂移；
- 合并冲突；
- 调度和审查；
- 任务包构造；
- 下游依赖等待。

一个强 Agent 可以连续完成的闭环任务，不应为“体现多 Agent”而拆散。

## 4. 任务原子性的真实标准

原子不是任务足够小，而是：

- 有单一可验证交付物；
- 所需信息可以形成闭包；
- 写集边界清晰；
- 失败不会污染过大范围；
- 能独立提交或明确合并协议；
- 交付后下游可消费。

## 5. 依赖图

依赖必须是显式类型化边，而不是散文：

- 数据依赖；
- 接口依赖；
- 状态依赖；
- 资源冲突；
- 审批依赖；
- 验证依赖；
- 同一写集互斥；
- 迁移顺序。

计划冻结前检查循环、假依赖、遗漏依赖和跨计划冲突。

## 6. 执行环境

执行 Agent 应在隔离、可审计、可恢复的工作空间中运行：

- 独立 worktree 或沙箱；
- 明确分支和提交权限；
- 绑定 session/task/plan；
- 工具按需加载；
- 运行时心跳；
- 所有重要动作留 Trace；
- 产物可由其他会话接手；
- 会话死亡不等于工作丢失。

## 7. 执行合同

Agent 开始前确认：

- 任务包版本；
- 事实投影新鲜度；
- read/write set；
- 允许和禁止动作；
- 当前活跃冲突；
- 必须返回的产物；
- 完成验证；
- 回流条件。

执行中发现上游错误，不得盲目“尽力完成”。应创建 Finding 并选择正确回流。

## 8. 独立审查

自检不能只由编码会话完成。独立审查应至少隔离上下文，并根据风险选择不同证据路径、模型或工具。

审查视角包括：

- 需求和设计覆盖；
- 工程契约；
- 代码和架构；
- 安全；
- 测试；
- 运维；
- 性能；
- 迁移；
- 局部与全局一致性；
- 是否创造了未授权对象或能力；
- 是否真正进入运行路径。

## 9. Finding

Finding 是一等对象，不是 Reviewer 的一段评论。

至少包含：

- 现象；
- 严重度；
- 证据；
- 受影响对象；
- 可能原因；
- 竞争解释；
- 建议回流层；
- 临时缓解；
- 完成判据；
- 所有者；
- 生命周期。

## 10. 六类回流

### 10.1 Re-execute

环境、暂态依赖或一次性失败，原任务不变。

### 10.2 Repair

局部实现偏差，任务和工程方案不变。

### 10.3 Replan

任务拆分、顺序、资源或依赖错误。

### 10.4 Re-engineer

技术方案、接口、容量或工程假设失效。

### 10.5 Redesign

系统结构或机制无法满足需求，或产生不可接受副作用。

### 10.6 Re-interview

用户意图被误解、发生变化或出现新的价值冲突。

回流分类器必须提供证据；无法确定时优先调查，不得自动扩大返工范围。

## 11. 合并和提交

- 每个任务独立提交；
- 提交只包含声明写集；
- 检测夹带他人修改；
- 公共接口修改需要契约验证；
- 合并前重新检查目标分支变化；
- 局部测试通过不等于全局可合并；
- 合并后运行集成、回归和影响相关验证器；
- 失败可定位到任务、提交、Agent 和共识版本。

## 12. 计划与执行完成标准

- 所有任务到合法终态；
- 依赖和写集没有静默冲突；
- 所有承重 Finding 已解决、接受或转债；
- 产物已被消费或可被下游发现；
- 独立验证通过；
- 代码和运行状态一致；
- 未验证内容明确；
- 运行证据可以闭合原始目标。

# 07 · 证据、验证器、追溯与变更涟漪规范

## 1. 为什么验证器是 Harness 的核心

Agent 可以快速生成方案、代码和解释，但语言上的完整感很容易制造假完成。真正决定 Harness 强度的不是 Agent 数量，而是验证器能够可靠判断到哪里。

验证器的职责包括：

- 检查结构；
- 复算事实；
- 比较承诺和结果；
- 阻止非法状态变化；
- 发现漂移；
- 证明完成；
- 校准其他验证器。

## 2. 证据对象

证据至少记录：

- `evidence_id`；
- 来源类型；
- 采集时间；
- 适用版本；
- 生产者；
- 原始内容或不可变引用；
- 能证明什么；
- 不能证明什么；
- 新鲜度；
- 完整性；
- 可信等级；
- 与哪些主张关联；
- 是否存在相反证据。

## 3. 证据等级

从弱到强可以包括：

1. Agent 声明；
2. 文档声明；
3. 静态代码存在；
4. 注册与可达；
5. 单元测试；
6. 集成调用；
7. 真实运行记录；
8. 独立重算；
9. 对抗实验；
10. 长周期生产结果。

不同主张需要不同最低证据。例如“代码存在”不能证明“生产正在使用”。

## 4. 验证器分类

### 4.1 结构验证器

Schema、类型、引用、图完整性、状态机语法、目录和文件结构。

### 4.2 契约验证器

API、事件、数据、权限和跨模块协议。

### 4.3 行为验证器

给定输入和状态，系统是否产生正确输出和副作用。

### 4.4 质量验证器

性能、容量、可靠性、成本、安全、体验和可维护性。

### 4.5 语义验证器

需求覆盖、设计忠实、概念一致、任务是否偏离目标。

### 4.6 运行验证器

服务是否真实启用、事件是否被消费、结果是否到达用户。

### 4.7 治理验证器

权限、审批、Owner 判断、不可逆动作和例外使用是否合法。

### 4.8 验证器的验证器

通过独立重算、样本标注、故障注入和对照实验检查探针本身的漏报、误报与偏差。

## 5. 追溯图

建议建立完整链：

```text
原始表达
→ Problem
→ Requirement
→ Design Requirement
→ Design Object / Decision
→ Engineering Component / ADR
→ Consensus
→ Task
→ Commit / Artifact
→ Test
→ Deployment
→ Runtime Evidence
```

关系必须类型化：

- `derived_from`；
- `satisfies`；
- `implements`；
- `constrains`；
- `validates`；
- `depends_on`；
- `consumed_by`；
- `supersedes`；
- `conflicts_with`；
- `invalidates`；
- `observed_by`。

每条边包含创建者、理由、证据、置信度、版本和失效条件。

## 6. 影响分析

代码或共识改变后，不应让全部上游对象直接失效，而应进入怀疑和重验证：

```text
valid
→ suspect
→ revalidated
```

或：

```text
valid
→ suspect
→ invalid
→ redesign / re-engineer / replan
```

步骤：

1. 识别变更类型；
2. 找直接关联对象；
3. 沿允许的关系传播；
4. 计算受影响测试、接口、共识、设计和需求；
5. 运行低成本验证；
6. 只升级真实失败部分；
7. 保留传播路径和处理结果。

## 7. 防止变化风暴

- 限制传播关系和深度；
- 区分重构与行为改变；
- 缓存验证结果；
- 同一变化批量合并；
- 对低风险变化使用抽样和统计；
- 对高风险公共契约 fail-closed；
- 不让告警自动等同于返工。

## 8. 完成证明

一个完成声明至少回答：

- 做了什么真实改变；
- 对应哪个目标；
- 哪些代码、数据或配置变化；
- 在什么环境验证；
- 谁独立验证；
- 运行证据是什么；
- 哪些部分未验证；
- 是否产生新债；
- 后续观察窗口多长；
- 如何回滚。

## 9. Benchmark 的正确用法

Benchmark 不是单一分数，而是对机制的对照实验。

至少记录：

- 基线；
- 变量；
- 样本；
- 重复次数；
- 成功率；
- 质量；
- token 和时间；
- 人工介入；
- 返工；
- 方差；
- 失败类型；
- 长期副作用。

对 Harness 的关键评价包括：

- 问题发现率；
- 需求遗漏率；
- 设计返工率；
- 局部正确、合并错误率；
- 上下文有效利用率；
- 漂移发现延迟；
- 完成声明准确率；
- 同类故障复发率；
- 单位 token 的可验证价值。

## 10. 验证边界

存在指标不等于可以自动化裁决。价值、战略、伦理和权力判断仍需要人作为标准源头。Harness 可以提供事实、候选和后果推演，但不能用代理指标替代人的最终价值判断。

# 08 · 实时语义空间与上下文编译器设计

## 1. 核心命题

Agent 不应只在任务开始时拿到一份静态上下文。它每次阅读、修改、测试或审查一个对象时，所在的语义空间都发生变化。

因此上下文应当像增量编译结果，而不是固定 Prompt：

> 当前动作 + 当前对象 + 当前任务 + 当前世界状态 → 最小充分语义空间。

## 2. 为什么静态上下文不够

静态 `AGENTS.md`、`CLAUDE.md` 或项目说明存在四个问题：

- 太全：不相关信息稀释注意力；
- 太粗：只能定位到文档或模块，不能定位到字段和行为；
- 太旧：代码、共识和运行状态变化后不自动失效；
- 太早：任务开始时还不知道 Agent 后续会进入哪个对象。

实时语义空间应在动作发生时重新计算相关性。

## 3. 语义对象层

为了支持实时编译，以下对象需要成为一等实体：

- Repository；
- Module；
- File；
- Symbol；
- API；
- Data Entity；
- Event；
- Concept；
- Requirement；
- Design Decision；
- Engineering Decision；
- Consensus；
- Task；
- Test；
- Runtime Component；
- Finding；
- Owner；
- Governance Zone。

不能只依赖文件路径。文件只是语义对象的一种物理投影。

## 4. 关系层

需要支持：

- contains；
- defines；
- calls；
- reads；
- writes；
- implements；
- constrained_by；
- tested_by；
- consumed_by；
- owned_by；
- governed_by；
- changed_with；
- invalidated_by；
- historically_related；
- implicated_in_finding。

每条关系有方向、来源、版本、置信度和生命周期。

## 5. 编译触发器

### 5.1 Session Start

基于任务和计划编译初始胶囊。

### 5.2 Read

Agent 读取文件或 symbol 时，加载：

- 定义和所属概念；
- 上下游；
- 适用共识；
- 历史事故；
- 活跃 Finding；
- 相关测试；
- 代码治理区。

### 5.3 Edit

编辑前追加：

- 消费方；
- 契约；
- write set；
- 禁止改变的不变量；
- 必须运行的验证器；
- 影响分析预估。

### 5.4 Test

加载测试目标、相关需求、已知失败模式、环境约束和结果解释规则。

### 5.5 Review

加载需求、设计、工程方案、diff、相关契约和独立攻击清单，但不继承作者的全部推理惯性。

### 5.6 Deploy

加载真实环境、变更范围、迁移、回滚、审批、SLO 和运行观测。

## 6. 增量编译算法

```text
1. 接收动作事件
2. 解析目标实体
3. 计算与现有上下文的差量
4. 扩展类型化邻域
5. 拉取适用共识与证据
6. 检查版本和新鲜度
7. 计算信息价值、风险和 token 成本
8. 加入新相关内容
9. 降权或移除已不相关内容
10. 记录编译决策
11. 必要时触发 Agent 重新确认任务边界
```

## 7. 上下文不是纯文本

建议将上下文分成：

- 必须服从的规则；
- 已验证事实；
- 当前任务状态；
- 可按需读取的索引；
- 设计和工程理由；
- 风险和未知；
- 示例与判例；
- 工具和权限。

不同类型用不同格式和优先级，不把所有内容拼成一个长 Markdown。

## 8. 上下文预算

上下文选择可以表达为受约束优化：

```text
最大化：完成概率 + 风险覆盖 + 信息增益
最小化：token + 干扰 + 过期信息 + 重复
约束：关键红线不得遗漏，事实版本一致
```

需要记录：

- 注入了什么；
- 为什么注入；
- Agent 是否读取或使用；
- 是否帮助发现问题；
- 是否造成浪费；
- 后续结果如何。

## 9. 缓存和失效

缓存键不能只包含任务 ID。至少考虑：

- 目标对象 hash；
- 相关概念版本；
- 共识版本；
- 投影水位；
- 动作类型；
- 任务 read/write set；
- Agent 能力等级；
- 编译器合同版本。

任一承重输入变化时，相关缓存失效或进入 suspect。

## 10. “新法区、过渡区、旧法区”

每个代码区域应有治理标签：

- `current`：完全遵守最新规则；
- `transition`：允许有限兼容和迁移；
- `legacy`：默认保持现状，禁止顺带重构；
- `protected`：必须由特定所有者批准；
- `experimental`：规则和接口尚未稳定。

上下文编译器在 Agent 进入目录或 symbol 时自动加载该治理区的规则。

## 11. 与现有 Flowness Capsule 的关系

现有 Capsule 已具备概念邻域、obligation 作用域、任务 read/write set、投影新鲜度、缓存、known facts、must-not-do 和 token 截断等基础。

下一步不是重写 Capsule，而是：

- 将 File/Symbol/Governance Zone 纳入图；
- 将工具动作变成编译触发器；
- 把 Capsule 从一次性任务产物升级为 session 内的增量状态；
- 增加上下文使用和效果反馈；
- 将设计、工程方案和 Finding 纳入候选检索。

## 12. 风险

- 图关系错误导致错误上下文；
- 过度注入造成更严重干扰；
- 编译频率过高造成性能和成本问题；
- 语义裁决器不稳定；
- 旧代码关系难以自动恢复；
- Agent 可能不使用已注入信息；
- 实时变更造成上下文前后不一致。

因此先做 shadow：只生成建议胶囊和差量，不立即影响生产 Agent；通过历史回放和真实任务对比后逐步启用。

## 13. 第一版完成标准

选择一个真实模块，证明：

- Read/Edit 时能够发现相关概念、契约、测试和治理区；
- 公共接口修改前自动加载消费方；
- 共识变更后相关缓存失效；
- 与静态胶囊相比，遗漏减少且 token 成本可控；
- 编译决策可解释、可回放；
- 错误关系不会直接放行高风险操作。

# 09 · Agent 行为算法化与 Trace 治理

## 1. 核心命题

Agent 的真实能力不仅体现在最终文本或代码，也体现在它如何经过一系列动作达到结果。

Trace 使以下问题第一次可计算：

- Agent 在什么时候开始偏离；
- 哪些工具调用产生信息增益；
- 哪些动作是重复和浪费；
- 哪个上下文缺失导致错误；
- 哪种任务拆分导致协调成本过高；
- 哪个策略在什么场景下有效。

因此 Harness 应把 Agent 行为视为可以观察、评价、实验和改进的策略系统。

## 2. 不把“路径短”当成唯一目标

较长路径可能代表谨慎，较短路径可能代表漏查。建议评价：

```text
Trajectory Quality =
结果质量
+ 证据质量
+ 安全性
+ 信息增益
+ 可恢复性
- 成本
- 重复动作
- 无必要风险
- 协调损失
```

## 3. Trace 事件模型

至少记录：

- session、task、plan、Agent 和模型；
- 上下文编译版本；
- 观察、推理阶段和决定；
- 工具调用与结果；
- 文件和对象访问；
- 错误；
- 重试；
- 产生的 Artifact；
- Finding；
- 人工介入；
- token、时间和资源；
- 最终验证结果。

不是要求暴露模型私有思维，而是记录可观察行动、输入输出和正式判断。

## 4. 轨迹片段本体

建议识别可复用片段：

- orientation：定位仓库和任务；
- search：搜索信息；
- evidence-chain：验证定义到运行；
- hypothesis-test：提出并验证假设；
- edit-loop：编辑—测试—回读；
- recovery：错误恢复；
- escalation：升级；
- review-loop：审查和修复；
- context-refresh：上下文重编译；
- premature-action：未理解就动手；
- redundant-reread：重复读取；
- wrong-target：在错误对象工作；
- convergence-failure：无法收敛；
- false-completion：错误宣布完成。

## 5. 结果归因

看到失败轨迹后，不应直接说“Agent 不够聪明”。需要区分：

- 模型能力；
- 上下文缺失或过载；
- 工具不可用；
- 权限错误；
- 任务拆分；
- 计划依赖；
- 环境；
- 验证器误判；
- 方案本身错误；
- 随机波动。

一个结果可能由多个因素共同造成，归因应保留不确定性。

## 6. 策略对象

可优化的不是“模型人格”，而是 Harness Policy：

- 何时搜索；
- 搜索多深；
- 何时调用子 Agent；
- 何时升级模型；
- 何时重新编译上下文；
- 何时停止；
- 何时请求人类；
- 何时回流；
- 哪些测试先跑；
- 怎样控制并行和预算。

每个策略有版本、适用场景、假设、指标、风险和回滚。

## 7. 优化循环

```text
Trace 收集
→ 轨迹片段识别
→ 结果与证据评分
→ 问题归因
→ 策略候选
→ 历史回放
→ Shadow 对照
→ 小流量启用
→ 独立验证
→ 晋升 / 回滚 / 保持实验
```

## 8. 反事实与实验

理想情况是在相同或相近任务上比较：

- 不同上下文；
- 不同模型；
- 单 Agent 与多 Agent；
- 不同任务分片；
- 不同工具顺序；
- 不同停止规则。

无法重复真实任务时，可以用历史回放、变体任务和合成故障，但必须说明外部效度限制。

## 9. 防止指标投机

Agent 或调度器可能通过压缩动作数、减少搜索、避免报告问题来让指标更好看。

因此：

- 效率指标必须和结果质量、证据质量绑定；
- 不使用单一分数；
- 监测未报告错误和后续返工；
- 定期人工抽样；
- 使用 verify-the-observer；
- 规则晋升前检查是否改变行为而非只改变记录方式。

## 10. 与 R07 的关系

R07 已经证明了这条路线的可行性：从 transcript 中计算错误率、探路长度、回读浪费和指代纠正等指标，建立越界检测与独立观测校准。

下一阶段应从“几个总体指标”升级为：

- 标准 Trace Schema；
- 轨迹片段识别；
- 上下文和策略版本绑定；
- 失败归因；
- 策略实验；
- 对照和晋升机制。

## 11. 第一版完成标准

选择三类重复任务：修 Bug、跨文件小功能、复杂调查。证明：

- 能稳定识别主要轨迹片段；
- 能区分至少三类失败来源；
- 一个策略改进在对照中改善质量或成本；
- 改进未显著增加漏检和风险；
- 结果可以回放和解释；
- 策略可以快速回滚。

# 10 · Flowness 现状映射与升级路线

## 1. 已验证的现有骨架

基于仓库代码和规范，Flowness 已经不是空白框架。已经存在：

- append-only 事件事实源；
- provenance 和事件分类；
- commit gate；
- 投影和快照；
- concept graph；
- obligation；
- Capsule Assembly Pipeline；
- Interview、Engineering Consensus、Planning、Execution、Review、Fix 等 Skill；
- Task DAG、read/write set、任务包和冻结；
- Finding、审查、修复和闭合；
- worktree 隔离；
- orchestrator、会话生命力和收割；
- invalidation cascade 的库层；
- R07 transcript 观测、越界检测和 verify-observer；
- Investigation 与 Cognitive Resolution 方法。

## 2. 当前最关键的结构缺口

正式建造管线仍大致是：

```text
Interview
→ Engineering Consensus
→ Planning
→ Execution
→ Review / Fix
```

Engineering Consensus 被迫同时承担：

- 设计系统应当长什么样；
- 决定技术如何实现；
- 冻结执行者共同前提。

这导致设计、工程方案和共识三类判断混合。

另一个缺口是 Investigation 虽已形成高质量方法，但仍主要作为调查型任务入口，没有正式成为“问题不清晰的新项目”进入建造管线前的 Problem IR 阶段。

## 3. 这次升级的目标

只补齐一条最小但真实的中间走廊：

```text
Investigation / Interview
→ Problem IR
→ Design IR
→ Engineering IR
→ Engineering Consensus
→ Planning
```

不重写现有 EventLog、ConceptGraph、Capsule、Planning、Execution、Review、Fix 和 Orchestrator。

## 4. 新增对象

第一版只新增必要对象：

### 4.1 Problem

现象、事实、假设、竞争解释、范围和证据。

### 4.2 Requirement

目标、约束、质量场景、反目标、授权和确认。

### 4.3 Design Alternative

候选机制及其适用条件、代价和失败模式。

### 4.4 Design Decision

选择、理由、权衡、假设、证伪条件。

### 4.5 Design Object

主体、对象、关系、状态、行为、权限和机制。

### 4.6 Engineering Decision

技术候选、证据、选择、迁移和重开条件。

### 4.7 Engineering Component / Contract

工程组件、接口、数据、SLO、测试和运维。

## 5. 与现有对象的关系

- Problem / Requirement 来源于 InterviewBrief 和 Investigation Workspace；
- Design Object 可以落入或引用 ConceptGraph，但不能把所有设计草案直接冻结为共识；
- Engineering Component 映射到代码、接口、数据和运行组件；
- Engineering Consensus 只从 accepted Engineering IR 中提取稳定共同前提；
- Planning 继续从 frozen consensus 编译 Task DAG；
- Capsule 增加 Design/Engineering trace；
- Finding 增加建议回流层。

## 6. 新阶段状态

### 6.1 Problem

```text
draft → investigated → accepted → changed / superseded
```

### 6.2 Design

```text
exploring → compared → selected → attacked → accepted → challenged / superseded
```

### 6.3 Engineering

```text
researching → prototyped → reviewed → accepted → migrating → active → deprecated
```

状态语义应通过正式 Schema 和事件定义，不只存在于文档。

## 7. 最小验证器

第一版不追求一百个验证器，只做承重门：

1. Problem Evidence Gate：重要问题有证据与竞争解释；
2. Requirement Coverage Gate：目标、约束、反目标和成功场景完整；
3. Design Coverage Gate：高优需求有设计响应；
4. Alternative Gate：承重机制不允许无候选直接拍板；
5. Design Consistency Gate：对象、状态、权限和场景无明显冲突；
6. Engineering Mapping Gate：设计对象有工程映射；
7. Decision Evidence Gate：承重技术决定有证据和重开条件；
8. Consensus Extraction Gate：只有 accepted Engineering IR 可冻结为共识；
9. Traceability Gate：从 Requirement 到 Task 可追溯。

## 8. 实施方式

### 阶段 A：文档和 Schema

先定义对象、事件和状态，不修改生产自动路由。

### 阶段 B：手动流程 dogfood

由主会话手动走 Problem、Design、Engineering，再调用现有 Consensus 和 Planning。

### 阶段 C：只读投影与 Capsule 接线

让后续 Agent 看见新对象，但不自动触发状态变化。

### 阶段 D：验证器和阶段门

先 warning，再 fail-closed。

### 阶段 E：Orchestrator 自动接棒

仅在真实项目证明稳定后启用自动路由。

## 9. Dogfood 项目选择

不要用 Flowness 全盘自重构作为第一案。选择：

- 有真实用户价值；
- 足够复杂，需要设计和工程方案；
- 影响边界可控；
- 可以构建和测试；
- 一到两周可形成结果；
- 能与旧管线做对照。

例如为现有 Harness 增加一个独立可观察的新模块，而不是重写 EventLog 或 Orchestrator。

## 10. 成功判据

- 旧管线中会在执行阶段暴露的问题，新管线更早发现；
- 执行 Agent 不再重新决定产品结构和公共接口；
- Design 到 Engineering 到 Consensus 的转换没有静默丢失；
- Finding 能准确回到不同层级；
- 文档和对象的新增成本没有压垮任务；
- 总返工、人工介入或假完成下降；
- 新管线可被冻结并用于下一项目。

## 11. 明确不做

本轮不做：

- 通用企业改革平台；
- 所有行业本体；
- 完整实时语义编译器；
- 自动训练 Agent；
- 全自动治理和自修复；
- 百万行陌生代码库自主重构；
- 重做现有 L0/L2 地基；
- 新的大型可视化控制台。

这些进入 Evolution Backlog，不得阻塞当前闭环。

# 11 · 实施边界、版本治理与生产/演进双轨

## 1. 最大风险：Harness 永远在升级

复杂系统永远可以更完整。只要把“还有问题”当成“不能冻结”，Harness 就会长期处于自我施工状态：

- 生产任务等待底座；
- 新机制不断改变旧假设；
- 团队无法形成稳定习惯；
- 客户项目成为基础设施试验田；
- 每一次失败都触发全局重构；
- 真实价值迟迟无法证明。

所以 Harness 必须拥有停止机制。

## 2. 生产轨和演进轨

### 2.1 Production Track

- 使用已冻结版本；
- 负责真实交付；
- 只接受兼容修复和明确版本升级；
- 有 SLO、支持范围和回滚；
- 不因为研究发现立刻改变生产协议。

### 2.2 Evolution Track

- 研究新本体、编译器、策略和验证器；
- 允许失败；
- 使用 shadow、历史回放和 dogfood；
- 所有实验有基线和证伪条件；
- 达到晋升门后才进入生产。

## 3. 机制晋升流程

```text
idea
→ research
→ prototype
→ replay
→ shadow
→ dogfood
→ limited production
→ active
→ monitored
```

任何阶段均可回到 rejected、rework 或 archived。

## 4. 晋升证据

- 它解决的故障真实存在；
- 基线已测；
- 新机制比当前方案明显改善；
- 引入的复杂度和成本可接受；
- 有失败和回滚路径；
- 不破坏核心不变量；
- 有负责人和维护方式；
- 对使用者的认知成本可承受；
- 文档、代码、验证器和运行路径一致。

## 5. 版本范围

一个版本必须写清：

- 要解决的问题；
- 目标用户和场景；
- 新增对象和协议；
- 修改的既有不变量；
- 兼容性；
- 迁移；
- 不做事项；
- 验收；
- 观察窗口；
- 退役条件。

## 6. “新法、过渡、旧法”治理

系统升级不应假设所有存量立即迁移。

### 新法区

新代码和已完成迁移的模块，必须遵守当前规则。

### 过渡区

同时承载新旧接口，有明确迁移任务和截止条件。

### 旧法区

稳定但未计划改造的遗留系统。默认禁止顺带重构，只做必要兼容或故障修复。

### 保护区

高风险核心模块，需要特定 Owner、专家评审和发布窗口。

### 实验区

允许快速试验，但不得被下游当作稳定公共契约。

## 7. 变更预算

每次升级应设：

- 可新增对象数量；
- 可新增事件类型；
- 可新增 Gate；
- 可改变的公共接口；
- 允许迁移的数据量；
- 最大 blast radius；
- 时间和 token 预算；
- Owner 关注预算。

超出预算必须显式重开版本范围，不得通过“顺手补齐”扩大。

## 8. 停止条件

本轮完成后，即使发现更多问题，也应冻结，只要：

- 当前目标已被独立验证；
- 主要风险在接受范围内；
- 新问题不阻塞当前用户价值；
- 未解决项已登记并可追溯；
- 生产回滚和运维成立；
- 继续优化的边际收益低于延迟交付成本。

## 9. 何时必须暂停升级

- 没有真实项目在使用；
- 验证器长期没有数据；
- 新文档和对象增加快于旧债关闭；
- 同一层不断被重新命名而行为不变；
- 生产问题主要来自基础接线和运维，而非理论缺位；
- Owner 成为所有微观决定的唯一瓶颈；
- 系统无法用自身机制完成一个受控项目。

## 10. 何时需要独立工程负责人

当系统开始承诺：

- 企业级 SLA；
- 多租户；
- 高并发；
- 生产数据；
- 复杂迁移；
- 百万行代码库；
- 安全和合规；
- 长期运维；

必须有 Principal/Staff 级工程负责人对工程真实性承担责任。Owner 可以继续掌握产品、机制和最终价值定义，但不应同时作为唯一 SRE、安全负责人和运行时架构裁决者。

# 12 · 跨领域扩展与企业改革边界

## 1. 通用性的正确理解

Flowness 的潜力不只在软件开发，但“任何可讨论的东西都可以自动化”是不成立的。

一个领域适合进入 Harness，至少需要：

- 对象可以表示；
- 过程可以留下证据；
- 结果可以接受反馈；
- 标准来源明确；
- 权限和责任可以定义；
- 失败可以被发现或限制；
- 关键行动可回滚或由人批准。

## 2. 三类可验证性

### 2.1 机械强验证

编译、类型、数学、格式、契约、数据一致性和确定性规则。适合高度自动化。

### 2.2 行为与结果验证

用户任务、业务指标、流程效率、服务质量。需要真实运行、实验和延迟反馈。

### 2.3 价值与治理判断

战略、伦理、组织结构、风险偏好和利益分配。系统可以辅助，但标准和最终授权必须来自人。

## 3. 跨领域扩展不是替换名词

从软件扩展到研究、法律、运营或组织改革，需要重新定义：

- 领域主体；
- 对象；
- 证据；
- 生命周期；
- 权限；
- 失败；
- 验证器；
- 反馈周期；
- 可逆性；
- 专家责任。

通用内核可以复用身份、事件、追溯、任务、证据、审批和回流，但领域本体不能自动从软件术语投影。

## 4. 企业改革的可承载部分

Harness 可以帮助企业：

- 把隐性流程对象化；
- 识别职责和信息断层；
- 建立决策与执行追溯；
- 把专家判断沉淀为规则、判例和验证器；
- 管理多 Agent 和人的共同工作；
- 发现流程瓶颈和重复劳动；
- 建立实验和持续改进；
- 将高风险决定保留给人。

## 5. 不能承诺的部分

- 自动决定企业战略；
- 用指标替代价值判断；
- 在没有领域专家时创造可靠标准；
- 自动解决组织政治和利益冲突；
- 对长期社会结果作确定保证；
- 仅凭讨论生成可执行且正确的改革方案；
- 用 Agent 数量替代责任主体。

## 6. 推荐扩展顺序

1. 软件工程；
2. 技术研究和尽调；
3. 有明确规则的运营流程；
4. 合规和审计辅助；
5. 项目管理和组织协作；
6. 战略和企业改革辅助。

越往后，自动执行越少，人的标准源头和审批越重要。

## 7. 企业落地产品形态

不应一开始销售“组织操作系统”。更可信的产品是：

- 大型代码库调查与迁移控制平面；
- AI 原生研发交付系统；
- 复杂项目的设计—工程—执行工作台；
- 专家知识对象化与 Agent 执行平台；
- 具备证据、审批和回流的数字员工治理系统。

这些真实场景积累的对象、失败和验证器，才可能逐步支持更大的企业改革。

# 13 · 阿里云端到端交付 2.0 对照研究

## 1. 总体判断

阿里云文章呈现的是一套经过真实组织实践的 AI Coding 工业化交付体系。它在范围控制、组织落地、渐进迁移、任务分级、平台化执行和数据驱动优化方面明显成熟。

Flowness 在事件事实源、概念与共识、字段级追溯、上下文编译、失效传播和验证器自校准方面更深。

两者不是简单高低关系：

- 阿里体系更像成熟生产线；
- Flowness 更像生产线的语义内核、法律和控制系统。

## 2. 共同问题

双方都发现：

- 模型速度超过人工质检；
- 信息在阶段传递中衰减；
- 复杂任务上下文丢失；
- 顶级模型昂贵、脆弱和不可控；
- 本地个人会话不能支撑组织生产；
- Session 和 Trace 没有形成持续改进；
- 设计和技术方案不足；
- 多 Agent 需要最小权限和独立审查；
- 领域知识和历史经验必须进入可加载物料。

## 3. 不同解法

### 3.1 阿里：标准化物料

- `spec.md`；
- `plan.md`；
- `tasks.md`；
- `check_reports`；
- `session log`；
- App-Adr；
- App-Desc；
- App-Research；
- 一个需求 ID 串联全链路。

优点是部署快、易理解、适合大规模组织采用。

### 3.2 Flowness：机器语义对象

- EventLog；
- ConceptGraph；
- Obligation；
- typed reference；
- Task DAG；
- read/write set；
- Capsule；
- Finding 和生命周期；
- invalidation cascade。

优点是长期可演化、可精确影响分析、可由系统强制执行。

## 4. 最值得吸收的实践

### 4.1 生产和升级双轨

旧体系继续交付，新规范平行建设；新体系热车和验证后再切换。Flowness 应正式产品化 Production/Evolution 双轨。

### 4.2 工作项分级

标准需求、简单需求、一般任务使用不同强度流程。Flowness 不应让所有正式工作走同样完整生命周期。

### 4.3 新法区、过渡区、旧法区

将规则适用范围直接绑定代码区域，禁止 Agent 用新规范顺带重构历史系统。

### 4.4 本地和平台双执行

本地用于调试，平台用于权威执行、审计、统计和合规。

### 4.5 独立自检

Reviewer 使用独立会话和工作区，并从产品、研发、安全和 SRE 等视角检查。

### 4.6 改进必须有对照证据

例如模板增加枚举定义后，对话轮次在后续需求中下降。Flowness 的规则和 Skill 晋升也应要求基线、样本和效果。

### 4.7 专家依赖被产品化而非消灭

产品和运营可以提需求，但架构师、研发负责人和领域专家仍定义规则、评审灰区和最终交付。Flowness 不需要假装可以服务完全无标准的人，而应先把专家能力规模化。

## 5. 不应直接照搬的部分

### 5.1 粗粒度 ID 追溯

需求 ID 可以归档，却不足以表达字段、设计决定、接口和测试之间的语义关系。

### 5.2 Markdown 作为主要事实源

文档适合作为交付接口，但容易漂移。Flowness 应保留事件与图作为事实源，Markdown 作为可进入视图。

### 5.3 传统角色直接映射 Agent

产品、开发、测试角色清晰实用，但 Flowness 应允许基于上下文和任务动态形成职能，不把角色名称当成本体。

### 5.4 Session 统计等同因果优化

对话轮次和 token 只是信号，需要验证质量、任务复杂度和环境影响，避免优化出“少查、少报、快结束”。

## 6. 对 Flowness 的直接行动

- 新增任务分级路由；
- 设计治理区标签；
- 将本地/云端/权威执行变成正式对象；
- 要求 Skill 与规则升级提供对照数据；
- 建应用级轻量导出包，降低概念图对普通团队的进入成本；
- 保留深语义内核，不让企业落地必须直接理解全部底层对象；
- 先以软件交付为边界证明价值，再扩展到企业改革。

# 14 · 术语表与对象目录

## 1. 核心对象

| 对象 | 定义 | 不是什么 |
|---|---|---|
| Commission | 一次工作委托、权力和范围的建立 | 普通聊天请求 |
| Problem | 经调查形成的可证据化问题对象 | 用户一句抱怨 |
| Requirement | 被确认的目标、约束或质量要求 | 解决方案 |
| Design Alternative | 核心机制不同的候选设计 | 同方案换包装 |
| Design Decision | 对候选的正式选择和权衡 | 会议结论摘要 |
| Design Object | 设计世界中的主体、对象、关系、状态和机制 | 代码类的简单别名 |
| Engineering Decision | 技术实现选择及其证据、假设和迁移 | 技术偏好 |
| Engineering Component | 真实工程组件和运行边界 | 产品功能列表 |
| Consensus | 跨任务稳定、必须共同遵守的事实与约束 | 整份工程方案 |
| Plan | 从 Engineering IR 编译出的任务图 | 待办列表 |
| Task | 有认知闭包、明确写集和验证合同的执行单元 | 一个动作描述 |
| Capsule | 针对当前任务和动作编译的最小充分上下文 | 固定 Prompt |
| Evidence | 能支持或反驳主张的可追溯材料 | Agent 的自我陈述 |
| Validator | 对对象、状态或结果进行独立判定的机制 | 提示词提醒 |
| Finding | 可追踪的偏差、风险或缺口对象 | Review 评论段落 |
| Trace | Agent 可观察行动和正式决定的事件序列 | 私有思维过程 |
| Policy | 可版本化、可实验的行为和调度策略 | 一次性提示词 |
| Reflow | 问题返回正确认知层级的机制 | 一律重新执行 |

## 2. 主要关系

| 关系 | 含义 |
|---|---|
| derived_from | 从某对象推导 |
| satisfies | 满足需求或条件 |
| implements | 工程实现设计 |
| constrains | 对对象施加约束 |
| validates | 验证某主张或对象 |
| depends_on | 生命周期或结果依赖 |
| consumes | 消费接口、数据或产物 |
| owned_by | 责任和修改权归属 |
| governed_by | 适用规则和治理区 |
| supersedes | 新版本替代旧版本 |
| conflicts_with | 同时成立会冲突 |
| invalidates | 使旧判断失效 |
| observed_by | 被观测机制监控 |
| implicated_in | 与 Finding 或事故相关 |

## 3. 回流术语

| 类型 | 适用情况 |
|---|---|
| Re-execute | 暂态、环境或一次性失败 |
| Repair | 局部实现偏差 |
| Replan | 任务和依赖错误 |
| Re-engineer | 技术方案或工程假设错误 |
| Redesign | 系统结构和机制错误 |
| Re-interview | 意图、价值或范围错误 |

## 4. 状态语义通则

- `draft`：尚未进入正式评审；
- `proposed`：已提出但未接受；
- `accepted`：可作为下游输入；
- `active`：当前生效；
- `challenged`：被证据或 Finding 质疑；
- `suspect`：变化后待重验证；
- `superseded`：由新版本替代；
- `deprecated`：仍兼容但不应新增使用；
- `retired`：正式退出运行；
- `archived`：保留历史，不参与当前决策。

具体领域对象可以有自己的状态，但必须映射到可治理的通用生命周期。

# Flowness 认知编译层建设路线

## 北极星

用一个真实、非平凡软件子系统证明：

```text
模糊意图
→ Problem
→ Design
→ Engineering
→ Consensus
→ Plan
→ Execution
→ Independent Validation
→ Evidence Closure
```

整个过程比旧管线更早发现关键错误，减少执行阶段返工，并且没有因文档和流程复杂度显著拖慢交付。

## Phase 0 · 冻结范围

- 接受本知识包为研究基线；
- 选定一个 dogfood 项目；
- 冻结“不做清单”；
- 建基线指标；
- 指定 Owner 与工程负责人。

## Phase 1 · 对象与 Schema

- Problem IR；
- Requirement IR；
- Design IR；
- Engineering IR；
- Decision 和 Evidence；
- Reflow 分类；
- 与现有 Concept/Event/Task 的映射。

产出：Schema、示例、状态机、迁移说明。

## Phase 2 · 手动流程

- 使用现有 Investigation 和 Interview；
- 手动产出 Problem、Design、Engineering；
- 人工触发现有 Engineering Consensus；
- 不改 Orchestrator 自动接棒。

目标：验证阶段边界和产物是否真的能被下游消费。

## Phase 3 · 最小验证器

- Problem Evidence；
- Requirement Coverage；
- Design Alternative；
- Design Consistency；
- Engineering Mapping；
- Decision Evidence；
- Consensus Extraction；
- Traceability。

先 warning，收集误报和漏报，再选择承重门 fail-closed。

## Phase 4 · Capsule 接线

- 注入 accepted Design/Engineering 决定；
- 记录上下文来源；
- 运行静态与动态胶囊对照；
- 检查 token、遗漏和行为效果。

## Phase 5 · 自动接棒

- 新事件和状态进入 Orchestrator；
- 每段支持暂停、人工审批和重入；
- 出错能回到正确层级；
- 避免旧项目被强制迁移。

## Phase 6 · 生产试点

- 小流量；
- 完整审计；
- 观察真实返工、质量和成本；
- 与旧管线对照；
- 达到晋升门后冻结 v1。

## Evolution Backlog

- 实时文件/Symbol 语义空间；
- Trace 片段和策略优化；
- 跨项目知识；
- 大型遗留代码迁移；
- 多领域本体；
- 企业级控制台；
- 更强自动治理。

# 附录 A · 阶段合同与验收模板

## 1. 通用阶段合同

```yaml
stage_id: design-001
stage_type: design
upstream_inputs:
  required:
    - accepted_problem_ir
    - confirmed_requirements
  optional:
    - external_research
    - historical_cases

responsibility:
  owns:
    - design_alternatives
    - design_objects
    - design_decisions
  must_not_own:
    - production_deployment
    - unapproved_value_decisions

required_outputs:
  - requirement_design_trace
  - alternatives_comparison
  - selected_design
  - quality_scenarios
  - risks_and_open_questions

completion_checks:
  mechanical:
    - schema_valid
    - references_resolve
  semantic:
    - critical_requirements_covered
    - alternatives_genuinely_different
    - failure_scenarios_closed

reflow_routes:
  missing_fact: investigation
  value_conflict: interview
  infeasible_design: redesign

authority:
  proposer: design_agent
  evaluator: independent_reviewer
  final_approval: owner_or_delegated_authority
```

## 2. Problem 阶段合同

### 输入

- 原始请求、事故、症状或问题描述；
- 当前系统材料；
- 可访问的代码、数据、日志、账本和人；
- 调查范围和时间约束。

### 必须做

- 建调查地图；
- 维护覆盖表；
- 区分事实、推断、假设、未知和建议；
- 记录竞争解释和反例；
- 追高信息量端到端路径；
- 形成可供采访或设计使用的问题模型。

### 不得做

- 第一轮就宣布唯一根因；
- 以文档或搜索命中代替真实调用路径；
- 只调查用户点名的名词；
- 在证据不足时冻结方案。

### 完成判据

- 关键问题达到可设计、可实现、可验证、可追责的分辨率；
- 覆盖和未知明确；
- 重要主张有证据或被明确标记；
- 下一阶段知道它能使用哪些事实、哪些仍是假设。

## 3. Interview 阶段合同

### 输入

- Problem IR 或相对清楚的原始意图；
- 用户历史判断；
- 外部成熟实践；
- 初步场景和草样。

### 必须做

- 给出主动推测；
- 用场景和具体草样帮助用户判断；
- 先自答可由事实和行业知识回答的问题；
- 问清价值冲突、风险偏好和不可逆边界；
- 让用户确认最终理解。

### 完成判据

- 用户不需要在后续被反复问同一层问题；
- 关键隐性需求和反目标被发现；
- 高风险决策归属清楚；
- Requirement IR 可直接进入设计。

## 4. Design 阶段合同

### 输入

- accepted Problem IR；
- confirmed Requirement IR；
- 约束和质量场景。

### 必须做

- 建对象、关系、机制、状态和权限；
- 提出真正不同的候选；
- 推演正常、异常、对抗和演化场景；
- 记录设计决定和证伪条件；
- 独立审查需求覆盖和内部一致性。

### 完成判据

- 工程团队无需重新定义系统应该长什么样；
- 重要机制有候选比较；
- 关键失败和权限边界明确；
- 工程自由度和不可改写事实清楚。

## 5. Engineering 阶段合同

### 输入

- accepted Design IR；
- 技术环境、存量系统、预算和运维约束。

### 必须做

- 建工程边界、组件、接口、数据和状态；
- 处理并发、错误、恢复、安全、容量和运维；
- 对关键选择做源码、原型、Benchmark 或生产证据；
- 定义迁移、回滚和可观测性；
- 形成可提取共识、可编译计划的 Engineering IR。

### 完成判据

- 设计对象均有工程映射；
- 承重决定有证据；
- 风险可测试；
- 可发布、可回滚、可维护；
- 下游无需重做架构。

## 6. Consensus 阶段合同

### 必须做

- 只从 accepted Engineering IR 提取；
- 明确作用域、版本、消费方和验证器；
- 分批冻结；
- 支持 supersede、迁移和失效传播。

### 完成判据

- 新执行者可以独立工作；
- 不同任务不会实现互不兼容的共同对象；
- 修改公共定义时能找到受影响消费方。

## 7. Planning 阶段合同

### 必须做

- 任务以交付物为中心；
- read/write set、依赖和资源显式；
- 每个任务形成认知闭包；
- 关键路径和并行组可计算；
- 计划冻结前通过完整性检查。

## 8. Execution / Review / Closure 合同

### Execution

只在声明边界内产生真实改变；发现上游错误时创建 Finding 和回流，不静默改写。

### Review

独立检查需求、设计、工程、代码、运行与证据；结论有证据，阻塞项不可被汇报语言软化。

### Closure

完成必须由实际运行、消费或独立验证证明；未验证项显式存在；所有承重 Finding 到合法终态。

# 附录 B · 设计评审攻击手册

## 1. 使用方法

本手册用于主动证明设计不成立。评审者不应只问“有没有覆盖清单”，而应构造足以暴露机制漏洞的场景。

每次攻击记录：

- 被攻击设计决定；
- 场景与前置条件；
- 预期失败；
- 实际推演；
- 证据；
- 是否阻塞；
- 修复后如何复验。

## 2. 需求忠实度攻击

- 方案解决的是用户的目标，还是用户随口提出的手段？
- 有没有高优需求没有任何设计响应？
- 有没有设计对象找不到服务目标？
- 隐性需求是否只是 Agent 自己发明？
- 如果去掉所有术语，用户是否仍会认可结果？

## 3. 机制攻击

- 功能存在，但稳定产生功能的机制是什么？
- 用户或 Agent 能否绕开关键机制？
- 机制依赖的假设在真实环境成立吗？
- 两个机制同时运行会不会互相抵消？
- 如果主要 Agent 失效，制度是否仍成立？

## 4. 对象攻击

- 对象是否有稳定身份？
- 同名对象是否被混成一类？
- 谁创建、拥有、修改、消费、废弃？
- 重复、孤立、过期、部分创建怎样表达？
- 对象存在于文档、数据库、代码还是运行时？这些投影如何一致？

## 5. 关系攻击

- 连线是否说明方向、条件、强度、版本和失败影响？
- 关系是声明还是可由代码和数据重建？
- 上游变化后，下游如何知道？
- 消费方清单会不会过期？
- 是否存在一对多、多对多、循环或隐藏依赖？

## 6. 生命周期攻击

- 初始态和终态是什么？
- 中途失败留下什么？
- 重试是否产生重复副作用？
- 取消、暂停、恢复、迁移和废弃如何发生？
- 同时收到两个相反事件怎样处理？
- 历史状态如何回放？

## 7. 权限攻击

- 谁能改变公共定义？
- Agent 能否通过间接工具绕权？
- 审批是否只是提示词而非机械边界？
- 紧急绕过如何记录和补偿？
- 身份借用是否造成不可追责？
- 人类延迟回应时系统怎么维持安全？

## 8. 信息攻击

- Agent 是否看到必要信息？
- 是否因为信息太多忽略红线？
- 信息是否过期、冲突或来源不明？
- 上下文截断时先丢什么？
- 不同 Agent 是否收到不同版本事实？
- 系统能否说明为什么加载某条规则？

## 9. 质量属性攻击

### 性能

负载、并发、峰值、冷启动、慢依赖和资源耗尽时怎样？

### 可靠性

进程、网络、模型、队列、数据库或外部 API 失败时怎样？

### 可维护性

一年后新工程师能否理解？规则、事件和 Gate 数量是否失控？

### 安全

数据越权、Prompt Injection、密钥、供应链和工具滥用如何处理？

### 成本

正常、异常和最坏情况下 token、模型、存储和人工成本是多少？

## 10. 演化攻击

- 模型、框架、技术栈或组织变化后还能运行吗？
- 版本升级是否需要一次性大迁移？
- 旧任务如何回放？
- 新规则会不会错误审判旧代码？
- 一个临时例外会不会变成永久债？

## 11. 组织现实攻击

- 谁愿意维护这些物料？
- 谁对错误负责？
- 团队能否理解和遵守？
- 流程成本会不会让人绕过？
- 审批人是否成为瓶颈？
- 指标是否制造错误激励？

## 12. 最小性攻击

- 不做会怎样？
- 只加观测是否够？
- 能否用更简单机制达到 80% 效果？
- 新对象、Agent、Gate 和数据库是否都有不可替代价值？
- 方案是不是为了追求完备而制造长期复杂度？

# 附录 C · 工程方案审查清单

## 1. 架构边界

- 系统内外边界明确；
- 外部依赖有失败和替换策略；
- 组件职责单一且所有权明确；
- 跨层调用受控；
- 公共接口数量和演化方式合理；
- 不把外部框架状态当作内部事实源。

## 2. 数据与一致性

- 实体、值对象和聚合边界清楚；
- 唯一性和幂等有机制；
- 事务边界符合真实业务；
- 强一致和最终一致选择有理由；
- 重复、乱序、延迟和丢失可处理；
- schema 演化、迁移、归档和恢复明确；
- 数据删除和隐私符合治理要求。

## 3. 并发和分布式行为

- 锁、租约、乐观并发和所有权选择有证据；
- 并发修改公共对象时冲突可检测；
- 重试不会重复副作用；
- 超时、背压、熔断和退避明确；
- 任务死亡和接手不会产生双写；
- 分区、网络抖动和时钟问题被考虑；
- 长事务和全局锁不会成为瓶颈。

## 4. Agent 运行时

- Agent 身份、会话、任务、工作区和产物绑定；
- 模型可替换；
- 工具按需发现；
- 权限最小化；
- 上下文有版本、新鲜度和来源；
- 会话中断可恢复；
- 结果不依赖私有聊天历史；
- 低置信判断不会跨越高风险边界。

## 5. API 和契约

- 输入输出类型完整；
- 字段单位、范围、默认值明确；
- 错误码和部分成功明确；
- 版本和兼容期明确；
- 消费方已知；
- 限流、超时、重试和幂等明确；
- 契约测试和弃用路径存在。

## 6. 安全

- 身份和授权独立；
- Agent 借用人类身份的边界明确；
- 高风险操作有 Owner Gate；
- 沙箱和网络限制有效；
- 密钥不进入上下文和日志；
- 外部内容视为不可信输入；
- 审计日志防篡改；
- 供应链和依赖风险可扫描。

## 7. 测试

- 单元测试覆盖核心纯逻辑；
- 契约测试覆盖模块边界；
- 集成测试覆盖真实调用；
- 状态机和属性测试覆盖组合空间；
- 并发和故障注入覆盖危险路径；
- 回放测试验证历史兼容；
- 迁移和回滚被演练；
- 测试失败可定位到设计、工程或实现层。

## 8. 可观测性

- Trace、metric、log 能关联到 task/session/decision；
- 指标定义有单位、口径和数据源；
- 能区分声明完成和真实完成；
- 有关键路径和队列延迟；
- 观测器有校准；
- 告警有行动路径，避免纯噪音；
- 当前状态可以从事实重建。

## 9. 发布和运维

- 本地、测试、shadow、灰度和生产区分；
- 配置、代码、数据迁移顺序明确；
- daemon 或长进程升级后会真正加载新代码；
- 回滚不会破坏数据；
- SLO、容量和成本可观测；
- Owner、值班和事故响应明确；
- 长期依赖更新和技术债有计划。

## 10. 复杂度

- 新组件数量合理；
- 没有相同能力多套实现；
- 临时脚本不会成为隐形生产路径；
- 文档、Schema 和代码不重复维护同一事实；
- 关键路径足够简单；
- 引入框架的抽象与自身本体隔离；
- 未来退出或替换成本可接受。

# 附录 D · 百万行代码重构资格审查

## 1. 基本判断

“能否重构几百万行代码”不是一个是非题。需要先判断目标、代码库可理解性、验证能力、迁移方式和组织条件。

Harness 可以管理超大型重构，但不能承诺把陌生仓库交给 Agent 后全自动完成。

## 2. 项目准入信息

### 业务

- 为什么要重构；
- 不重构的成本；
- 允许的停机和风险；
- 哪些业务行为绝不能改变；
- 谁拥有最终验收权。

### 代码库

- 语言和构建系统；
- 仓库、服务和模块数量；
- 活跃与废弃代码；
- 所有权；
- 依赖图可恢复程度；
- 生成代码和第三方代码；
- 代码版本治理区。

### 验证

- 能否完整构建；
- CI 时间和稳定性；
- 单元、集成和端到端覆盖；
- 是否有 characterization tests；
- 是否有生产流量回放；
- 数据一致性如何验证；
- 关键性能基线。

### 运行

- 部署拓扑；
- 数据库和消息；
- 发布频率；
- 灰度、双写和回滚；
- 可观测性；
- 事故历史。

### 组织

- 架构负责人；
- 模块 Owner；
- 评审与发布权限；
- 业务专家；
- 迁移时间窗口；
- 并行业务需求。

## 3. 拒绝或降级条件

出现以下情况，不应承诺自主大规模重构：

- 无法稳定构建；
- 没有可信测试和行为基线；
- 核心模块无人理解；
- 数据迁移不可回滚；
- 需求是“顺便把代码变好”；
- 没有业务验收人；
- 生产发布和观测极弱；
- 要求一次性替换；
- 时间预算不足以建立安全网。

可以先承接调查、资产盘点、依赖图、测试补齐和迁移设计。

## 4. 推荐阶段

1. Inventory：代码、服务、Owner、数据和依赖；
2. Baseline：构建、测试、性能和运行行为；
3. Characterization：为关键旧行为建立保护；
4. Target Design：明确目标架构和不变行为；
5. Seams：寻找兼容层和迁移切口；
6. Pilot：选一个低风险垂直切片；
7. Parallel Run：新旧路径对照；
8. Progressive Migration：按模块和数据逐步迁移；
9. Decommission：确认消费方清空后退役旧路径；
10. Long-tail Cleanup：处理临时兼容和债务。

## 5. Harness 在其中的角色

- 维护事实和资产图；
- 编译模块上下文；
- 管理目标设计和工程契约；
- 拆任务和写集；
- 隔离执行 Agent；
- 运行多层验证；
- 管理 Finding 和回流；
- 追踪迁移状态；
- 防止规则跨治理区误用；
- 为人类架构委员会提供证据。

## 6. 第一阶段可销售承诺

可信的承诺是：

> 用 Agent Harness 完成超大型代码库的调查、设计、迁移规划、分批执行和证据治理。

不可信的承诺是：

> 全自动重写几百万行代码并保证没有问题。

# 附录 E · 外部资料卡与汇合协议

## 1. 为什么需要汇合协议

框架、论文和大厂实践不断出现。若每次看到好内容就直接改 Harness，会产生概念污染、重复机制和方向摆动。

外部资料先被当作证据和候选，不直接成为内部事实。

## 2. 资料卡模板

```yaml
source_id: source-xxx
title: ...
type: paper | framework | company_practice | incident | standard
published_at: ...
reviewed_at: ...

problem_addressed: ...
context:
  organization_size: ...
  domain: ...
  constraints: ...

objects:
  - ...
mechanisms:
  - ...
evidence:
  type: benchmark | production | case_study | claim
  strength: low | medium | high

same_as_flowness:
  - ...
different_from_flowness:
  - ...
conflicts:
  - ...

adopt_candidates:
  - mechanism: ...
    reason: ...
    adaptation_needed: ...

reject_or_defer:
  - item: ...
    reason: ...

validation_plan: ...
```

## 3. 吸收规则

- 吸收问题和机制，不盲目吸收术语；
- 先映射到现有对象；
- 外部运行时不得成为内部语义内核；
- 生产案例优先于营销描述；
- 论文 Benchmark 不能自动代表组织环境；
- 开源项目要读代码、测试、Issue 和历史；
- 冲突不通过模糊整合消失；
- 新机制先进入 Evolution Track。

## 4. 冲突处理

当外部方案与 Flowness 冲突时，分别判断：

- 目标不同；
- 适用规模不同；
- 约束不同；
- 抽象层不同；
- 一方缺少证据；
- Flowness 的设计确实需要被推翻。

输出不是“取长补短”四个字，而是明确采用、适配、并存、延后或拒绝。

## 5. 合并后的追溯

被吸收的机制应记录：

- 来源；
- 内部对应对象；
- 修改内容；
- 适用范围；
- 实验证据；
- 是否已进入生产；
- 后续与原来源不同的演化。

# 附录 F · 工程负责人能力与责任边界

## 1. 为什么需要工程负责人

Flowness 的 Owner 可以持续负责问题定义、产品方向、机制创新、Agent 交互和质量判断，但当系统对外承诺企业级可靠性时，需要有人对技术真实性承担独立责任。

这个角色不是普通编码执行者，而是 Principal/Staff 级工程负责人。

## 2. 负责内容

- 运行时架构；
- 数据和一致性；
- 并发与故障；
- 性能和容量；
- 安全与权限；
- 发布、迁移和回滚；
- 可观测性和 SLO；
- 测试与验证；
- 工程复杂度；
- 技术债；
- 线上事故；
- 工程团队分工和质量标准。

## 3. 与 Owner 的边界

### Owner 决定

- 产品目标；
- 价值判断；
- 风险偏好；
- 体验和机制方向；
- 哪些现实值得改变；
- 不可逆的战略取舍。

### 工程负责人决定

- 如何在真实约束中实现；
- 哪种架构风险可接受；
- 技术方案的最小性；
- 何时不能上线；
- 如何迁移、回滚和维护；
- 哪些承诺缺少证据。

### 共同决定

- 大规模范围；
- 质量与成本权衡；
- 是否接受重大工程债；
- 是否进入企业生产；
- 是否更改核心系统不变量。

## 4. 筛选题

1. 读完 Flowness 核心代码和规范后，指出三个未被当前团队充分看到的真实风险。
2. 给一个宏大机制，要求压缩成两种不同成本的可行实现，并说明牺牲。
3. 设计一次事件事实源 schema 迁移和回滚。
4. 分析并发 Agent 修改公共接口时的冲突和一致性。
5. 设计百万行遗留代码迁移的第一阶段，不允许直接开改。
6. 举一次亲历的生产事故，说明检测、恢复和制度改进。
7. 反驳一个看起来很深但工程收益不足的方案。
8. 说明如何与 AI 高强度协作，同时不把模型输出当事实。

## 5. 红旗

- 只用大厂职级和术语压人；
- 只会写代码，不会定义完成和回滚；
- 对 AI 要么崇拜要么排斥；
- 无法阅读复杂设计，只想重写；
- 所有问题都建议上微服务、消息队列或新框架；
- 不愿意用证据反驳；
- 把 Owner 当需求输入机器；
- 不承认未知和风险。

## 6. 团队最小形态

在早期，一位强工程负责人 + Owner + AI Agent 群，可能优于多个普通开发。

随着生产扩大，再补：

- 平台/分布式工程；
- 测试与验证；
- SRE；
- 安全；
- 前端与产品工程；
- 领域专家。

团队扩张应围绕真实瓶颈，而不是照传统公司组织图复制职位。

# 附录 G · 开放问题与研究议程

以下问题没有在 v0.1 中假装解决。它们应作为持续研究对象，逐项建立实验和证据。

## 1. 认知编译

- Problem、Requirement、Design 和 Engineering 的最小通用 Schema 到底是什么？
- 哪些内容应进入 ConceptGraph，哪些应保持阶段产物？
- 如何检测阶段转换中的语义丢失？
- 怎样比较两个设计是否真正机制不同？
- 怎样校准语义验证器的误报和漏报？

## 2. 实时语义空间

- File/Symbol 与概念如何自动绑定且保持新鲜？
- 代码分析、运行 Trace 和人工声明的关系如何融合？
- 上下文增量编译的最佳频率是什么？
- 如何测量一条上下文是否真的被 Agent 使用？
- 怎样防止错误图关系造成错误注入？

## 3. Agent 行为算法

- 轨迹片段如何跨模型和工具统一？
- 结果归因如何排除任务难度？
- 怎样进行低成本反事实实验？
- 策略优化何时需要机器学习，何时规则足够？
- 如何防止指标改变记录而不改变真实行为？

## 4. 多 Agent 协作

- 何时多 Agent 的认知收益超过协调成本？
- 如何自动评价任务拆分？
- 怎样避免多个 Reviewer 共享盲点？
- 如何进行长期任务接力而不丢失语义？
- 分布式账本和多仓库事实如何合并？

## 5. 共识与变化

- 共识作用域如何自动计算？
- 消费方发现的准确率能达到多少？
- 变更涟漪如何避免告警风暴？
- 旧规则、新规则和历史代码如何长期共存？
- 什么时候应该重验证，什么时候直接迁移？

## 6. 验证器

- 设计质量怎样建立跨项目 Benchmark？
- 如何证明验证器覆盖真实失败而非模板合规？
- 语义验证和机械验证怎样组合？
- 长反馈周期领域如何进行治理？
- 验证器之间冲突如何裁决？

## 7. 产品与组织

- 专家认知外骨骼如何逐步服务较弱用户？
- 哪些专家判断可以沉淀，哪些必须保持人类在场？
- 如何降低 Flowness 对普通团队的进入成本？
- 深语义内核如何导出轻量组织界面？
- 企业愿意为何种结果付费？

## 8. 工程经济性

- 每新增一个对象、事件、Gate 的真实维护成本是多少？
- 哪些机制只需要观测，不值得强制？
- 什么规模下事件和图模型优于文档物料？
- 如何计算 Harness 本身的复杂度债？
- 什么时候应该停止自研并使用外部组件？

## 9. 长期终局

- 软件工程中证明的机制能迁移到哪些领域？
- “验证器成熟到哪里，自动化就到哪里”如何被量化？
- 人和 Agent 的权力、责任、身份和信用如何组织？
- Harness 是否会成为组织操作系统，还是只是一类专业生产控制平面？

每个开放问题进入研究时，都应创建 Problem IR、证据计划、候选方案和停止条件，避免开放议程再次变成无限发散许可证。
