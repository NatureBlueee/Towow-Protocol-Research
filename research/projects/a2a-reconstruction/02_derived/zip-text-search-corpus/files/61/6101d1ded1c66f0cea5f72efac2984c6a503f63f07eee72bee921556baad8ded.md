# 14　面向超级个体与 OPC 的主权代理操作系统

## 14.1 OPC 不是缩小版企业

将 OPC 理解为“员工数为一的公司”会低估其结构。大型企业通过岗位、部门、预算、法务、审计和信息系统把不同权威分开；OPC 往往由同一人承载，却通过多个 Agent、平台、账户、外包方和临时伙伴扩展执行能力。这种结构具有四个特点：

1. **单一外部责任根。** 违约、声誉、现金流与法律后果常集中在一个人或一个法人；
2. **内部角色复数。** 同一人对品牌、财务、交付、数据和生活拥有不同边界；
3. **注意力极度稀缺。** 高认知判断和异常处理是主要瓶颈，模型调用成本反而可能较低；
4. **能力可快速组装。** 工具、伙伴、外包和 Agent 能在短时间内创造新能力，但可靠性和责任更脆弱。

因此，OPC 的 Agent 系统不能只追求“自动化更多”，而应优化：哪些判断值得保留给人，哪些关系可以编译，哪些能力可以临时形成，哪些承诺必须被资源和证据约束。

## 14.2 OPC Operating Envelope

OPC Operating Envelope 是一个派生视图，而非新的事实 root。它汇总：

\[
OE_t = \langle objectives, roles, mandates, resources, commitments,
capacity, risk, attention, relationships, compiled\ routines \rangle.
\]

该视图回答：当前 OPC 在什么边界内能够安全行动，哪些资源已被承诺，哪些 Agent 有何权限，哪些关系处于形成或运行，哪些异常需要本人处理。

它不等于一个固定“用户画像”。其数据来自权威对象和事件图，并随着 Mandate、Commitment、Effect 和 Defeater 更新。

## 14.3 十二阶段操作模型

三维统一模型是理论坐标；OPC 十二阶段是面向运行的操作视图：

### 阶段 0　身份与权威根

确认自然人/法人身份、账户所有权、代表关系、签署和接受权。输出不是“已登录”，而是可追溯 Authority Root。

### 阶段 1　Mandate 与策略编译

把“帮我处理业务”转化为版本化目标、动作、金额、数据、风险、升级、撤销和过期规则。高风险动作需要更窄 Mandate。

### 阶段 2　本地世界编译

从邮件、文档、项目、日历、财务、工具和人的判断中生成任务相关投影；保留来源和不可数字化 Gate，不构造伪完整人格模型。

### 阶段 3　机会发现与问题构成

发现潜在客户、伙伴、资源或组合机会，并判断当前问题是否已经有稳定制度和字段，还是需要构成新的 Relation Schema。

### 阶段 4　协调机制选择

Router 选择平台、中心优化、人类经纪、双边形成、临时联盟、确定性服务或人工裁决的组合。

### 阶段 5　关系形成与现实 probe

通过边界问题、countercondition、sandbox 和可逆现实动作形成条件，而不是只交换长文本。

### 阶段 6　能力、工具与资源组装

引入模型、工具、伙伴、预算和执行环境；CRA 资格化可交付范围和恢复能力。

### 阶段 7　认领、承诺与资源预留

相关角色对精确 RelationVersion 作出 Stance，必要资源原子预留，明确退出、违约和数据权利。

### 阶段 8　Operation 与目标世界 Effect

编译最小权限 Operation，执行并由目标域 witness 观察真实变化。

### 阶段 9　Adoption、Acceptance 与 Settlement

分别处理目标域采用、主体接受、付款、争议和补救，不用“完成”覆盖全部状态。

### 阶段 10　数据派生、记忆与学习

记录实际数据使用、派生、长期记忆和训练更新；根据 Mandate 决定保留、删除或再利用。

### 阶段 11　Defeater、退出、恢复与局部重开

能力、权威、环境、价值或外部性变化只重开依赖闭包；稳定部分继续运行。

## 14.4 角色冲突与“内部多主体”

一个信任根内部可能存在多个主体性来源。例如创始人本人既有商业目标，也有个人边界；品牌合作 Agent 追求曝光，财务 Agent 追求现金流，交付 Agent 追求技术质量。它们并不是独立法律主体，却可能代表不同局部目标和权限。

系统不能简单以“最终都是同一个人”消除冲突。需要：

- 角色化 Authority Locus；
- 冲突策略和升级顺序；
- 预算、时间、信誉和私人生活的独立资源约束；
- material objective change 的本人确认；
- 不能由模型自动权衡的 lexicographic 禁区，例如违法、隐私泄露或明确个人边界。

## 14.5 OPC 的典型关系类型

### 标准化服务

例如订阅、支付、报税和固定模板交付。若制度充分、数据可授权集中、Effect 可观察，应优先平台或确定性服务。

### 非标准定制服务

需求、数据、交付、知识产权和接受标准未完全定义，需要双边形成与现实 probe；稳定后可以编译为重复模板。

### 临时能力联盟

多个超级个体联合投标、共同交付或资源互换。关键是高阶互补、资源预留、对外责任和客户 Acceptance。

### 个人品牌合作

商业、品牌、内容、时间和声誉角色同时存在。模型可以生成报价与创意，但本人对调性和长期关系的认领不可被自动化吞并。

### 数据与模型合作

训练、派生、保留和再披露权往往比“是否上传原始数据”更关键。最小可行路径可能是代码进入数据域，而非数据离开主体。

### 争议与恢复

交付已发生但对方拒绝接受，或 Agent 越权承诺。系统必须保留旧版本、Effect 证据、Mandate、补救和人工裁决。

## 14.6 真实价值假说

面向 OPC，系统价值不应只用成交率衡量。本文提出六项可测量假说：

- H1：在非标准事项中，组合机制减少达到真实 Commit/Reject 的人类高认知时间；
- H2：在标准事项中，Router 能旁路重型形成，成本不高于简单机制；
- H3：范围化 Mandate 降低越权 Effect，而不显著损害授权动作完成率；
- H4：版本化 Relation 与 explain-back 降低“同意但理解不同”的分歧；
- H5：现实 probe 与 countercondition 能形成部分静态表单或中心摘要无法形成的路径；
- H6：长期复用已编译关系降低后续边界披露和协调成本。

这些假说需要真实 OPC 前瞻性实验，当前尚未建立 E7 证据。

# 15　系统架构、协议内核与外部连接器

## 15.1 四个平面与一个联邦事件图

系统架构分为四个逻辑平面：

1. **主体与权威平面**：Entity、Authority Root/Locus、Mandate、Standing、Commitment；
2. **认识与形成平面**：Assertion、Unknown、Evidence、Boundary Oracle、PFE、CRA；
3. **协调与编译平面**：RelationVersion、JAA、Router、Stability Gate、Compiled World；
4. **操作与效力平面**：Operation、Attempt、Effect、Adoption、Acceptance、Settlement。

四平面通过联邦事件图连接。每个主权域维护自己的权威事实，跨域系统保存可验证引用、版本和事件，不要求一个全局数据库成为所有事实的最终来源。

![主权代理操作系统的四平面和组件关系。](figures/fig04_architecture.png){width=96%}

## 15.2 六个 canonical roots

当前最小权威对象保持六类：

### Entity

外部身份、信任根和责任关系。

### Mandate

范围化、版本化、可撤销委托。

### RelationVersion

具体共同关系的版本化 Schema、参数、参与者、条件和依赖。

### Assertion

带来源、置信、证据、有效期和可反驳性的主张。

### Commitment

产生未来义务、资源和补救的规范对象。

### Operation

可执行、幂等、可观察 Effect 的动作规范。

其他结构应优先表示为事件、属性、溯源边、策略或派生视图。只有出现独立权威和生命周期需求时才提升为 root。

## 15.3 统一事件包络

事件最小包络：

```json
{
  "event_id": "uuid",
  "event_type": "STANCE_RECOGNIZED",
  "entity_id": "...",
  "authority_locus": "...",
  "relation_version": "sha256:...",
  "subject_ref": "...",
  "mandate_ref": "...",
  "payload_ref": "...",
  "evidence_refs": ["..."],
  "previous_event_hash": "...",
  "timestamp": "...",
  "signature_or_attestation": "..."
}
```

包络保证来源、顺序和引用，但事件语义由具体类型和相称 Authority 决定。哈希链有助于审计，不等于去中心化账本，也不替代真实身份和目标域 witness。

## 15.4 关键事件类型

事件至少覆盖：

- `ASSERTION_CREATED / CHALLENGED / SUPERSEDED`；
- `BOUNDARY_ASSESSMENT`；
- `SCHEMA_REVISION_PROPOSED / MATERIALIZED`；
- `STANCE_RECOGNIZED / REJECTED / CONDITIONAL / WITHDRAWN`；
- `MANDATE_ISSUED / NARROWED / REVOKED / EXPIRED`；
- `RESOURCE_RESERVED / RELEASED / CONSUMED`；
- `COMMITMENT_CREATED / ACTIVATED / FULFILLED / BREACHED`；
- `OPERATION_SPECIFIED / ATTEMPTED`；
- `EFFECT_CONFIRMED / PARTIAL / UNKNOWN / REVOKED`；
- `ADOPTION_RECORDED`；
- `ACCEPTANCE_RECORDED / CONTESTED`；
- `SETTLEMENT_RECORDED`；
- `DEFEATER_RAISED / SCOPE_REOPENED`；
- `DATA_USED / DERIVED / RETAINED / DELETED / LEARNING_UPDATED`。

## 15.5 Boundary Oracle 接口

```text
assess(
  task_family,
  relation_version,
  candidate,
  requested_claim,
  disclosure_budget,
  mandate_ref
) -> OracleAssessment
```

返回：

```text
status: ACCEPT | SEPARATE | WITNESS | COLUMN |
        MODEL_OBJECTION | HUMAN_REFUSAL | UNKNOWN | COUNTERCONDITION
scope
evidence_refs
cut_or_condition
validity
confidence        # 仅认识语义
authority         # 是否具有规范效力
disclosure_cost
reconstruction_risk
```

`confidence` 和 `authority` 必须分别记录。模型高置信异议不能被编码成有权拒绝；真实主体拒绝可以没有模型解释。

## 15.6 Context Compiler

Context Compiler 将主体本地世界编译为任务相关上下文包，而不是上传全部历史。其职责包括：

- 按 Mandate 和用途选择信息；
- 保留来源和有效期；
- 区分事实、推断、偏好和模型建议；
- 生成未知项和冲突；
- 对敏感内容输出证明、摘要、区间或本地 Oracle；
- 防止“上下文越多越好”的无界复制。

Context Compiler 是 Harness 的核心组件，因为 Agent 的行动质量取决于可用上下文和权限，而不是模型参数 alone。

## 15.7 Coordination Runtime

Coordination Runtime 维护 RelationVersion、JAA、候选、Stance、Commitment 和机制图。它不拥有各主体的全部本地世界，也不自行产生最终权威。其功能包括：

- 版本差异与 materiality 检查；
- Unknown 和形成算子管理；
- Router 与 Stability Gate；
- 资源预留和并发控制；
- explain-back、冷静期和逐项认领；
- 依赖图与 scoped reopen；
- 对 A2A、MCP、人类工作台和外部 TrustAdapter 的协调。

## 15.8 Effect Gateway

Effect Gateway 把 Operation 连接到目标世界。它负责：

- 验证 Mandate 和 RelationVersion；
- 生成 idempotency key 和 AttemptID；
- 执行 pre-effect validation；
- 调用工具、API、人类或物理流程；
- 从目标域获取 authoritative readback；
- 记录 Effect、撤销、恢复和补偿；
- 将模型输出与目标事实分开。

Effect Gateway 可以由支付、代码托管、日历、ERP、CRM、文件系统、区块链、法律签署或人工回执实现。

## 15.9 Event Ledger 与 Compiled World

Event Ledger 保存不可覆盖的因果和权威历史；Compiled World 提供当前可运行视图。二者关系类似：

\[
CompiledWorld_t = Fold(EventLedger_{\le t}, valid\ policies, local\ facts).
\]

若事件被撤销或新 Defeater 出现，视图重算或局部失效。Compiled World 不能绕过原始 Authority 直接修正事实。

## 15.10 外部协议适配

### A2A Adapter

用于 Agent 发现、Task、Message、Artifact 和长任务状态。A2A Task 可以承载 Operation 或形成任务，但其 `completed` 状态不能自动映射为业务 Acceptance。

### MCP Adapter

用于工具、资源和本地服务访问。MCP authorization scope 映射到 Mandate 的资源动作子集；RelationVersion 仍提供目标、数据派生、Effect 和接受语义。

### OAuth / Mandate / VC Adapter

OAuth 和新型 Agent Mandate 草案可绑定令牌、任务和委托链；VC 可承载身份、资格和授权声明。适配器必须保留发行者、持有者、受众、有效期和撤销，并避免把可验证声明误写成真实世界充分证据。

### WoWok / TrustAdapter

WoWok 一类可编程信任对象可以承担托管、权限、服务、Treasury、仲裁和 Repository 等 Effect 基础设施。本文把它视为可替换 TrustAdapter，而非理论前提或唯一实现。

## 15.12 最小实现顺序

正式系统不应从“搭一个通用 Agent 市场”开始。最小纵向闭环为：

1. 一个 OPC Entity 与两个 Authority Locus；
2. 一个范围化 Mandate；
3. 一个非标准 RelationVersion；
4. 一个 Boundary/Countercondition 循环；
5. 一个可逆现实 probe；
6. 一个资源预留；
7. 一个可见目标 Effect；
8. 一个独立 Adoption/Acceptance；
9. 一个 Defeater 和局部 reopen；
10. 一个稳定子图编译为确定性运行。

只有该闭环真实运行后，横向扩展发现市场和开放协议才不会失去现实语义。

## 15.13 安全边界

生产系统至少需要：

- 强身份、密钥和凭证管理；
- 细粒度、短期、可撤销 Mandate；
- 不可逆动作的人类或双重 Gate；
- Effect readback 与幂等；
- 资源预留与限额；
- 私有上下文隔离和最小披露；
- 事件溯源和争议保全；
- 模型升级、工具变化和 prompt injection 的 Defeater；
- 安全默认拒绝，但允许结构化 countercondition；
- 面向第三方外部性的 Standing 与审查。

当前 Fieldkit 只验证研究对象和状态机，不具备生产级上述能力。
