# Agent 协调基础设施的深度研究报告

## 核心结论

你的总方向是成立的，但要把话说得更准：你要做的**不是一个“协议”**，而是一套横跨**发现、承诺、验证、结算、归因、争议处理**的**协调基础设施**。MCP 的官方定位是把模型连接到工具和数据，A2A 的官方定位是面向任务生命周期的 agent 间通信，x402 的官方定位是把支付嵌入 HTTP 交互；它们分别解决的是“能接上”“能说话”“能付钱”，却没有单独解决陌生主体之间最难的那一层：**第一次接触时，如何在不共享全部内部状态的前提下，完成可信发现、可验证承诺、自动结算和事后归因**。这一层更像市场基础设施，而不是消息协议。citeturn12search13turn29search2turn27search1turn27search3

从学术脉络看，你提出的东西也不该自称“凭空出现的第三类机制”。Coase 对企业的解释仍然是基础：企业存在，是因为使用市场有成本。Roth 后来进一步把“好市场”拆成三个条件：**厚度、抗拥塞、安全**。在多智能体研究里，承诺协议与电子制度已经研究了二十多年，核心想法是：开放系统里的自治主体，需要在通信之上有一层可检查的社会约束与制度结构。你真正新、也真正有价值的地方，不在于“需要新机制”这句总论，而在于**把承诺协议、市场设计、共享状态、可验证结算和边界签字这几样东西，拼成一台能落地的机器**。citeturn24search4turn31search0turn30search0turn30search1turn30search7turn30search24

如果把话再压缩一点，我的判断是：**五年内能做成的，不是一个面向全世界陌生 Agent 的“完全开放大市场”，而是一套先在单信任根内部成立、再在少数信任根之间扩展的薄层基础设施。**最现实的路径，是从**强验证器行业**起步，先做**“可验证产物 + 自动托管结算 + 有限披露发现”**，而不是从“通用 Agent 大市场”起步。软件工程已经证明了这条路径能跑：Anthropic 官方披露，Claude 写了 Anthropic 大量代码，2026 年 5 月合入代码中超过 80% 由 Claude 生成；Claude Code 的商业化速度也说明，**先把单根内部的编排、验证、交付做透**，再谈跨组织协调，是现实中的先后顺序。citeturn36search0turn36search1turn0search0

## 这件事到底是什么

你现在最该坚持的一句话是：**它不是协议，它是基础设施；协议只是它在成熟后的一部分退休形态。**协议擅长规定字段、消息和过程；基础设施擅长承载流动性、归因、争议规则和结算终局。Swift 自己把自己定义为全球成员制 cooperative、提供安全金融报文服务；Linux Foundation 对 AAIF、x402 的处理方式，也是在把 agent 通信与支付标准往“中立治理的公共层”上推。历史反复说明，真正值钱的，通常不是报文格式，而是**谁掌握了成员网络、谁坐在结算点、谁积累了案例库、谁掌握了准入与争议边界**。citeturn37search3turn37search7turn37search9turn28search0turn27search1

从机制学上看，这套基础设施至少要同时承担六件事。第一，**发现**：让陌生主体在不泄露全部家底的前提下彼此可见。第二，**承诺**：把未来状态改造成今天就能锁定一部分后果的结构。第三，**验证**：让“说得出来”与“作数”分开。第四，**结算**：让钱、权限或其他押物随验证自动移动。第五，**归因**：让系统知道到底发生了什么，而不只能看到“任务完成了”。第六，**争议处理**：当验证器不完备时，谁来裁定、谁承担剩余责任。现有 A2A 的 task lifecycle 已经提供了一个很好的骨架——任务、状态、artifact、异步更新——但连 A2A 社区自己的讨论都承认，**首次跨组织调用至少还缺 authority 和 offline-verifiable evidence 两大块**。也就是说，A2A 像是握手和会话层；你要做的是**让握手之后真的能成交**的那层。citeturn29search2turn29search1turn35search12turn35search15

你文中“志、域、场”的直觉，我认为是对的，而且比很多行业里常见的“再造一个 agent profile”思路深得多。它本质上是在把协调所需的持久物拆成三类：**事件事实、权责边界、语义位置**。这和分布式系统、共同知识、会话语用学的脉络是吻合的。Halpern 与 Moses 的经典结论是，单靠不可靠消息无法制造真正的共同知识；Clark 对 common ground 的论述则说明，人类对话并不是裸消息交换，而是不断往共享地基上加砖。把这两条放在一起，你会得到一个很硬的工程判断：**高价值协调不能只靠 agent 彼此发消息，必须落在一份可共同引用、可验证、可追加的共享状态之上。**这也是为什么“共享工作区”“共享文件系统”“事件日志”在真正能跑的 agent 系统里反而越来越重要。citeturn22search0turn22search11turn22search2turn23search11turn23search13turn23search22

## 学术上已经有了什么

如果你要把这件事做成一套严谨论证，最好的姿势不是“我发明了一个全新的世界”，而是“我把几条原本分散的学术线收束成一个可操作的设计判决”。目前最相关的四条线，其实已经很明确。

第一条是**企业与市场的经典制度经济学**。Coase 解释为什么会有企业，Hayek 解释价格为什么能压缩分散知识，Demsetz 解释产权为什么在稀缺时出现，Hart 与 Moore 解释为什么资产控制权与企业边界有关。拿这些理论来读 Agent 世界，一个自然推论就是：当某些交易成本被软件、支付轨道和验证器大幅压低后，原来必须留在企业内部的协调，会开始向“更细颗粒度的外部召集”迁移；但凡验证器不成熟、披露代价太高、归因不清晰的地方，边界又会收回来。换句话说，**不是“公司消失”，而是公司边界开始随验证器成熟度移动。**citeturn24search4turn24search1turn24search2turn24search3turn24search19

第二条是**市场设计**。Roth 说得很直白：市场若要好用，必须既厚、又不拥塞、还要让参与者觉得安全。你想做的跨-Agent协调层，核心难点正好一一对上：没有发现层，就做不厚；谈判和调用太贵，就会拥塞；如果新参与者没有办法靠押物与验证而安全进入，市场就会板结成“只有老玩家有资格被调用”。这一视角特别重要，因为它会逼你把“产品成功”定义成**市场质量问题**，而不是“协议功能完备问题”。一个机制即便字段设计得极漂亮，只要没有流动性、没有安全的冷启动、没有低摩擦完成交易，它就不会形成市场。citeturn31search0turn31search1turn31search3turn31search5

第三条是**承诺协议与电子制度**。这条线最接近你的“成约之刻”直觉。Singh 系的工作长期强调，传统 interaction protocol 只规定“允许发什么消息”，却不天然承担谁对谁负有什么义务；承诺式建模则把社会关系显式化，使 compliance checking 成为可能。电子制度的研究则进一步把“开放多主体系统需要规则、角色、场景与可执行的规范结构”这件事说透了。你的贡献空间不是推翻这条线，而是把它从语义层搬到基础设施层：**承诺不只是一种抽象逻辑关系，而是要和押物、验证器、结算、签字边界直接耦合。**citeturn30search0turn30search3turn30search7turn30search8turn30search22

第四条是**共同知识与共享状态**。两将军问题的教训不是“别通信”，而是“别指望消息本身构成足够强的协调基底”。所以工程上才会不断重演同一件事：最可靠的系统，最后都重新长回某种共享事实源。Anthropic 的多 agent 研究系统，用的是 orchestrator-worker；Managed Agents 的设计语言高度像操作系统；Claude Code 又不断把持久文件、技能目录、记忆文件这些“结构化外部状态”重新引回来。这里的行业信号已经很清楚：**生产级 agent 的瓶颈越来越不是“让模型再聪明一点”，而是“让状态、权限、验证与回放变得可管理”。**citeturn13search0turn13search10turn13search13turn36search13turn12search11

## 工程现实与真正的难点

真正的难点不是结算，也不是“让 Agent 说话”。结算轨道和会话轨道这两年进展反而很快。A2A 已经有任务对象和生命周期，AAIF 已经成为 MCP 等项目的中立托管地，x402 也已经被捐给 Linux Foundation 作为开放支付标准继续演化。换句话说，**“会说话”和“能付款”已经不是最稀缺的地方。**citeturn29search2turn28search0turn28search7turn27search1turn27search3

最硬的第一道墙，是**隐私保护下的语义发现**。你不能把“会做什么、现在能不能接、最低边界条件是什么”全公开，否则企业根本不敢挂单；但如果什么都不公开，陌生匹配就不会发生。更糟糕的是，“把文本做成向量再匹配”并不天然安全。近年的攻击工作表明，文本嵌入可以被反演，少量泄露样本下也能进行部分恢复；防御研究虽然在推进，比如投影网络、池化与噪声注入、embedding obfuscation，但主流方案仍然是“有用但不够通用”，远不能让人放心地把高价值商业语义直接暴露给开放市场。这里没有魔法。五年内更现实的方案，是**粗粒度公开索引 + 细粒度受保护比对 + 分阶段披露**，而不是指望一套纯密码学近义匹配一招定乾坤。citeturn33search12turn33search21turn33search3turn33search8

第二道墙，是**验证器强度**。这一条必须说得很绝：**机制强度基本上等于验证器强度。**软件为什么最先成熟？因为编译器、测试、回归、lint、本地重放、本身就是现成验证器。Anthropic 公开材料显示，Claude Code 已经在真实工程里承担了高比例代码生成，Anthropic 也明确把 eval、tooling、harness、containment 看成生产 Agent 的核心工程。反过来，法律、医疗、复杂审计之所以慢，不是模型不“聪明”，而是输出何时“作数”这件事没有足够强的机器判据。这个差距不是文案能抹平的。只要验证器够不着，市场就会向边界借人类身份、执照、章或保额。citeturn36search1turn36search0turn12search17turn36search9turn36search8

第三道墙，是**可信执行环境只能缓解，不会消灭信任问题**。AWS、Azure、Google 都已经把 enclave、confidential VM、attestation 做成了商用品，这给“受保护匹配”“受保护验证”“受保护结算前检查”提供了非常现实的工程工具。可问题在于，TEE 提供的是更好的隔离与证明，不是神圣不可侵犯。AWS Nitro Enclaves 强调它没有持久存储和外网；Google 和 Azure 都提供 attestation；与此同时，AMD 的 2026 安全公告和云厂商自己的安全 bulletin 又提醒你：**TEE 仍然有实现缺陷、补丁窗口和供应链假设**。所以 TEE 适合做“信任预算里的重要组成部分”，不适合被吹成“信任问题的终极终结者”。citeturn20search1turn20search5turn20search17turn20search0turn21search0turn21search7

第四道墙，是**声誉系统的诱惑与陷阱**。行业里天然会有人想靠 reputation layer 来填这一大坑，因为它便宜、顺手、像平台评分。但这一层在开放系统里非常容易被女巫攻击、合谋、买评与“洗白”身份破坏。相关研究和行业讨论都在反复强调：声誉可以作为附加信号，不能作为高价值协调的承重墙。连 A2A 社区关于 trust primitives 的讨论，也在往“signed receipts”“offline-verifiable evidence”而不是单一分数倾斜。我的建议很明确：**你可以保留声誉，但不该让声誉承重。承重的必须是验证器、押物、授权链和可验证收据。**citeturn35search13turn35search7turn35search1turn35search6turn35search15

## 产品终局与最现实的蓝图

如果从五年终局倒推，这套东西最终不会长成一个单独的“App”，而更像三层叠加。

最下层是**本地主权结构层**。不管你最后叫不叫“志、域、场”，都需要一个能容纳三类持久物的容器：**事件记录、权限与委托边界、可检索的语义索引**。Anthropic 自己的产品与工程文档已经在多个地方验证了这种方向：持久 memory 文件、skills 目录、工作区作用域、可编程 harness、托管 agent 的状态资源，本质上都在把 agent 的“脑”与“身外结构”拆开。你的机会不在再造一个聊天框，而在于把这个容器做成**默认本地优先、可导出、可审计、能挂接跨根薄层**的 runtime。citeturn13search10turn13search6turn13search14turn13search13turn36search14

中间层是你真正该自建的东西：**跨信任根薄层**。它不该很厚，厚了就会吃掉主权、拖垮隐私和共识成本；它只需共持最少的几类事实。我认同你文里的四件事——**挂出的意图、计价的披露、锁定的承诺、结清的事实**——因为它们刚好对应了跨根协调里最不能只留在各自内部的东西。A2A 的 task/artifact/status 可以做你部分事件骨架；x402 或其他可编排支付轨道可以做结算管道；但**发现、授权、押物登记、签字边界、判例与收据**必须由你自己来定义成第一类对象。否则你做出来的还是“能互调的 Agent”，不是“能成交的 Agent”。citeturn29search2turn29search1turn27search1turn27search3turn35search12

最上层才是**面向不同用户的产品表现层**。对中小企业，它会表现成“我的 agent 可以安全接单、下单、托管、验收、收款”；对一人公司，它会表现成“我没有平台评分也能靠押物和验收拿到活”；对大企业法务/采购/财务，它会表现成“我能把 SOP 变成可审计的状态机”；对开发者，它会表现成“我把一个可调用能力挂出来，就能在符合条件的前提下被发现、被调用、被结算”。这层 UI 不值得你投入过多战略资源，因为界面会被生成、渠道会被重画、入口会不断变化；真正长命的是底层数据结构、授权链、案例库与结算规则。Anthropic 自己的经验也在朝这个方向走：越来越多价值沉在 harness、eval、tooling、containment 与 workspace，而不是“对话框长什么样”。citeturn12search11turn12search17turn36search2turn13search13

具体到“第一款产品”，我不建议你从“开放 Agent 市场”起步。我建议从**单根内闭环 + 伞形根跨企业协同**起步。最适合的前两个场景，不是最性感的场景，而是最容易判定对错的场景：**软件交付**与**结构化 B2B 作业**。前者有天然验证器；后者可以先选那些结果可机器检查、且剩余风险可被押物和有限人工签字覆盖的流程，比如对账、票据核验、标准化内容交付、带明确验收口径的采购与供应协作。Anthropic 已经在金融工作流上推出 ready-to-run agent 模板，说明像 KYC、月结、文档处理这类任务正在接近“半结构化可验证”的商业甜点区。citeturn36search0turn36search1turn15search17turn18search0

## 商业模式、治理与进入路径

商业上，最危险的误判是“协议一旦成了标准，自然就有价值”。现实往往反过来：**协议开源和中立化是加速采用的条件，不是价值沉淀的位置。**AAIF、x402 被推到 Linux Foundation，本身就是信号：大厂愿意共同托管互联协议，因为真正想争的是协议之上的生态位。对你来说，值钱的地方应该落在四类资产上：**流动性、判例库、归因/收据数据、以及担保与结算能力。**其中最难复制的，通常不是代码，而是“这类争议你们怎么判、外部信不信你们的判法、结果能不能执行”。citeturn28search0turn27search1turn27search3turn37search7

所以治理上，最好从一开始就把“公司产品”和“公共层规则”分开。一个现实可行的路径是：**公司先建产品与早期网络，公共薄层逐步基金会化或联盟化**。Linux Foundation 这两年的动作，已经把 agent 互操作、支付协议、中立托管这条路径示范了一遍。你若想成为跨根基础设施，不宜把最关键的识别、发现与规则层做成“只能信你这家公司”的黑盒；那会在规模起来之前，就先触发生态与监管的不信任。citeturn28search0turn27search1

地缘与司法辖区问题也不能装没看见。Swift 自己既是合作社，也明确受比利时法律与治理结构约束，并有明确的 sanctions/compliance 义务。这说明“中立基础设施”从来都不是神话中的无国籍云雾，它一定落在某种公司法、监管和执法边界里。若你的系统最终碰钱、碰准入、碰争议裁决，就必然要处理司法辖区。香港和新加坡之所以是现实候选，不是因为叙事漂亮，而是因为它们已经在稳定币与可编排资金工具上形成了较清晰的监管与实验路径。要真做全球层，技术上应该做**联邦化**，治理上应该做**可迁移**，而不是假装存在一个“纯粹超主权”的中枢。citeturn37search7turn37search9turn17search4turn17search0turn17search15turn17search1turn17search5

进入市场的路径，我建议比你原来的想法更保守一点，也更凶一点：**先从一个你能实际控制风险的伞形根开始。**例如产业园区、行业联盟、特定大型企业生态、或者一个强服务商网络。原因很简单：Roth 的“安全”不是口号，新市场在冷启动时最缺的不是供给和需求，而是**第一批人为什么敢把真实业务挂进来**。你需要一个能代垫部分押物、能做线下尽调、能当早期仲裁者的 umbrella root。等验证器成熟、案例库变厚、收据与结算轨迹积累起来，再逐步把这个伞撤掉。说难听点，这不是理想主义受损，这是市场设计在干活。citeturn31search0turn31search1

## 路线图与可证伪的实验设计

如果你想把这件事做得像科学而不是像信仰，路线图里每一阶段都必须有**可证伪判据**。我建议把路线分成三个阶段。

第一阶段是**单根内闭环**。目标不是“开放市场”，而是把你的本地主权结构、事件状态机、验证器接入、押物逻辑和结算接口打通。最合适的应用是软件开发协作、文档处理流水线、结构化财务/运营流程。验收不是 DAU，而是非常冷血的几个指标：**端到端通过率、自动重试后的最终通过率、平均每单协调时延、人工介入率、争议率、争议后的可回放率**。如果这一步你都无法让一家公司或一个园区内部显著省时省错，那么跨根市场基本不用做梦。Anthropic 关于 agent eval 的写法值得学：评估就是把 grading logic 直接绑到产物上，而不是量“看起来聪明”。citeturn12search17turn36search2turn36search11

第二阶段是**少数信任根之间的跨根试点**。这里最重要的实验，不是“协议互通成功率”，而是三组 A/B 对照。第一组，对比**共享状态驱动**与**消息驱动**的效率、成本与错误率；Halpern-Moses 的理论告诉你为什么前者可能更可靠，Anthropic 的多 agent 实践提供了现实样板。第二组，对比**不同披露粒度**下的撮合率与履约率联合指标；只看撮合率会骗你，必须把履约乘上去。第三组，对比**不同验证器成熟度**下所需押物比例与坏账/争议情况；如果你的理论对，验证器越弱，市场越需要更高押物、更多人工签字或更窄权限。citeturn22search0turn22search11turn13search0turn31search0

第三阶段才是**联邦化和规则外溢**。判据不该是“你自己扩张多快”，而该是**有没有第二个独立运营方愿意在不依赖你公司运营团队的前提下跑同一套薄层规则**。如果没有，那说明你做成的是一家优秀的垂直服务公司，而不是基础设施。两者都可以是好生意，但不是一回事。citeturn28search0turn27search1

理论研究上，你最适合发力的不是空泛哲学，而是三个窄而硬的研究问题。其一，**隐私保护语义发现**：怎样在不暴露明文语义的前提下支持“足够好”的近义匹配。其二，**验证器成熟度与市场边界**：能否把“某行业可自动验收比例”与“外部化协调比重”建立起经验关系。其三，**收据与归因本体**：怎样定义一组通用的、可离线验证的交易收据，使声誉退居次位、证据前置。这里完全可以自己做工程研究，同时和 MAS、机制设计、分布式系统、密码学方向的研究者合作。承诺协议、电子制度、共同知识、市场设计这些文献，足够把论证骨架搭得很硬。citeturn30search3turn30search7turn22search0turn31search0

## 最值得坚持的设计原则

有几条原则，我认为你应该非常强硬，甚至强硬到让某些“更容易卖”的方案进不了门。

第一，**不要让声誉承重**。评分可以有，排行榜可以有，但高价值行为必须靠验证器、押物、授权链和收据。否则你只是在复制平台经济那套“先评分、后贵族化、再白洗”的路径。citeturn35search13turn35search7turn35search6

第二，**不要把跨根薄层做厚**。凡是可以留在各自本地主权结构里的，就不要共持。厚层会诱发隐私泄露、治理争夺和共识成本膨胀。A2A、MCP 已经说明，行业愿意共同标准化的，通常是薄接口而不是厚内脏。citeturn28search0turn29search2turn12search13

第三，**默认“验证器不够强”是常态，而不是例外**。因此，你的系统必须天然支持边界签字、可吊销接入权、风险分级权限和人工兜底，而不是等出了事故再补。Anthropic 对 containment 和 permission 的投入，就是这个现实的最好注脚：模型层永远不会 100% 靠谱，所以系统层必须接管。citeturn36search8turn36search9

第四，**把可导出、可迁移、可回放当作一等公民**。如果用户无法导出自己的记录、授权、收据和案例，你做的就不是基础设施，而是新型平台锁定。AAIF、x402 都在往中立托管方向走，原因很朴素：真正的公共层，必须允许参与者在不丢身份与历史的前提下迁移。citeturn28search0turn27search1

## 开放问题与限制

最重要的未决问题，仍然是**隐私保护语义发现到底能做到多好**。现有研究足以证明“直接暴露 embedding 并不安全”，也足以证明“防御有进展”，但还不足以证明你能在真实商业环境里同时拿到高撮合率、高隐私和低成本。这个问题如果五年内没有突破，你的终局就会从“开放跨根市场”退化为“多个单根内市场 + 有限互联”。这不是失败，而是边界重画。citeturn33search12turn33search21turn33search8

第二个限制，是**TEE 不是圣杯**。它足够重要，值得用，但不能当宗教。做系统设计时，最好把 TEE 放在“额外提升可信度”的篮子里，而不要把全部合法性押在“这台 enclave 没问题”上。citeturn20search1turn20search17turn21search0turn21search7

第三个限制，是**你对“无身份”的坚持需要更精确**。严格地说，不是所有地方都能无身份，而是**内部流动单元可以弱身份甚至无持久身份；高风险边界能力仍然要有人、法人、执照、保额或受监管实体来垫背。**这一点不是理论失败，反而是现实感所在。没有这层现实感，整套设计会很优雅，也会很快撞墙。citeturn37search7turn17search0turn17search1

最后一个限制，是**“中立”永远不是口号，而是架构与治理的结果**。只要你碰支付、准入、争议、跨境合规，就不可能完全脱离主权与司法。最好的做法不是否认这件事，而是把它显式化：联邦化、最小共持、规则公开、证据可离线验证、治理可迁移。做不到这些，中立就是品牌词；做到了，中立才勉强配叫能力。citeturn37search7turn37search9turn28search0turn27search1

整体上，我的结论很明确：**这件事不是空想，而且很值得做；但它能做成，靠的不是“Agent 会越来越强”这句废话，而是你能不能把发现、承诺、验证、结算、归因、争议这六件事压缩成一套薄而硬的基础设施。**先在强验证器行业里做成，先在少数信任根之间做成，再让规则外溢；反过来做，十有八九会变成又一个“协议很多、成交很少、故事很大、判例很空”的行业泡沫。citeturn36search1turn31search0turn30search7turn27search1turn28search0
