# 04 · 工程方案系统规范

## 1. 工程方案是什么

工程方案是将 Design IR 编译为一个在真实技术、资源、组织和运行约束下可实现、可验证、可维护、可演化的系统模型。

它不负责重新定义产品目标，也不应暗中修改设计。如果工程约束迫使设计改变，必须显式回流，而不是由实现者静默替换。

## 2. Engineering IR 的主要内容

### 2.1 系统边界

- 系统与外部依赖；
- 信任边界；
- 数据边界；
- 部署边界；
- 责任边界；
- 故障隔离边界；
- 可替换与不可替换组件。

### 2.2 组件与模块

明确服务、包、Worker、Agent、队列、数据库、缓存、对象存储、策略引擎、审计系统和观测系统的职责、接口和所有权。

### 2.3 接口契约

每个接口至少定义：

- 身份和版本；
- 调用方与消费方；
- 输入输出类型；
- 必填、默认、范围和单位；
- 幂等键；
- 超时和重试；
- 限流；
- 错误模型；
- 兼容性；
- 权限；
- 审计；
- 弃用与迁移。

### 2.4 数据模型

包括实体、值对象、聚合边界、唯一性、一致性、索引、生命周期、归档、删除、版本、迁移、隐私和恢复。

### 2.5 状态与事务

- 哪些状态持久；
- 哪些状态可重建；
- 强一致和最终一致边界；
- 原子事务；
- Saga 和补偿；
- 并发写入；
- 锁、租约和乐观并发；
- 幂等和去重；
- 部分成功如何表达。

### 2.6 调度与资源

- 模型路由；
- Agent 池；
- token、CPU、内存和时间预算；
- 优先级和抢占；
- 背压；
- 并发帽；
- 超时；
- 熔断；
- 退避；
- 降级；
- 防止重试风暴。

### 2.7 安全与权限

- 身份认证；
- 最小权限；
- 文件、分支、工具和网络访问；
- 密钥；
- 沙箱；
- 多租户隔离；
- 高风险操作审批；
- 越权检测；
- 审计和追责。

### 2.8 可观测性

不仅监控进程和错误，还要记录：

- 当前任务和阶段；
- 使用的 Design/Engineering/Consensus 版本；
- 上下文编译输入；
- 工具和外部调用；
- 决策和证据；
- 产物和消费方；
- 阻塞与回流；
- 资源消耗；
- 完成判定。

### 2.9 测试与验证

至少考虑：

- 单元；
- 集成；
- 端到端；
- 契约；
- 状态机；
- 属性测试；
- 变形测试；
- 并发测试；
- 故障注入；
- 回放；
- 权限；
- 迁移；
- 漂移；
- Agent 行为；
- 追溯完整性。

### 2.10 发布、迁移与回滚

- feature flag；
- shadow；
- canary；
- 灰度；
- 双写；
- 数据迁移；
- schema 兼容；
- 旧版本退役；
- 回滚条件；
- 故障恢复演练。

### 2.11 运维和长期演化

明确所有者、SLO、报警、值班、容量、成本、依赖更新、技术债、灾难恢复和一年后的可理解性。

## 3. 工程方案的证据结构

每个承重技术决定应形成增强型 ADR：

```yaml
decision_id: ADR-042
question: 如何保证多个执行 Agent 不同时破坏公共协议
context: ...
candidates:
  - global_mutex
  - optimistic_concurrency
  - ownership_partition
  - proposal_approval_merge
evaluation:
  consistency: ...
  throughput: ...
  recovery: ...
  operational_cost: ...
decision: ownership_partition + optimistic_concurrency
reasons: ...
tradeoffs: ...
evidence:
  source_review: ...
  prototype: ...
  benchmark: ...
assumptions: ...
falsification_conditions: ...
reopen_trigger: ...
```

方案的可信度来自证据等级，而不是作者语气。

## 4. 技术研究方法

### 4.1 文献和权威资料

优先官方文档、标准、论文和成熟项目的设计记录。搜索只能找到入口，不能替代验证。

### 4.2 源码考古

研究开源项目时，不只读 README：

- 找核心类型和接口；
- 找注册和调用路径；
- 看测试如何表达不变量；
- 看故障和 Issue；
- 看历史设计为何改变；
- 建最小实验验证真实行为。

### 4.3 原型与基准

对性能、并发、上下文选择、模型行为和外部依赖进行可重复实验。记录环境、输入、次数、方差和失败样本。

### 4.4 生产证据

原型通过不代表生产成立。需要真实负载、长周期、故障恢复、运维成本和用户结果。

## 5. 以简驭繁

完整工程思考可以很长，最终实现不应因此自动复杂。

工程方案必须比较：

- 不改；
- 加观测；
- 最小修补；
- 局部重构；
- 适配层；
- 统一抽象；
- 渐进迁移；
- 完整替换。

最优方案不是对象最多、Gate 最多或文档最长，而是在风险可接受的前提下，用最少长期复杂度达到目标。

## 6. 工程方案审查

至少包含：

- 架构与质量属性；
- 数据和一致性；
- 并发；
- 安全；
- 性能和容量；
- 测试和可验证性；
- 可运维性；
- 迁移与回滚；
- 成本；
- 复杂度与技术债；
- 组织可执行性；
- 设计忠实度。

评审者不得只给“同意/不同意”，应提出具体风险、证据、反例和修改条件。

## 7. 工程方案完成门

- 设计对象均有工程映射或明确不实现；
- 关键接口和数据契约完整；
- 并发、错误和部分成功有处理方式；
- 安全和权限边界明确；
- 质量属性映射到指标和测试；
- 关键技术选型有证据；
- 发布、迁移、回滚和运维可执行；
- 主要风险经过攻击；
- 开放问题有所有者和触发条件；
- 可以从中提取工程共识和计划，而无需下游重新做架构设计。
