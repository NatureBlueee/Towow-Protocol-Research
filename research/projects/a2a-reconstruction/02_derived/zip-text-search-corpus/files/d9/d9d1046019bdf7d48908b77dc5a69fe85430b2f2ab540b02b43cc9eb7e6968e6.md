# 给本地团队的交接说明

## 你们接到的不是一个完成品

当前包已经形成可运行的结构，但仍处在“研究型参考实现”阶段。它最有价值的部分不是文件数量，而是已经立住了几条必须继续守住的逻辑：

1. **规范与运行主体分离**：规则约束结果，不绑死 Agent、模型和编排拓扑。
2. **对象先于页面**：页面是领域世界的投影，不能反向发明产品。
3. **证据、验证、接受和责任分离**：能检查不等于能替主体作数。
4. **上下文是受治理的渠道**：每个 Agent 读取什么，比它自称什么专家更重要。
5. **方法必须可观测**：不观测隐藏推理，而观测路由、上下文、产物、校验、冲突与升级。
6. **规格变更必须传播**：不能继续采用“在文档末尾追加新内容”的方式。

## 建议的第一阶段工作（2—4 周）

- 把本地 Harness 映射到 PRSE 的八个通用对象；
- 跑通 package load、context resolve、capability route、artifact validate、event emit、human escalate；
- 使用召集台 reference pack 完成一次盲消费者实验；
- 建立最小方法健康面板；
- 记录哪些规则帮助了结果、哪些规则只增加了仪式成本。

## 建议的团队分工

- Method Steward：维护宪法、对象与质量门；
- Runtime Integrator：负责 Harness Adapter；
- Spec Architect：维护项目规范节点、对象与闭环；
- Assurance Lead：维护 Validator 与升级政策；
- Observability Lead：维护方法事件与指标；
- Reference Project Owner：以召集台持续验证方法；
- External Language Owner：维护规范到界面/市场语言的编译。

这些是 concern 所有权，不是固定职位。一个人或 Agent 可承担多个 concern，但高风险 Producer 与 Reviewer 应隔离。

## 不要马上做的事

- 不要先建设一个庞大的 Web 管理后台；
- 不要为所有方法对象设计数据库；
- 不要把所有知识包一次性塞入 Agent；
- 不要把 Agent 数量当作专业度；
- 不要急着宣布 v1.0；
- 不要为了“结构完整”保留实际没有价值的流程。

## 第一个真正的成功判据

不是“包能跑起来”，而是：

> 一个不了解历史的 Agent，通过包生成的召集台理解和 UI 骨架，显著少于不使用 PRSE 的误读；当它做错时，我们能定位是渠道、能力、规则还是产品本身的问题。
