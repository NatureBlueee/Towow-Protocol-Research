# 关键修正：过去哪些设定被挑战

## 1. “执行级约束就是规格” → 错

规格首先要规定产品语义、对象、闭环、边界和机制准入；技术选型与自动化是后续实现研究。

## 2. “一条总状态机可以解释产品” → 不足

宏观阶段可以帮助用户理解，但 Disclosure、Verification、Acceptance、Settlement 等对象必须有自己的生命周期。

## 3. “能力卡/意图卡是对象” → 不准确

Card 是 UI 容器。CapabilityClaim、Intent、Opportunity、Offer、Case 才是领域语义。

## 4. “事件账本承载一切” → 过载

DomainEvent、AuditRecord、Evidence、ActivityProjection 必须分离。

## 5. “验证通过就是验收完成” → 高风险错误

验证回答证据和判据；接受决定回答谁让结果在业务上作数。

## 6. “Agent 不需要身份” → 表述不完整

Agent 不应靠持久身份承重，但执行身份、委托、权限和动作必须可归因。

## 7. “默认对等披露” → 过强

正当场景存在不对称。更稳定的默认是最小必要、目的限定、条件化授权、可撤销/过期与可追责。

## 8. “五个一级空间、六个页面是长期架构” → 过早锁死

长期稳定的是用户目的地、主对象和页面语法，不是某一次导航和页面数。

## 9. “旧原型要么继续改、要么丢掉” → 假二选一

正确方法是 Clean-room 原型与设计考古双轨运行，再做有理由的延迟继承。

## 10. “多个专家角色能保证专业” → 不足

专业能力由 concern、知识、Skill、工具、证据标准、Scope、Authority 和历史表现共同定义。

## 11. “必须 100 个 Agent” → 通常不是高质量规范

应先规定覆盖、独立性、证据多样性、停止条件和验收；实例数量通常由 Harness 决定。

## 12. “更完整的 Word 就能解决交接” → 不够

AI 原生规格需要稳定 ID、依赖、Scope、版本、来源、Supersession 和机器可执行测试。
