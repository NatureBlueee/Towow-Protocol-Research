# 研究状态与成果边界

本文是第二轮研究的工程论文，与理论论文《从搜索到行动构成》共同构成一个版本化 Design IR/Engineering IR。它不把合成实验写成生产证明，也不把参考实现写成已安全部署的协议。

| 标记 | 含义 |
|---|---|
| **[F] 已验证事实** | 来自代码测试、可复现实验、正式规范或已证明定理 |
| **[I] 有据推断** | 有明确证据链但尚未完成目标现实验证 |
| **[H] 待验证假设** | 可被真实试点、攻击或对照实验推翻 |
| **[U] 未知** | 尚无足够证据，不以设计语言伪装解决 |
| **[D] 设计建议** | 当前最合理的协议/工程选择，不等于标准已冻结 |

> **[F] 当前实现范围。** 本轮参考引擎包含 Pydantic 协议对象、哈希链事件存储、凸多面体本地边界预言机、切平面协调器、隐藏贡献模式列生成、Delegation 检查、Commitment 编译和内存平台 TrustAdapter。当前核心测试 3 项通过；实验脚本可重复生成四组结果。它没有实现安全多方计算、生产身份、真实电子签、跨节点共识、隐私证明、法律合同自动化或开放网络抗女巫攻击。

# 从理论到工程：系统必须具备什么

理论论文把元问题定义为：行动语法、主体集合、角色、约束、效用和证据规则均可能尚未被共同构成。工程系统因此不能只提供“搜索 API”或“多 Agent 会话”，而必须具备六种能力：

1. **本地世界保持主权**：完整上下文、策略和隐性知识优先留在主体/Agent 的信任域；
2. **共同语法可演化**：Coordination IR 是版本化对象，允许在反例出现时 Redesign；
3. **候选空间可生成**：模型提出新角色、新组合和新机制，不只重排已有卡片；
4. **边界可交互发现**：主体按当前候选返回 cut、column、witness、unknown 或 refuse；
5. **认领与权威独立**：模型生成不能静默成为主体意图或义务；
6. **结果可闭合**：承诺、执行、证据、验证、接受、结算和争议各自有对象和事件。

A2A v1.0 可承载跨 Agent 消息与任务，MCP 可连接工具和资源；本引擎位于其上，定义“共同动作如何形成并作数”的协调语义。[@a2a10; @mcp2025]

# 总体架构

![社会生产中的完整分层：开放协议、主权节点、共享协调运行时、信任适配器和编译世界。](../figures/production_stack.png){#fig:stack width=96%}

系统分为五个平面。

## 主权节点平面（Sovereign Context Node）

每个主体维护一个本地节点，可运行在个人设备、企业内网、云端私有环境或受托平台租户中。它包含：

- **Context Compiler**：把文档、数据库、关系和历史编译为任务局部信念；
- **Local Belief Store**：区分事实、推断、争议、未知和失效知识；
- **Semantic Oracle**：解释共同语法在本地主体世界中的含义；
- **Boundary Oracle**：返回可行性、切割和证据；
- **Column Oracle**：发现尚未公开但对当前对偶价格有价值的贡献模式；
- **Policy & Disclosure Engine**：决定哪些内容可因何目的被披露；
- **Delegation Wallet**：保存 AgentExecution 可做什么、对什么对象、在何期限内有效；
- **Local Audit Log**：记录本地判断和对外投影的来源。

## 共享协调平面（Coordination Medium / Runtime）

共享平面不拥有主体完整真相，而维护：

- Coordination Space；
- Coordination Schema / IR；
- 候选 Arrangement 与分叉；
- Patch、Stance、Probe；
- Cut、Column、Witness 和 Finding；
- 生成器与验证器状态；
- 主问题求解器；
- 事件账本与物化投影；
- 人类认领与审批队列。

## 概率语义平面

大模型或模型群负责：

- 从模糊张力提出暂定 Problem IR；
- 生成/修订 Coordination Schema；
- 提出候选 Arrangement；
- 翻译本地反例；
- 生成探问；
- 解释为什么某个候选被阻断；
- 形成面向不同主体的最小上下文。

模型层可替换，系统不绑定某一家模型。DeepSeek-V3 的稀疏 MoE 和高效训练、Kimi K2.5 的多模态 Agent Swarm 都说明模型在并行探索和工具执行上的上限仍在移动。[@deepseekv3; @kimi25]

## 权威与保证平面

确定性或严格受证据约束的内核负责：

- 身份与主体映射；
- Delegation；
- 资源预留；
- 目的限定披露；
- 不变量；
- 承诺生命周期；
- 幂等与并发控制；
- 验证规则版本；
- 接受者与责任边界；
- 争议路由。

## 外部执行与信任平面

通过 TrustAdapter、A2A Adapter、MCP Adapter 和领域 Adapter 接入：

- 平台实名/企业认证；
- 电子签；
- 支付、托管、保证金和保险；
- Wowok 或同类链上确定性约束；
- ERP、CRM、代码仓库、生产系统；
- 第三方验证与仲裁；
- 法律和监管接口。

Wowok 在系统中的位置是 `TrustAdapter` 的一种实现，不是 Coordination IR 或生成引擎的替代品。

# 协议对象：什么可以存在，什么可以作数

## 最小对象模型

| 对象 | 语义 | 是否可由模型单独创建 | 是否可产生外部义务 |
|---|---|---:|---:|
| Principal | 承担权利、责任或后果的主体 | 否，需身份来源 | 间接 |
| AgentExecution | 某次具体 Agent 运行 | 是，但需绑定 Principal | 否 |
| Delegation | 主体授予执行的能力、对象、期限和约束 | 否，需权威来源 | 允许后续动作 |
| Claim | 带来源、状态、概率、用途和期限的主张 | 是 | 否 |
| CoordinationSchema | 角色、任务、资源、约束和结果的版本语法 | 是候选，需评审/冻结 | 否 |
| Arrangement | 某版本共同动作的候选实例 | 是候选 | 否 |
| Patch / Fork | 对候选的局部修改或分叉 | 是 | 否 |
| Stance | 主体对局部条件的支持/反对/条件接受/未知 | Agent 可建议，主体可确认 | 不直接 |
| ConstraintCut | 某候选违反本地边界的反例 | 本地预言机可出 | 阻断 |
| ContributionColumn | 本地可提供的隐藏贡献模式 | 本地预言机可出 | 否 |
| Recognition | 主体认领某候选版本 | 否，需主体/有效预授权 | 打开承诺编译 |
| Commitment | 债务人对债权人的有向社会承诺 | 编译生成，需 Delegation/签署 | 是 |
| Evidence | 对执行或结果的可回查材料 | Agent/系统/人可出 | 否 |
| VerificationResult | 证据是否满足某版本判据 | 验证器可出 | 不等于业务接受 |
| Acceptance | 有权主体让结果在业务上作数 | 否，需权威 | 是 |
| Settlement / Dispute | 关闭、补偿或进入争议 | TrustAdapter/有权主体 | 是 |

这一对象分离继承了社会承诺研究的基本洞察：开放多 Agent 系统更适合用 debtor-creditor、条件、期限和生命周期表达规范关系，而不是把内部心理状态当成协议真相。[@singh1999; @cupid2015; @tosca2017; @clouseau2020]

## 规范生命周期

![候选可能性必须经过认领、委托、承诺和证据门，才成为可结算的社会事实。](../figures/normative_lifecycle.png){#fig:lifecycle width=93%}

标准路径为：

```text
Tension / Problem IR
→ Schema candidate
→ Arrangement draft
→ local cuts / columns / patches / probes
→ candidate
→ principal recognition
→ commitment compilation
→ reserve / sign / activate
→ perform / attest
→ verify
→ accept or dispute

```

任何“模型已经讨论一致”的状态都不能跳过 `recognize → compile → sign/activate`。

# Coordination IR：共享世界的编译目标

## 为什么需要 IR

自然语言适合发现和解释，不适合独立承担并发控制、版本、权威和验证。固定业务 Schema 又无法承载开放世界的新对象。Coordination IR 应处于二者之间：

- 对模型足够可读和可生成；
- 对算法足够结构化；
- 对人足够可解释；
- 对版本和事件足够稳定；
- 对领域适配足够开放。

# 核心算法 I：语义构成与反例修复

## 语义构成循环

输入通常不是完整需求，而是碎片化张力 $T_0$。模型生成候选语法：

$$
\Gamma_0\sim q_\phi(\Gamma\mid T_0,domain,history).
$$

各主体本地节点对语法进行解释与反驳：

$$
c_i^t=Oracle_i^{semantic}(\Gamma_t,W_i).
$$

若反例指出缺少角色、条件或区分，模型修订：

$$
\Gamma_{t+1}=Repair_\phi(\Gamma_t,\{c_i^t\},design\ history).
$$

直到：

- 在当前任务范围内没有阻断性语义反例；
- 达到预算；
- Owner 决定冻结；
- 或确认现阶段无法形成可用语法。

这不是让模型自行宣称“设计完成”。语法冻结必须有证据、适用范围、已知缺口和反例历史。PRSE/Flowness 的 Problem → Design → Engineering 分层在这里直接成为运行协议。[@flowness01; @prse03]

## CEGIS 式候选修复

```python
def constitute(space, sovereign_nodes, budget):
    findings = []
    schema = llm.propose_schema(space.problem, findings)
    for _ in range(budget.schema_rounds):
        counterexamples = [n.review_schema(schema) for n in sovereign_nodes]
        hard = [c for c in counterexamples if c.blocks]
        if not hard:
            break
        findings.extend(hard)
        schema = llm.revise_schema(schema, hard)

    candidates = []
    for _ in range(budget.arrangement_rounds):
        arrangement = llm.propose_arrangement(schema, space.state, findings)
        local = [n.assess(arrangement) for n in sovereign_nodes]
        deterministic = validators.check(arrangement)
        hard = blocking(local, deterministic)
        if not hard:
            candidates.append(arrangement)
        else:
            findings.extend(hard)
    return diverse_rank(candidates), findings
```

LLM 可以解释反例，但不能删除有权验证器返回的阻断状态。CEGIS 的价值不是让模型“永不犯错”，而是把错误转化成可积累的结构化反例。[@cegis2006]

# 核心算法 II：主权边界预言机与 Benders 式切割

## 线性凸子问题

设共享决策 $z$ 由协调主问题选择，主体 $i$ 的私有变量 $x_i$ 和约束不公开：

$$
Q_i(z)=
\max_{x_i}
\quad c_i^\top x_i
$$

满足：

$$
A_i x_i+B_i z\le b_i.
$$

若子问题不可行，可由 Farkas 证书或分离预言机返回对 $z$ 有效的 feasibility cut：

$$
\alpha_i^\top z\le\beta_i.
$$

若可行且需要优化，可返回 optimality cut：

$$
\theta_i\le \pi_i^\top(b_i-B_i z).
$$

主问题加入切割后重新提案。Benders 分解的基本思想正是把连接变量留在主问题，私有/局部变量留在子问题。[@benders1962]

## 协议化 OracleAssessment

```json
{
  "principal_id": "prn_...",
  "candidate_version": 12,
  "status": "separate",
  "cut": {
    "relation": "<=",
    "coefficients": [0.0, 1.0, 0.4],
    "rhs": 1.2,
    "scope": "capacity",
    "confidence": 1.0,
    "witness": {"violation": 0.27}
  },
  "explanation": "当前并行交付量超过已授权能力边界",
  "disclosure_policy_ref": "pol_..."

```

现实非线性/非凸预言机可以返回非线性规则、no-good cut、反例对象或只能由模型解释的 Finding。协议必须区分：

- mathematically valid cut；
- empirically estimated boundary；
- model-suggested objection；
- human refusal。

它们不能统一标成同等强度的“约束”。

# 核心算法 III：隐藏贡献模式与列生成

## 为什么 Profile 不等于能力空间

一个主体可以公开“我会软件开发”，但针对某个特殊安排，他可能组合出“代码审查 + 供应商对接 + 一周驻场”的局部模式。这个模式不是静态 Profile 中的一项标签，而是受当前价格、目标和条件激发的列。

令主体 $i$ 的潜在贡献模式集合为 $\mathcal M_i$。每个模式 $m$ 有能力向量 $a_{im}$ 和成本 $c_{im}$。主问题的对偶价格为 $\pi$，主体本地求解 pricing problem：

$$
m_i^*=\arg\min_{m\in\mathcal M_i}
\left(c_{im}-\pi^\top a_{im}+\mu_i\right).
$$

若 reduced cost：

$$
\bar c_{im_i^*}<0,
$$

主体只披露这个当前有价值的模式，而不是全部私有能力组合。Dantzig-Wolfe 分解把局部极点/活动作为列提交给协调主问题，提供了可解释的算法原型。[@dantzigwolfe1960]

> **[D] 模型作用。** 现实中的 $\mathcal M_i$ 不是预先枚举的。LLM 在本地根据主体世界和对偶价格生成若干候选模式，再由确定性资源/权限/时间验证器过滤，形成 `ColumnOracle`。

# 核心算法 IV：净协调价值信息（ECVI）

传统 VOI 询问“哪个问题最能改善单个决策”。协调场景还要考虑：一个问题可能改变参与主体、语法、信任机制或验证规则。因此定义：

$$
ECVI(q)=
\mathbb E_{Y_q}
\left[
\max_{\mathcal C\in\mathcal F(Y_q)}W(\mathcal C)
\right]
-
\max_{\mathcal C\in\mathcal F}W(\mathcal C)
-C_{privacy}(q)
-C_{latency}(q)
-C_{attention}(q)
-C_{strategic}(q).
$$

其中 $C_{strategic}$ 表示回答可能让对方反向推断、操纵或先占机会的成本。系统只在 $ECVI(q)>0$ 且拥有披露权限时探问。

候选问题可来自：

- 判断某条 cut 是否真实硬约束；
- 确认某个主体是否能担任新角色；
- 请求一份最小证据；
- 询问是否存在更便宜的本地模式；
- 询问主体是否愿意在某个条件下认领；
- 询问需要哪种 TrustAdapter 才能解锁合作。

> **[H]** ECVI 能否在真实开放任务中比启发式探问显著减少隐私和人类注意力成本，仍需真实对照实验。它本身依赖模型对后验价值的估计，可能系统性低估难以量化的价值。

# 核心算法 V：概率语义、风险门与完整中介

## 选择性执行

对候选动作 $a$，模型和本地节点估计关键主张失败概率：

$$
\widehat R(a)=
\sum_{c\in Claims(a)}
\widehat P(c=false\mid E_c)\cdot Impact(a,c)
+R_{execution}(a).
$$

动作只有在以下条件同时成立时进入执行：

$$
Execute(a)
\iff
\widehat R(a)\le\delta_a
\land Authority(a)=valid
\land Invariants(a)=pass
\land Lifecycle(a)=allowed.
$$

风险门可用 isotonic calibration、共形风险控制、语义熵或领域后验，但必须报告覆盖率。低错误率若来自 0.1% 覆盖，不等于系统有生产价值。[@farquhar2024; @angelopoulos2021; @angelopoulos2022]

## 完整中介

```{=latex}
\begin{theorem}[完整中介的不变量保护]
设外部状态为 $S$，安全不变量为 $I(S)$。所有外部命令 $c$ 均只能经过验证器 $V(S,c)$，且验证器可靠地满足：若 $I(S)$ 且 $V(S,c)=1$，则 $I(\delta(S,c))$。若不存在旁路，则任意随机模型生成的候选序列都不能通过已接受命令到达违反 $I$ 的状态。
\end{theorem}
```

这一定理不保证验证器表达了现实中的所有伤害，也不保证实现没有旁路。它只精确说明：随机模型不会神秘地穿透一个正确且完整的确定性门。验证器的正确性、范围、证据和审计本身必须被治理。

# 核心算法 VI：认领、承诺与外部 TrustAdapter

## Recognition 不是按钮文案

Recognition 是主体把某个具体 Arrangement 版本声明为“愿意进入后续承诺编译”的规范事件。它必须包含：

- principal；
- arrangement_id + version；
- recognized scope；
- excluded/conditional parts；
- delegation source；
- expiry；
- signature or authenticated act；
- whether further human confirmation is required。

Recognition 不等于合同成立，也不等于结果被接受。

## Commitment 编译

承诺对象：

$$
C=(debtor,creditor,performance,preconditions,evidenceRule,
 deadline,remedy,jurisdiction,signatures,state).
$$

只有在：

1. Arrangement 为 recognized；
2. debtor 的 AgentExecution 有有效 Delegation；
3. performance 在授权范围；
4. 必要资源可预留；
5. TrustAdapter 能提供所需身份/签署/救济；

时才进入 `proposed/active`。

## TrustAdapter 接口

```python
class TrustAdapter(Protocol):
    def identify(principal_id) -> IdentityResult: ...
    def reserve(commitment, asset, amount) -> Reservation: ...
    def sign(commitment, principal_id) -> Signature: ...
    def activate(commitment) -> Commitment: ...
    def verify(commitment, evidence) -> VerificationResult: ...
    def settle(commitment, verification) -> Commitment: ...
    def dispute(commitment, reason) -> DisputeCase: ...
```

Wowok、链上合约、电子签平台、托管支付、企业合同系统或人工仲裁都可以实现这个接口。生成式协调不研究它们内部如何达成确定性；它只要求能力与结果可映射为统一语义。

# 国内与国际双配置

## 统一语义，不统一信用底座

技术签名只能证明某个密钥做过某事，不自动证明它有权代表某公司，也不自动证明自然语言交付已完成。系统必须区分：

- cryptographic authenticity；
- principal identity；
- delegation validity；
- contractual effect；
- evidence sufficiency；
- remedy enforceability。

## 中国优先配置

国内 P0 更适合：

- 平台实名/企业认证；
- 企业内部账号与组织权限；
- 合规电子签；
- 里程碑支付、托管、保证金、发票；
- 行业监管和人工仲裁；
- 私有部署、最小出域和审计日志。

《中华人民共和国电子签名法》为符合条件的可靠电子签名提供与手写签名或盖章同等法律效力的基本框架，但具体代表权限、合同内容、证据链和司法域仍需专业审查。[@prcesign2019] 国内不应要求普通用户先学习区块链，也不应把质押设为所有关系的默认机制。

## 国际联邦配置

国际版本可以组合：

- A2A Agent Card 与签名元数据；
- OAuth/capability；
- DID 与 Verifiable Credentials；
- 跨域审计；
- 支付/托管；
- 仲裁或链上合约。

DID 和 VC 提供可携带标识与凭证数据模型，但不替代实际授权和救济。[@did2022; @vc2025; @uncitral2001]

# 分布式状态：草稿能合并，承诺不能随意合并

Coordination IR 的草稿修改可以使用 CRDT 或事件分叉：添加一个风险、一个证据链接、一个候选角色通常可以交换、幂等地合并。[@crdt2011]

但以下动作涉及稀缺资源和唯一后果：

- 同一预算被两个承诺同时预留；
- 唯一交付席位被重复认领；
- 同一数据授权超范围使用；
- 付款/数字资产重复消费；
- 同一生产对象被冲突写入。

这些操作必须使用串行化预留、共识、锁/租约、幂等键或业务等价机制。

第二轮并发模拟中，两个请求都先读取余额再写入的 eventual check-then-write 模式产生约 60.46% 超额承诺；串行预留为 0%。这不是对所有数据库的一般性能结论，而是证明“最终一致性足以管理承诺资源”这一想法在最简单并发模型中已经失败。

## 兼容四动词，但不再由四动词承担全部本体

旧 `emit / quest / disclose / crystallize` 可以保留为高层 SDK façade：

- `emit` → 发布 Claim、Projection、Column 或 Event；
- `quest` → 创建 Probe/OracleQuery；
- `disclose` → 依据 DisclosureGrant 返回材料或边界；
- `crystallize` → 创建/推进 Arrangement candidate。

但协议底层必须暴露更细对象，尤其不能把“生成候选、主体认领、承诺成立、验证完成”都藏在 `crystallize` 里。

# 可观测性与“编译世界”

这套引擎最终不能只以日志 API 存在。它需要一个可操作的编译世界，至少显示：

- 当前共同语法与版本；
- 候选 Arrangement 的结构、分叉和差异；
- 哪个主体/Agent 代表谁；
- 已知、争议和未知；
- 哪些路径被本地边界阻断，但不泄露完整私有原因；
- 哪些问题有正 ECVI；
- 哪些主体已认领、哪些只是模型推测；
- 承诺、资源预留和证据状态；
- 失败 Finding 应回流到 Problem、Design、Engineering、Execution 还是 Verification。

游戏式界面不是装饰。它把开放世界中的对象、区域、边界、可达状态和阻塞原因转化为人能够快速理解和操作的空间语法。它也是协议的调试器、尽调材料和真实 Demo。

# 第二轮实验设计

## 实验 A：静态投影与任务自适应边界

### 目的

验证在受控凸世界中，是否可以在不公开全部私有约束的情况下，通过边界 cut 获得与完整披露相同的可行最优解。

### 设置

- 300 个随机实例；
- 5 个主权主体；
- 8 个共享决策维度；
- 每个主体 18 条私有线性约束，总计 90 条；
- 静态基线每个主体随机公开 1/2/4/8 条；
- 自适应方法从相同公开约束开始，候选违反时返回一条最严重边界；
- 完整披露为 oracle upper baseline。

### 结果

| 方法 | 真可行率 | 平均目标比 | 披露约束中位数 | 平均轮次 |
|---|---:|---:|---:|---:|
| Static-1 | 0.000 | - | 5 | 1.00 |
| Adaptive-1 | 1.000 | 1.000 | 22 | 5.40 |
| Static-2 | 0.000 | - | 10 | 1.00 |
| Adaptive-2 | 1.000 | 1.000 | 25 | 5.04 |
| Static-4 | 0.000 | - | 20 | 1.00 |
| Adaptive-4 | 1.000 | 1.000 | 31 | 4.26 |
| Static-8 | 0.000 | - | 40 | 1.00 |
| Adaptive-8 | 1.000 | 1.000 | 46 | 3.30 |
| Full disclosure | 1.000 | 1.000 | 90 | 1.00 |

![在该合成设置中，静态随机局部画像不能保证真实可行；边界预言机在较少披露下收敛到完整解。](../figures/boundary_feasibility.png){#fig:boundary width=92%}

![可行率与披露约束数量的机制权衡。](../figures/boundary_disclosure_tradeoff.png){#fig:boundarytrade width=88%}

> **[F] 对本实验成立。** 精确线性预言机 + 切平面能够恢复完整披露的最优解，并平均只披露一部分边界。

> **[U] 现实外推未知。** 现实约束非凸、语义化且 Oracle 会犯错；静态基线被故意设置为随机外近似，因此结果不能直接解释成“所有 Profile 搜索都会 0% 可行”。

## 实验 B：开放贡献模式与列生成

### 目的

验证固定公开 Profile 是否会漏掉只有在当前任务和对偶价格下才显现的组合能力。

### 设置

- 300 个实例；
- 24 个主体；
- 12 类能力；
- 每个主体一个公开低带宽模式和 1-3 个私有模式；
- 每个任务植入由 4 个隐藏模式构成的互补结构；
- 最大团队规模 6；
- 比较公开 Profile、随机披露 20%、价格引导本地 Oracle、完整披露。

### 结果

| 方法 | 可行安排率 | 相对完整最优成本 | 披露模式中位数 | 平均轮次 |
|---|---:|---:|---:|---:|
| Public Profile Search | 0.020 | 2.638（仅可行样本） | 24 | 1.00 |
| Random 20% disclosure | 0.913 | 1.816 | 34 | 1.00 |
| Price-guided local oracle | 1.000 | 1.00035 | 53 | 3.70 |
| Full private disclosure | 1.000 | 1.000 | 75 | 1.00 |

![固定公开画像与开放列生成在合成高阶互补任务中的可行安排率。](../figures/team_feasibility.png){#fig:team width=90%}

> **[F] 对本实验成立。** 对偶价格引导的本地 Oracle 在不披露全部模式时恢复近乎最优团队。

> **[H] 待现实验证。** LLM 能否在真实主体上下文中根据“影子价格/缺口”稳定生成有价值的新贡献模式，是通爻引擎最关键的模型实验之一。

## 实验 C：概率门与分布漂移

### 设置

- 16,000 校准样本，16,000 同分布测试，16,000 漂移测试；
- 构造过度自信概率模型；
- isotonic calibration；
- 目标失败风险 5%；
- 比较无门、固定校准门、带随机审计的自适应门。

### 结果

| 方法 | 分布 | 覆盖率 | 执行后错误率 |
|---|---|---:|---:|
| Unguarded | 同分布 | 1.000 | 0.5603 |
| Calibrated fixed gate | 同分布 | 0.0300 | 0.0479 |
| Unguarded | 漂移 | 1.000 | 0.6683 |
| Calibrated fixed gate | 漂移 | 0.0235 | 0.0612 |
| Audited adaptive gate | 漂移 | 0.0000 | 未执行 |

![概率可被风险门管理，但在严重漂移下，可靠策略可能只能 fail closed。](../figures/probability_shift.png){#fig:risk width=90%}

这个结果支持一种更谨慎的说法：模型只要优于随机，就可能在“覆盖率-风险”曲线上提供价值；但一旦分布不受控，保证可能通过降低覆盖甚至停机来维持。系统必须把“拒绝执行”当成正常结果，而不是可用性故障。

## 实验 D：并发信任与资源预留

### 设置

100,000 次双请求并发模拟，余额固定 100，每个请求独立读取余额并申请 10-100 的随机金额。

### 结果

| 方法 | 超额承诺率 |
|---|---:|
| eventual check-then-write | 0.60461 |
| serializable reservation | 0.00000 |

> **[F] 对该并发模型成立。** 草稿可以最终一致，资源承诺不能只靠最终一致性检查。TrustAdapter 必须提供原子预留或等价强度机制。

# 如何评价实验，而不是被实验骗到

四组实验的价值是“构造性可行性”：它们分别证明某个结构在一个明确世界类中可以工作。它们不证明：

- 真实人的私有世界是多面体；
- LLM Oracle 精确；
- 公开 Profile 的现实可行率只有 2%；
- 所有协调都需列生成；
- 5% 风险门可迁移到业务损失；
- 平台事务即可解决法律双花。

下一轮应把证据阶梯分为：

1. 数学单元世界；
2. 合成 Agent 世界；
3. 历史案例反事实重放；
4. 人类在环沙盒；
5. 影子生产；
6. 低风险真实执行；
7. 高风险受监管执行。

任何阶段失败都应回流到正确层，不得为了“保住协议”把执行失败重写成文案问题。

# 工程路线与停止条件

## R0：研究参考实现（当前）

目标：对象分离、边界/列生成机制、委托与信任接口成立。

停止条件：核心代码可运行、实验可复现、限制清楚。当前基本达到，但不等于协议成熟。

## R1：单组织主权节点 Dogfood

- 把 Flowness Harness 作为首个本地节点；
- 一个真实项目进入 Coordination Space；
- 本地完整上下文不出域；
- 编译世界显示候选、cut、unknown、recognition；
- 承诺只限内部低风险任务。

Gate：至少 20 个真实长任务，能够重放每次安排如何被边界修改；未授权外部效果为 0；人类能够解释最终结构。

## R2：两主体平台信任试点

- 两个独立 Actor/组织；
- A2A 或 API 交换 Oracle 消息；
- 平台身份与电子签/托管 Adapter；
- 人类显式认领；
- 真实小额里程碑结算。

Gate：与人工协调对照；净注意力、披露成本和履约质量至少一项显著改善，且无新增高后果风险。

## R3：多主体开放列生成

- 三方以上互补安排；
- 隐藏贡献模式；
- 反事实探索；
- TrustAdapter 可替换；
- 真实分布漂移和攻击测试。

Gate：固定搜索基线无法替代；生成的新安排有真实认领和履约，而不是只被评价“很有创意”。

## R4：联邦与开放协议

- 独立实现者；
- 可导出 Coordination IR；
- 跨域 Delegation/VC；
- 分布式事件和撤销；
- 女巫/串谋/垃圾提案治理。

Gate：至少两个独立实现通过一致性套件，互相交换 arrangement/commitment 而无语义分叉。

# 真实社会生产中的最终形态

用户要求回答：这个成果最终应以软件、协议、SDK、合约还是网页服务存在？研究结论是：**任何单一形态都不完整。** 最合理的是一个分层产品族，但只有一个语义核心。

## 1. 开放协议规范：Coordination IR + Event Semantics

它定义：

- Principal、AgentExecution、Delegation；
- Schema、Arrangement、Patch、Stance；
- Oracle query/response；
- Recognition、Commitment；
- Evidence、Verification、Acceptance、Settlement、Dispute；
- 版本、幂等、权限和保证语言。

这是互操作和长期壁垒的语义层。

## 2. 主权节点 SDK

供个人 Agent、企业 Harness 或第三方 Agent 平台接入：

- 本地 Context Compiler；
- Boundary/Column Oracle；
- Disclosure Policy；
- Delegation Wallet；
- 本地审计与模型适配。

这是“完整上下文不必集中”的工程条件。

## 3. 共享协调运行时

可以是托管 SaaS，也可以私有部署：

- Coordination Space；
- Model Swarm；
- Master Solver；
- Counterexample Ledger；
- Event Store；
- Context Compiler；
- Risk/Authority Gates；
- Observability。

这是近期最可能形成收入和融资认知的核心软件。

## 4. TrustAdapter 生态

Wowok、平台信用、电子签、托管支付、保险、链上合约、仲裁和企业系统各自实现适配器。通爻不垄断所有信任技术，而是让它们可以被生成式协调统一调用。

## 5. 编译世界 / 游戏式交互面

它不是营销外壳，而是：

- 协调对象编辑器；
- 世界状态与边界可视化；
- 人类认领和审批界面；
- 协议调试器；
- 真实 Demo；
- 投资人和用户能够理解系统的入口。

## 6. 一致性、模拟与红队套件

- 协议 conformance tests；
- 合成主体和 Oracle 模拟器；
- 机制比较；
- 故障注入；
- 盲实现测试；
- 法律/领域 Adapter 测试。

因此最终形态可以概括为：

> **开放社会语义协议 + 主权节点 SDK + 可私有部署的协调运行时 + 外部信任适配器 + 编译世界界面 + 证明与一致性套件。**

网页服务只是其中一种部署；智能合约只是外部信任接口的一种；SDK 只是主权节点入口；协议规范提供跨产品的长期连续性。

# 结论

边界预言机生成式协调引擎不是一个“更复杂的 Agent 匹配器”。它把开放世界协作拆成可治理的构成过程：模型产生语法与候选，本地节点保留主权世界并返回边界和贡献模式，算法逐步求解共同可行域，主体明确认领，权威内核编译承诺，外部信任设施将其变成可执行和可救济的现实。

第二轮的工程结论可以压缩为一句话：

> **不要把每个主体先压成一个中心可搜索的点；让主体保留自己的“体”，按具体共同动作返回必要的“边”，再由共享协调介质把这些边编译成一个能够被认领和履约的世界。**

这条路线允许今天从中心化、私有部署和人类在环开始，也允许未来接入更强模型、开放 A2A 网络和多种外部信任基础设施。它不承诺一次性完美发现所有机会，而是提供一个更强、也更诚实的目标：让机会、条件和共同动作能够在不完整理解中被持续生成、反驳、修订、认领和验证。
