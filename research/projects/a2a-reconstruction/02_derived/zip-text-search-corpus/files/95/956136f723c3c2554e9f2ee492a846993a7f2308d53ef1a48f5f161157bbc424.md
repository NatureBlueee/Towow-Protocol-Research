# Relation Schema（关系模式）操作化规范 v0.5

## 0. 目的

“关系语法”曾经是一个解释力很强、但容易包住一切的词。本规范把它收敛成一个有限、版本化、任务相关、可比较、可编译和可重开的机器对象，并明确回答：

- 什么变化算关系模式变化；
- 什么只是实例参数变化；
- 什么变化需要重新形成；
- 怎样判断某个局部已经稳定；
- 怎样把稳定部分编译为实际运行机制；
- 哪些判断必须由相称权威而不是自动分类器完成。

---

## 1. 定义

关系模式：

```text
Γ = <R, V, T, A, E, D, O>
```

### `R`：Roles, topology and affected-party representation

定义参与角色、必要性、互斥/组合关系和受影响者位置。例如：预算批准者、数据权威、服务交付者、目标域验收者、仅受影响但无签署权的第三方。

### `V`：Vocabulary

定义对象、主张、动作、条件、资源和错误类型。它规定“什么能被说成一个协议内对象”，而不是规定具体值。

### `T`：Transitions, challenge and recovery

定义当前状态允许的动作、目标状态、恢复、撤回、取消、争议、补偿和重开。它给出一类合法的类型化执行轨迹。

### `A`：Authority, standing and jurisdiction semantics

定义每一类 material action、stance、witness 和 override 由哪个 Authority Locus 产生，Mandate 如何引用、何时失效、能否再委托。

### `E`：Evidence, source qualification and effect semantics

定义不同 Assertion 允许的证据，副作用由哪个目标世界证明，freshness、独立性、复现和 Defeater 如何处理。

### `D`：Data semantics

定义披露、用途、组合、派生、保留、训练、再传递、撤销和删除语义。它不要求每次数据操作都变成顶层对象，但必须使需要审计的区别可表达。

### `O`：Outcome and scoped-settlement semantics

定义 `COMMIT / REJECT / CONDITIONAL / DEFER_UNKNOWN / WITHDRAWN / DISPUTED / REOPEN`、Domain Adoption、Principal Acceptance 和稳定处置的判定。

## 2. 模式与实例

一个具体关系为：

```text
RelationInstance = <Γ_version, x, state, references>
```

`x` 包含：

- 具体参与者和 Entity 引用；
- 价格、数量、日期和地域；
- 当前资源和数据集；
- 当前候选、条件和风险值；
- 当前 Mandate/Assertion/Commitment/Operation 引用。

### 2.1 参数变化

若变化只改变 `x`，并且：

- 新值仍属于既有类型和值域；
- 不改变合法动作和状态轨迹；
- 不改变谁有权决定；
- 不改变什么证据算数；
- 不改变数据和接受语义；
- 不触发既有模式中明示的 material threshold；

则为 `INSTANCE_PARAMETER_CHANGE`。

例：

- 预算从 5,000 调整为 8,000，仍在预算方已有授权额度内；
- 试点日期从 8 月 1 日改为 8 月 5 日，仍满足同一时窗规则；
- 数据样本从 1,000 条改为 800 条，仍属于相同只读、匿名化数据类。

### 2.2 非实质模式变化

改变了 `Γ` 的文本或元数据，但不改变当前任务相关的合法轨迹和效力语义，例如：

- label、说明文字或展示顺序；
- 只服务于不可达归档状态的可选动作；
- 当前任务族从未引用的观察者角色；
- 不影响 hash/语义的文档修订。

分类为 `NON_MATERIAL_SCHEMA_CHANGE`。它可以产生新版本，但不必重开当前关系。

### 2.3 实质模式变化

给定任务族 `F`、当前状态 `s`、时间窗 `H`、风险阈值 `ρ`，若变化改变以下任一项，则为 `MATERIAL_SCHEMA_CHANGE`：

```text
ReachableTypedTraces(Γ, F, s, H)
AuthorityValidity(trace)
EvidenceOrEffectValidity(trace)
DataRightOrDuty(trace)
OutcomeOrAcceptanceMeaning(trace)
RecoveryExitDisputePath(trace)
RoleIntegrity(trace)
```

换句话说，它改变了“可以发生什么”或“发生后怎样才作数”。

例：

- 增加法务批准作为数据访问必要条件；
- 允许服务方将试点数据用于训练；
- 将 Effect 见证从客户系统改成服务方日志；
- 将业务负责人 Acceptance 改成系统自动通过；
- 新增一种不可撤回的生产写入动作；
- 删除当前轨迹所需角色；
- 将失败后的补偿改为只能进入争议。

## 3. 形式判据

令 `L_F^H(Γ, s)` 表示在任务族 `F`、起始状态 `s`、时间窗 `H` 内可达的类型化轨迹集合。每条轨迹携带：

```text
trace = <states, actions, required_authorities,
         witness_rules, data_rules, outcome_rules>
```

定义任务相关语义等价：

```text
Γ1 ≡_(F,s,H,ρ) Γ2
```

当且仅当：

1. 两者可达轨迹在风险相关投影下相同；
2. 每条对应轨迹的必要权威相同或存在被相称主体认可的等价映射；
3. Evidence/Effect、数据和结果语义相同；
4. 退出、恢复、争议和第三方保护相同；
5. 差异不会改变超过 `ρ` 的损失、责任或不可逆性。

若实例变化但模式等价，则无需重新形成。若不等价，则至少重开受影响依赖闭包。

### 3.1 为什么不能只比较 JSON diff

同一个 JSON diff 可能：

- 只是重命名；
- 修改不可达分支；
- 改变当前可执行动作；
- 改变权威；
- 改变现实见证；
- 改变数据训练权。

因此 diff 只是候选变化，不是 materiality 结论。

### 3.2 为什么也不能只看状态机

两套模式可能有相同状态转移字符串，但：

- 承诺者不同；
- Effect 来源不同；
- 数据用途不同；
- Acceptance 主体不同；
- 某角色已经被删除；
- 同一动作在风险上从可逆变为不可逆。

所以轨迹签名必须包含 `A/E/D/O` 与角色完整性。

## 4. Materiality 决策流程

### Step 1：定位变化

按 `R/V/T/A/E/D/O` 分类，并列出实例字段变化。

### Step 2：计算当前可达依赖

从当前状态、已激活资源和角色出发，计算有限深度内的可达动作、状态和其语义引用。

### Step 3：类型化差异

对每个差异判断：

- 是否可达；
- 是否 material action；
- 是否改变必要 Authority；
- 是否改变 Witness/Effect；
- 是否改变数据权利；
- 是否改变 disposition/acceptance；
- 是否影响已存在 Commitment 或编译运行。

### Step 4：风险与权威门

自动分类器只输出：

```text
PARAMETER_CHANGE
NON_MATERIAL_SCHEMA_CHANGE
MATERIAL_SCHEMA_CHANGE
AMBIGUOUS_REQUIRES_AUTHORITY_REVIEW
```

以下情况必须升级人工/相称 Authority：

- 语义文本无法确定是否改变权利或义务；
- 风险阈值本身发生变化；
- 现有 Mandate 对修改权不明确；
- 变化涉及法律、监管或未建模第三方；
- 新动作不可逆；
- 多个 Authority Locus 对 materiality 有冲突。

### Step 5：生成 ReopenPlan

Material change 不是全局重启。输出：

```text
changed_components
invalidated_assertions
affected_commitments
affected_operations
required_new_stances
required_new_mandates
compiled_artifacts_to_suspend
unaffected_subgraph
```

## 5. 怎样判断模式稳定

稳定不是“没有人继续说话”，而是相对于一个任务族、风险窗和运行时限的工程判断。

### 5.1 局部稳定条件

一个子图 `G` 可以声明 `STABLE_FOR_COMPILE`，至少满足：

1. **语法闭合**：当前计划使用的角色、对象、动作和转移均已定义；
2. **权威闭合**：每个 material action 和 stance 有有效 Mandate/Authority 规则；
3. **认识闭合**：关键前提有相称 Assertion/Evidence，Unknown 未被伪装成事实；
4. **能力闭合**：必要能力和资源在当前环境、容量、恢复和有效期内得到支持；
5. **效力闭合**：每个副作用有目标世界 witness；
6. **接受闭合**：谁、在何时、根据什么作出 Acceptance 已定义；
7. **失败闭合**：取消、回滚、补偿、争议和 reopen 已定义；
8. **反例预算闭合**：在预先设定的 probe/挑战预算内没有未处理 material counterexample；
9. **变化监测**：已知 Defeater 有可观察触发器；
10. **版本认领**：所有必要 Authority Locus 对同一 content hash 作出范围化 stance。

### 5.2 稳定度不是单一分数

建议使用向量：

```text
Stability = <syntax, authority, evidence, capability,
             effect, acceptance, recovery, drift>
```

不同维度可以处于不同等级。系统只编译满足该动作风险要求的子图，不以平均分掩盖一个关键缺口。

### 5.3 稳定的时间边界

稳定声明必须写明：

```text
valid_for_task_family
valid_environment
valid_until / review_interval
risk_ceiling
known_defeaters
```

稳定不是永恒属性。

## 6. 怎样编译为实际运行机制

### 6.1 编译输入

- 精确 RelationVersion；
- 稳定子图；
- 当前有效 Mandate；
- 已获得 stance/commitment；
- Assertion 与 WitnessPolicy；
- rollback/compensation；
- Defeater 与监控；
- 数据用途与保留规则。

### 6.2 编译输出

可以是：

- 工作流状态机；
- 最小权限 token/credential；
- 队列与重试策略；
- 幂等键；
- Effect gateway；
- target-domain readback；
- 监控和 reopen hook；
- 可视化 Compiled World。

### 6.3 编译不变量

编译器必须满足：

```text
NoNewAuthority
NoNewObjective
NoNewCommitment
NoClaimStrengthening
NoEffectSelfCertification
NoDataRightExpansion
PreserveRefusalExitAndRecovery
PreserveProvenanceAndVersion
```

编译是语义保持的降复杂度，不是一个新的决策主体。

### 6.4 最小权限

每个运行凭证只覆盖：

```text
actor × action × object × purpose × amount/risk × time × precondition
```

模型、工具或执行器升级不得自动扩大该集合。

## 7. Reopen 规则

### 7.1 触发器

- Mandate 撤销/过期；
- 关键 Assertion 被 Defeater 推翻；
- 环境或工具版本越出 Capability scope；
- Effect readback 与预期不一致；
- 数据用途或法规改变；
- Acceptance 标准改变；
- 新参与者/受影响者进入；
- 重复运行出现超阈值漂移；
- 主体提出新的 material countercondition。

### 7.2 局部影响闭包

从触发节点沿以下边传播：

```text
supports
requires
authorized_by
witnesses
commits_to
compiled_into
derived_from
accepted_by
```

只暂停依赖触发节点的 Operation/Commitment；不相关的已验证子图继续有效。

### 7.3 Reopen 不是回滚历史

旧版本仍然是真实发生过的历史。重开只表示：旧版本不再足以授权未来动作或证明当前主张。

## 8. 示例

### 示例 A：价格变化

14 天只读 AI 试点从 5,000 元变为 6,500 元；预算 Mandate 上限为 10,000 元，其他规则不变。

结论：`INSTANCE_PARAMETER_CHANGE`。需要预算方对新实例值作 stance，但不必重建数据/技术 schema。

### 示例 B：允许训练

原规则禁止训练，服务方提出将匿名样本用于模型微调。

结论：`MATERIAL_SCHEMA_CHANGE`，因为 `D` 改变，并可能新增数据权威、派生权、删除和长期 Effect。必须重开数据和接受依赖闭包。

### 示例 C：新增不可达归档动作

在已经关闭、不会重新进入的 ARCHIVED 状态增加“附加说明”动作。

结论：通常是 `NON_MATERIAL_SCHEMA_CHANGE`。若法律保留义务要求该说明成为正式记录，则可能升级，需相称 Authority 判断。

### 示例 D：服务方日志替代客户 readback

运行结果由客户系统 readback 改成服务方自己的 stdout。

结论：`MATERIAL_SCHEMA_CHANGE`，因为 `E` 改变且可能把 Producer completion 冒充 target Effect。

### 示例 E：模型升级

执行器从模型 M1 换成 M2，动作、Mandate 和 Effect gate 不变。

结论：Entity/Instance 与 Capability 变化，未必是 Relation Schema 变化；但若 M2 新增动作或风险，使既有资格化不再充分，则触发 Capability reopen，而不是静默扩权。

`instrument/towow_fieldkit/towow_fieldkit/schema_change.py` 实现：

- 有界可达动作分析；
- 组件级 typed diff；
- materiality 分类；

## 10. 停止概念膨胀的约束

Relation Schema 只回答“哪类关系轨迹怎样有效”，不能替代：

- 具体事实和证据；
- 主体价值和真实偏好；
- 现实能力资格化；
- 法律解释；
- 经济净价值；
- 社会权力分析。

凡是不能改变 `R/V/T/A/E/D/O` 或 `L(Γ)` 的概念，不应被硬塞成 schema component。凡是可以用实例、事件、策略或派生视图表达的语义，不应因名称重要就升级为顶层对象。

## 11. v0.5 公开现实证据校准

### 11.1 新增规则组不新增维度

`standing_rules`、`jurisdiction_rules`、`challenge_rules`、`settlement_rules` 是 `R/A/T/O` 的可执行分组，不把 `Γ` 从七维扩张成十一维，也不新增 aggregate root。

### 11.2 默认 materiality

在最小通用 checker 中，上述四组规则发生变化默认判为 material。原因是其影响可能来自当前双边可达图之外，不能仅凭本地图证明无关。行业化实现可以提交一份 domain-specific irrelevance proof 将其降级。

### 11.3 Compile readiness 新门

关系实例可以声明：

```text
required_jurisdictions
covered_jurisdictions
required_external_standing
reviewed_external_standing
open_material_challenges
challenge_contingency_defined
challenge_horizon
```

缺少必要 jurisdiction 或 standing review 时为 `NOT_READY`；存在 material challenge 且无 contingency 时为 `NOT_READY`；若 challenge 已明确且具有暂停、补偿、升级和重新资格化机制，则可为 `READY_WITH_CONTINGENCY`。

### 11.4 Settlement scope

编译结果只能声称：

```text
Settled(RelationVersion, JurisdictionSet, StandingSet, ChallengeHorizon, EvidenceState)
```

不能把局部完成扩张为全局结清。

### 11.5 Formation delta

ReopenPlan 现在可以由 Expansion、Transformation 或 Protective contraction 触发；只产生 Epistemic clarification 时，默认不建立新的“形成成功”主张，但仍可建立新 Assertion 或 Assurance view。
