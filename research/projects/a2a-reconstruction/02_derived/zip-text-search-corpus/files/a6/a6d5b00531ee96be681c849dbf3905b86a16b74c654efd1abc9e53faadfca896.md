# Analysis

## Pre-formation holdout

The static profile asserted all three held-out operations were available because
the Docker client and `sandbox-exec` binaries existed. Under the current
seatbelt, all three assertions were false:

- Docker could not access its local Unix socket.
- A permissive `sandbox-exec` profile could not be applied.
- The canary-denial profile therefore could not enforce a child boundary.

The scoped Claim abstained (`Unknown`) on all three. This prevented false
assertions but had zero coverage; safe abstention is not a capability by itself.

## Formation intervention

Three exact, explicit approvals changed only the executor policy path:

- Docker daemon version query became reachable (`29.1.3`).
- A sandboxed `/usr/bin/true` child ran successfully.
- A child subject to a deny rule could not read a synthetic canary that the
  parent could read.

No binary was installed, no service was started, no task was weakened, and no
private data was disclosed. This is a direct action-space change rather than a
language rewrite.

## Theory consequence

A useful Capability Claim must bind at least:

```text
operation × executor/sandbox × authority/approval path ×
resource/service state × environment/version × evidence freshness
```

`docker installed` and `sandbox-exec present` are discovery facts, not
operational capabilities. Conversely, the default-scope failures did not prove
the machine could never perform the operations; they proved the current
execution configuration could not.

The result supports `Unknown → bounded probe → qualified Claim` and shows that
Authority is not merely normative metadata: in this environment it causally
changed the reachable action set.

## Limits

- The holdout count is three.
- Two cases use one underlying boundary mechanism.
- User/approval cost is counted as three gates but not monetized.
- The canary probe establishes one file-read denial, not a complete
  multi-principal security proof.
