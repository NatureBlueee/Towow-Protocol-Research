# Flowness Harness 认知工程与可靠交付体系 v0.1

本知识包沉淀了围绕 Flowness、Agent Harness、设计、工程方案、工程共识、计划执行、验证与持续演进的一整套研究。

它不是某一次升级的任务清单，也不是把若干最佳实践拼成一篇长文。它的目标是建立一套可继续研究、可实例化、可验证、可与外部资料汇合的工程知识体系。

## 核心命题

Harness 不是“让多个 Agent 自动写代码”的框架，而是一套把模糊意图逐层转化为可验证现实的认知—设计—工程—执行系统：

```text
委托与问题发现
  → 采访与需求建模
  → 设计
  → 工程方案
  → 工程共识
  → 计划编译
  → 执行
  → 独立审查与验证
  → 修复 / Replan / Re-engineer / Redesign / Re-interview
  → 运行证据与持续演进
```

## 阅读入口

1. `00-导航与使用说明.md`：本套文档如何使用、怎样继续合并资料。
2. `01-Harness认知工程总纲.md`：完整架构、阶段边界与核心原则。
3. `03-设计系统规范.md`：设计究竟是什么，以及如何系统地产生高质量设计。
4. `04-工程方案系统规范.md`：怎样把设计编译成可实现、可维护、可验证的工程系统。
5. `10-Flowness现状映射与升级路线.md`：现有 Flowness 已有什么、缺什么、下一轮应该做到哪里停止。
6. `ROADMAP.md`：可执行的分阶段建设路线。

## 文档状态标记

本文档体系使用四类内容标记：

- **已验证事实**：来自已查看的 Flowness 仓库代码、规范或运行记录。
- **有证据推断**：根据多个事实推导，但尚未通过完整运行实验确认。
- **设计建议**：建议未来采用的结构或机制，不伪装成当前能力。
- **开放问题**：目前没有足够证据或需要 Owner / 专家裁决的事项。

## 重要边界

本版本依据 2026-07-23 之前的对话、Flowness GitHub 仓库快照与公开行业资料整理。它没有读取服务器上当时的实时账本，也没有执行全量生产验证。因此，关于“当前是否已经真实启用”的结论必须在实施前重新用代码、账本和运行行为复核。
