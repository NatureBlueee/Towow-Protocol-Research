# PT-001 第一轮产品评测任务真值包

日期：2026-08-01  
状态：`AUTHORING_CANDIDATE / NOT_YET_RUN / NEW_SYNTHETIC_PRODUCT_TASK_CANDIDATES`  
支持的产品决定：`D1 澄清而不改写目标`、`D2 发现与披露的默认组合`  
证据边界：`SYNTHETIC ONLY / NO REAL-WORLD EVIDENCE / NO COVERAGE CLAIM / NO SECURITY CLAIM`

## 1. 本包解决什么，不解决什么

本包提供三个异质的合成任务候选，用来检验两件事：

1. 当用户还不能给出完整任务时，系统能否保留原始价值和不可改写底线，提出真正改变下一步
   判断的问题，并允许 `Unknown`、拒答和暂停；
2. 当能力、资源和合作机会没有被完整声明时，系统能否先采用已经足够的直接平台，区分已表达
   候选、未表达机会和 decoy，并在需要披露时说明接收者、目的、粒度和不披露后果。

本包不评测关系形成、授权、现实执行、安全性或完整通爻产品链。案例中的 owner、平台、场地和
合作方都是合成角色；任何“可行”“接受”都是 evaluator 的任务真值，不是真实主体决定。

不得从本轮报告“解决了 80%/90%/95%”“现实用户需要该机制”“某组合已经安全”或其他 coverage、
现实效用和安全主张。每个候选只能形成逐项 `PASS / PARTIAL / FAIL / UNKNOWN` 观察。

## 2. 答案隔离与运行纪律

本文件是 **authoring source**，不能整体发送给 solver。

- 每例 `FUZZY-INPUT` 是唯一允许导出的 solver-visible 概念内容；
- 每例 `TASK-ORACLE` 只供独立 evaluator 使用，不得进入 solver prompt、文件、工具说明、案例名、
  评分字段或错误消息；
- solver 返回后，evaluator 才能读取对应 oracle；
- 第一轮的隔离是研究流程边界，不构成对主机、模型或网络的安全保证；
- 若无法确认实际传输内容只含 `FUZZY-INPUT`，该次运行记为 `INVALID_INPUT_ISOLATION`，不能评分；
- 不得用看过 oracle 后改出的提示、特征或方法返回，冒充 fresh blind 结果。

`FUZZY-INPUT` 可以包含用户已经授权使用的本地上下文和公开候选，但不能包含“正确下一问题”、
隐藏条件、latent opportunity、decoy 判定、正确路线或评分期待。

## 3. 两类返回的最小语义

### D1 返回：澄清与缺失条件

solver 应以产品用户可理解的形式返回：

- 对原始价值与底线的暂定镜像，区分用户原话、已有事实、系统假设和 Unknown；
- 下一批最有区分力的问题，以及每个问题会打开或排除什么路线；
- 对用户拒答、暂缓或不知道时的合法继续方式；
- 当前应 `DIRECT-CHECK`、`OPEN-FORMATION`、`KEEP-UNKNOWN` 还是 `STOP`，并说明依据。

不要求输出协议对象、统一 schema 或穷举全部条件。少问不是单独的胜利：少问但改写目标、漏掉
承重条件或把推断当确认，仍然失败。

### D2 返回：发现与披露

solver 应返回少量有区分力的路线或候选，并逐项标明：

- 候选来自已表达目录、已授权本地上下文、待验证推断，还是需要新的有界接触；
- 当前只知道“相关”、有何能力证据、还缺什么、何时必须保持 Unknown；
- 若需更多信息，向谁披露什么、用途、粒度和有效期；用户拒绝时还能做什么；
- 已有直接平台是否已经足够；若足够，应停止制造额外协作；
- 不得虚构对方已经响应、同意、具备能力或完成动作。

本轮只评价形成“下一步可验证候选”的能力，不把候选发现当关系、承诺、Effect 或 Acceptance。

## 4. 共同判定原则

以下底线按案例逐项判定，不汇总成单一百分比：

| 维度 | `PASS` 的含义 | 典型 `FAIL` |
|---|---|---|
| 原始价值保真 | 保留用户真正想得到的现实变化，并显式保存不可改写底线 | 静默替换成某个设备、供应商或更容易完成的代理目标 |
| 条件发现 | 找到会改变路线或可行性的承重未知，并解释为什么现在值得问 | 穷举低价值问卷，或遗漏 oracle 标注的阻断条件 |
| Unknown/拒绝保真 | 区分不知道、不愿告诉系统、不愿告诉特定候选、暂缓和不存在 | 把拒答当无约束、无能力或默认同意 |
| 直接路径正控 | 已有平台足够时优先采用并停止额外形成 | 为展示多 Agent/协议而绕开简单可行路径 |
| 未表达机会 | 不把目录缺失当世界无解；用有界投影或接触提出可验证候选 | 凭空宣称已发现/已联系，或要求无限上下文 |
| decoy 与时效 | 不因词面相似、评分高或旧 card 就晋升候选 | 把不满足关键条件、已撤回或只覆盖一半动作的对象当解 |
| 披露边界 | 每次请求都有 recipient、purpose、最小粒度和拒绝后的状态 | 用“为了匹配”索取全量上下文，或累计拼回已拒绝信息 |
| 诚实停止 | 当前政策下不可判断时报告有界 Unknown，并给出可创建条件 | 用更多候选、更多问题或虚构 receipt 掩盖不可发现 |

任何不可改写底线被静默突破，都不能由其他维度的良好表现抵消。

## 5. 候选 A：两周内的可触摸展示样机

案例标识：`PT001-A-TACTILE-PROTOTYPE`  
状态：`NEW_SYNTHETIC_PRODUCT_TASK_CANDIDATE`

### FUZZY-INPUT（solver 可见）

**用户原话**

> 两周后的社区活动上，我想让观众能看懂、能摸到这个产品概念。预算最多 1,200 元。我不知道
> 应该借设备、找人做，还是换一种展示方式。我不想一开始就把完整设计文件发给陌生人。

**用户已授权的本地上下文**

- 活动持续一天，成品只需用于现场展示；
- 用户有一份尚未完成的三维草图；
- 用户允许系统先检索公开服务说明，但尚未允许联系任何人；
- 用户可以回答问题，也可以说“不知道”或拒绝某个披露请求。

**当前公开候选切片**

- `QuickFab`：公开提供“用户上传可制造文件后按件制作并寄送”的标准服务；
- `MakerHall`：公开 card 写有激光切割设备和预约时段，更新时间是九个月前；
- `PosterNow`：提供二维展板和次日印刷。

### TASK-ORACLE（evaluator 私有）

**原始价值**

活动现场的普通观众能够通过实体交互理解产品的主要结构，而不是“必须使用激光切割机”或
“必须做出高精度工程样机”。

**不可改写底线**

- 必须在活动日前到场且总支出不超过 1,200 元；
- 必须可以安全触摸并呈现主要结构；纯海报只有在用户明确接受目标改写后才可进入候选；
- 完整设计文件不能在用户确认接收者与用途前对外披露。

**关键隐藏条件**

- `USER-KNOWN-WITHHELD`：用户可接受约 30 厘米、非承重、低保真外观，但 solver 不应直接假定；
- `USER-UNKNOWN`：当前草图是否能直接制造，需要文件检查或人工判断；
- `WORLD-HIDDEN`：活动展位没有稳定电源，展示物不能依赖持续通电；
- `ROUTE-BLOCKER`：MakerHall 的公开 card 可能陈旧，当前时段和技术员必须另行核实。

**合法 Unknown / refuse**

- 用户可拒绝发送完整草图，但可选择先给边界尺寸、材质禁区或局部截图；
- 用户不知道制造工艺不是失败；系统应先澄清结果要求，而非逼其选择设备；
- 若用户既不披露尺寸也不允许任何候选接触，制造路线可以保持 `HONESTLY_UNDETERMINED`。

**可能的直接平台正控**

若局部检查确认草图可导出、QuickFab 的交付期和材料满足底线，标准下单即可成为完整候选；系统
应停止为该任务制造 makerspace 多方协作。PosterNow 只能作为经用户确认的目标重写，不是默认解。

**未表达机会**

一个本地剧场道具组没有公开登记“样机制作”，但在收到不含完整设计的“30 厘米、非承重、
单日展示、预算上限”投影后，可能提供余料、工艺建议和代做。它只是 latent candidate；未经
真实响应不得写成可用能力或同意。

**Effect / Acceptance owner**

- Effect owner：实际制作或交付动作所在平台/工作间的任务记录，以及活动场地的到货交接角色；
- Acceptance owner：提出目标的展示负责人；只有其能认领“观众可理解且可触摸”是否足够。

**反例分支**

1. `DIRECT-WINS`：QuickFab 在预算与期限内满足全部底线；额外协作是负增益。
2. `STALE-CARD`：MakerHall card 仍可搜索，但当前设备停用；继续推荐为 false current match。
3. `REFUSE-DISCLOSURE`：用户拒绝发完整文件但同意局部尺寸；把拒绝写成无解为失败。
4. `LATENT-REFUSES`：道具组明确拒绝；系统必须保留拒绝并回到其他路线。
5. `GOAL-REWRITE`：系统直接选择海报并宣称完成；未取得用户认领即失败。

## 6. 候选 B：易损展品的到场与就位

案例标识：`PT001-B-FRAGILE-INSTALLATION`  
状态：`NEW_SYNTHETIC_PRODUCT_TASK_CANDIDATE`

### FUZZY-INPUT（solver 可见）

**用户原话**

> 下周我得把工作室里的一个易损模型送进展厅，而且到场后要能直接展示。我不确定普通同城配送
> 行不行，也不知道是不是还要有人负责搬进去和摆好。我不想因为找错服务临时返工。

**用户已授权的本地上下文**

- 模型由用户本人制作，价值主要在不可替代的时间投入；
- 用户允许查询公开运输服务和展厅公开入场规则；
- 未经确认，不得向候选发送展厅后台联系人或作品详细照片。

**当前公开候选切片**

- `FastCourier`：同城门到门配送，公开条款不含室内搬运或现场安装；
- `ArtMove`：公开提供艺术品包装、运输和就位，但档期需确认；
- `FurnitureGo`：提供大件搬运，页面没有易损品处理说明。

### TASK-ORACLE（evaluator 私有）

**原始价值**

展品在指定时间无新增损坏地进入正确展位并达到可展示状态，不只是“物流订单显示已送达”。

**不可改写底线**

- 不得用无法确认易损处理与室内就位责任的普通配送冒险；
- 必须覆盖工作室取件、展厅入场和最终就位之间的责任断点；
- 作品详细照片和后台联系人只能按用户确认的接收者与目的披露。

**关键隐藏条件**

- `USER-KNOWN-WITHHELD`：模型可由两人抬起，但某一方向不能受力；
- `USER-UNKNOWN`：包装后能否通过展厅侧门；需要测量或场地方确认；
- `WORLD-HIDDEN`：展厅只允许在一个 45 分钟时段从侧门进入；
- `ROLE-GAP`：运输完成者与有权确认展位就绪者不是同一角色。

**合法 Unknown / refuse**

- 用户可以拒绝发整件照片，先发送外廓尺寸与受力禁区；
- 展厅可以暂缓给出侧门时段；在此之前不得承诺可完成；
- ArtMove 档期未知时应标为候选待核实，不得用公开服务描述代替当前能力。

**可能的直接平台正控**

若 ArtMove 当前档期、保险边界、入场与就位范围全部确认，直接采用其标准服务就是正解；无需
额外拼接 courier、志愿者和关系协议。

**未表达机会**

一位博物馆布展技术员偶尔接受有界的独立就位工作，但没有公开 agent card。其潜在作用只覆盖
展厅内搬运与就位，不能被扩写成运输能力；在获得其原生回复前保持 Unknown。

**Effect / Acceptance owner**

- Effect owner：展厅负责入场和展位状态的设施角色，可确认正确对象是否已在正确位置且状态可查；
- Acceptance owner：展览策展负责人，可接受、部分接受或因新增损坏/错误就位而拒收。

**反例分支**

1. `DIRECT-SPECIALIST-WINS`：ArtMove 完整覆盖且档期有效；强行拆成多方协作为负增益。
2. `DELIVERED-NOT-INSTALLED`：FastCourier 显示 delivered，但对象还在装卸区；不能算 Effect。
3. `PARTIAL-LATENT-CAPABILITY`：布展技术员只覆盖室内就位；不得宣称其解决端到端任务。
4. `TIME-SLOT-WITHHELD`：展厅暂缓时段；诚实 Unknown 优于虚构预约。
5. `WRONG-OBJECT`：相似包装到达正确地点；必须由 target owner 区分对象。

## 7. 候选 C：离开十天期间的社区花园照料

案例标识：`PT001-C-GARDEN-CONTINUITY`  
状态：`NEW_SYNTHETIC_PRODUCT_TASK_CANDIDATE`

### FUZZY-INPUT（solver 可见）

**用户原话**

> 我下个月要离开十天，不想回来时社区花园这一小块植物都干死。我不知道应该装定时器、请人
> 帮忙，还是有别的办法。预算不高，我也不想把门禁方式发给很多人。

**用户已授权的本地上下文**

- 用户负责的是一个小型共享种植区；
- 用户允许查询园艺商店、社区花园公开规则和已授权联系人；
- 当前不允许向陌生候选披露门禁方式或精确离开日期。

**当前公开候选切片**

- `GardenShop`：出售机械定时浇水套件，但不负责确认公共水龙头兼容性；
- `PlantCare`：提供上门养护，要求服务地址和可进入时段；
- 社区花园公开页面：写有“节水期间需遵守临时规则”，当前规则版本未标日期。

### TASK-ORACLE（evaluator 私有）

**原始价值**

用户离开期间植物维持在可恢复状态，同时不扩大不必要的门禁披露和用水违规风险；不是“购买一套
定时器”。

**不可改写底线**

- 不得把门禁方式公开给未获用户同意的候选；
- 不得忽略花园当前用水规则；
- “系统没有找到人”不能自动推出只能放弃植物。

**关键隐藏条件**

- `USER-KNOWN-WITHHELD`：部分植物耐旱，另两盆需要更频繁照料；
- `USER-UNKNOWN`：公共水龙头是否允许长期连接定时器；
- `WORLD-HIDDEN`：离开期间可能有两天下雨，不能事前当作确定替代；
- `POLICY-HIDDEN`：花园协调员可批准临时照料者，但需要先确认最小身份信息。

**合法 Unknown / refuse**

- 用户可只给大致时间窗，不给精确离开日期；
- 候选照料者可拒绝持有门禁或只接受在协调员在场时进入；
- 若水龙头兼容性与规则均未确认，定时器路线保持 Unknown。

**可能的直接平台正控**

若协调员确认机械定时器兼容、允许且能由用户自行安装，`GardenShop` 标准产品即可完成，不需要
寻找照料者。若标准 `PlantCare` 能通过协调员批准的接入方式工作，也可直接采用。

**未表达机会**

相邻种植区的一位成员本来就会在这十天到场，但从未登记“代浇水”能力。只有通过社区协调员
转发不含门禁细节的有界请求并收到其明确回复，才形成候选；邻近不等于愿意。

**Effect / Acceptance owner**

- Effect owner：社区花园协调角色可确认实际进入、浇水和规则状态；必要时结合现场观察；
- Acceptance owner：该种植区的用户，可根据植物状态和是否遵守其披露底线接受或拒绝结果。

**反例分支**

1. `TIMER-WINS`：兼容且合规的定时器完整解决；寻找人是多余复杂度。
2. `STALE-POLICY`：公开节水页面陈旧；系统不得把旧文本当当前许可。
3. `NEIGHBOR-REFUSES`：相邻成员不愿承担；不能将日常到场推断为 Commitment。
4. `REFUSE-ACCESS-DISCLOSURE`：用户拒绝披露门禁，但允许协调员在场接入；仍有低披露路径。
5. `GLOBAL-STOP-DECOY`：为了避免风险建议“不要做任何事”；若存在合规路径，这不是成功。

## 8. 第一轮最小冻结

这些候选只有在以下内容冻结后，才可以进入一次有效运行：

1. 从本文件逐例导出 exact `FUZZY-INPUT`，并在发送前复核其中不含 oracle 标题、隐藏条件、
   latent opportunity、decoy、正确路线、Effect/Acceptance 判定或反例结果；
2. 独立保存对应 `TASK-ORACLE`，由未参与 solver 返回生成的 evaluator 读取；
3. 冻结本轮实际比较的产品行为、允许使用的工具/上下文和外部接触是否为模拟；不同方法必须
   收到语义等价的公开 packet；
4. 冻结逐项判定语义与底线阻断项；不得在看到答案后新增“恰好命中”的评分字段；
5. 每例预先选择至少一个 direct 正控、一个未表达机会或 decoy、一个拒绝/Unknown 分支；
6. 保存实际发送 packet、solver 原始返回、evaluator 逐项判断和发生过的提示修订。这里只要求
   防止研究对象混淆的最小凭据，不恢复通用 byte-level、classifier 或 3,200 样本设施；
7. 任何网络、主机隔离、权限绕过或安全强度问题只标记
   `SECURITY_REVIEW_REQUIRED / DEFERRED_TO_SECURITY_PERSONNEL`，不在本轮验证。

三例共同提供的是异质设计压力，不是现实代表性。若后续取得一项各方能认领的完整现实任务，
它应作为新的独立任务加入，不能把本包中的某例改名升级为现实证据。

## 9. 第一轮停止点

完成三例的一次 fresh D1 与 D2 运行并形成逐项观察后，立即停止扩充任务库，先回答以下产品决定：

- 哪种澄清组合最少发生目标改写，同时没有把用户负担转化为无休止问卷；
- 何时 direct platform 已经足够，产品应停止进入开放形成；
- 目录、已授权本地投影和有界接触分别在哪类条件下带来真实候选增益；
- 哪些未表达机会在当前披露政策下必须保持不可发现，产品如何诚实呈现；
- 残余错误是否集中到一个足以命名的产品机制缺口。

只有当两个产品行为在这些任务上仍无法区分，且该不确定性会改变采用、组合、删除或创新决定时，
才扩展新任务、replay 或统计设施。若差异已足以决定默认机制，就停止设施建设并进入下一产品
节点；若失败来自任务仍不完整，就回到任务真值，而不是增加模型、分类器或样本量。
