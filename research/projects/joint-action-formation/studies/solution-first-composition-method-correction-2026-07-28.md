# 解决问题优先：组合现有技术本身就是通爻成果

日期：2026-07-28  
状态：`USER_CORRECTION / ADOPTED_RESEARCH_DIRECTION`  
校正对象：
`research/projects/joint-action-formation/studies/existing-technology-first-2026-07-28.md`

## 一、这次具体错在哪里

上一版方向虽然写了“现有技术完整满足要求时直接采用”，但仍然保留了错误的价值评价：

- 把强中心、通用模型或现有组合完整解决问题描述为“关闭通爻主张”；
- 把 adapter、编排或组合方案描述为“通爻最多只是实现/集成方案”；
- 继续以“通爻是否有独立增量”为隐藏评价中心；
- 先列 RAG、目录、Agent Card 等熟悉组件，再把它们放进强基线，没有先证明它们与 V1/V2
  的具体环境、输入条件和目标相匹配；
- 把七条母线理解为七个单 Agent 研究任务，没有为每条母线建立自己的多 Agent 发现、构造、
  反例、任务验证和综合体系；
- 前期过早强调合同、规格和形式闭合，容易奖励形式正确、显而易见、但不增加解决能力的结果。

这些错误会使研究不断寻找“通爻特有部分”，而不是寻找、构造并沉淀原问题的最佳解决方案。

## 二、正确的价值函数

研究成功的判断只有一个中心：

> 是否针对 V1/V2 精确界定的问题与环境，找到了一种能解决问题、可准确复现、可复用、可迁移
> 并可在新任务中继续检验的方法。

因此以下都是同等重要的正向成果：

- 一个通用模型完整解决了问题；
- 一个强中心系统完整解决了问题；
- 一个成熟平台或现有协议完整解决了问题；
- 两个或多个现有技术通过新的条件化组合解决了问题；
- 一个 adapter、Router、编排方式或状态映射使原本分散的能力形成完整闭环；
- 只增加了很小的新机制，但使现有能力能够可靠复现、迁移和泛化；
- 某个边界明确的小机制只解决一项具体问题，但能稳定成为完整方案的一部分。

现有技术被采用后，不是“通爻价值为零”。它成为通爻解决方案的组成部分。被关闭的只能是
“还需要另造一个同能力的新机制”这一必要性，不能把已经找到的解从通爻方案中删除或贬值。

通爻协议可以全部或主要由成熟能力组成。协议成果可以体现在：

- 精确的问题分解；
- 各方法的适用条件与停止条件；
- 能力之间的组合与收敛方式；
- 状态、权威、证据和责任怎样贯通；
- 哪个机制在何时被调用；
- 怎样从任务结果判断方案成立、失败或需要换路；
- 怎样复现、复用、迁移和泛化整个解决方法。

原创性、独占性和新增机制数量都不是研究价值指标。

## 三、遇到一个现有或新技术时的严格处理逻辑

不能因为技术名称与某个局部词汇相似就把它放入方案。每项技术必须依次通过：

1. **重读原问题**：直接读取 V1/V2 的问题、目标环境、不变量、正例、移除失败和完整生命
   周期，不从“检索”“授权”“工作流”等表面词汇开始。
2. **冻结技术前提**：它要求什么输入已经存在？世界是否静态？Intent、能力、角色和关系
   是否已声明？信息能否集中？它的 authority root、更新机制、失败方式是什么？
3. **定位实际能力**：它确切改变哪个任务状态、解决哪个 failure、产生什么可读回结果；
   不能用产品说明中的“大词”代替。
4. **放回完整任务**：先单独测它解决多少，再与其他方法组合，测组合覆盖、冲突、重复事实、
   新失败和端到端闭环。
5. **比较多种组合**：允许 `A=90%`、`A+B=95%`、`A+B+C=93%`；新增组件可能提高覆盖，也
   可能因冲突、治理和错误传播降低结果。
6. **按结果吸收**：
   - 完整解决：作为通爻方案的正式组成直接采用；
   - 部分解决：保留其明确子能力并继续寻找组合；
   - 需要 adapter：adapter 与组合方法本身是正式成果；
   - 不适用或负贡献：从该任务路径移除，但不外推否定其原始作用域；
   - 仍有缺口：只有这时才探索最小新机制。
7. **检验复现与迁移**：不能只在研究者构造的同源任务中成立；需要独立任务、留出案例、
   变体、反例、组合消融和跨场景迁移。

这里的判别单位首先是“问题是否被解决”，其次才是单个机制身份。

## 四、RAG 判断为什么错

把 RAG 自动列为发现母线的主要方案或默认强基线，是没有先核对条件的想当然。

RAG 通常要求：

- 相关内容已经被表达为可索引材料；
- query 或检索目标已经足够显式；
- 索引能够跟上世界变化；
- 相关性可以由文档相似、结构检索或后续 rerank 表达。

而 V1/V2 的承重环境允许：

- Agent 的本地世界持续变化；
- 需求、能力、问题、角色、关系和合作方向尚未显式声明；
- 未来任务所需维度事前不能枚举；
- 局部世界不能被完整复制；
- SEEK/OFFER 方向、Unknown、拒绝披露和 authority status 不能由文本相关性推出。

在这些条件下，RAG 不能检索尚未表达、尚未投影或尚未形成的事实，也不能替 Agent 产生
任务相关的动态投影。它可能只在某个很窄的后置位置有用，例如：

- Intent 或任务已经形成后，读取显式文档；
- 在本地域内部帮助生成候选投影；
- 为已知资源提供说明或 provenance；
- 为 Context Compiler 提供可回源材料。

RAG 是否进入某条任务路径必须由任务和条件验证，不再默认进入发现基线。

## 五、Google ARD 的遗漏与方法错误

2026-06-17，Google 发布
[Agentic Resource Discovery（ARD）](https://developers.googleblog.com/announcing-the-agentic-resource-discovery-specification/)：
它通过组织域名下的 catalogs 和可联邦 registries，发布、发现和验证 agents、skills、MCP
servers、APIs 等资源。其
[正式规范](https://agenticresourcediscovery.org/)明确把 ARD 定位在调用之前：发现服务返回
匹配资源，之后由资源自己的原生协议执行；ARD 不是执行 runtime，也不是 A2A/MCP 的替代。

此前研究没有发现 ARD，不是“小漏项”，而是检索方法暴露了问题：

- 来源搜索由已有术语和旧标准列表驱动；
- 没有为七条母线分别运行持续的协议/论文/产品 horizon scan；
- 没有从 V1/V2 的问题条件生成开放检索问题；
- 没有安排独立 Agent 专门寻找“最新、最强、最可能使我们的路线变得多余”的方案；
- 研究合规和合同物化早于充分发现。

ARD 现在应作为“发现与边界”母线的重要候选方案研究，但不能因名称相关就预判其足够。至少
需要检验：

- catalog 是否要求能力已被显式声明；
- 动态本地世界怎样更新 catalog；
- 未声明 Intent 和未声明能力怎样进入发现；
- plain-language intent 查询能否保持 SEEK/OFFER、Unknown、拒绝和局部权威；
- 域名/信任 manifest 证明了谁的什么权威；
- ARD 发现结果与后续关系构成、能力兑现和 Acceptance 怎样连接。

同样，Google A2A、MCP、AP2、ARD 和其他协议都只是待判断的候选能力，不能因发布者、热度
或“标准”身份预设正确。

## 六、为什么“组件都有”仍不等于问题已经解决

“现有技术已经分别拥有检索、目录、协议、授权、工作流、签名、事务和监控能力”与“V1/V2
问题已经被端到端解决”是两个不同命题。但不能从市场上仍有困难反推一定需要新技术；必须逐项
检验以下可能性：

1. **前提没有形成**：目录、RAG、policy 和 workflow 往往要求 query、能力、角色、资源、
   authority 或流程已经显式表达；V1/V2 的困难可能正发生在这些输入尚未形成时。
2. **各自只解决局部切片**：ARD 负责 invocation 前的发现，A2A/MCP 负责通信或调用，IAM
   负责特定 authority root 下的授权，事务/workflow 负责既定系统内执行；任何单项都没有承诺
   跨主体的完整任务生命周期。
3. **接口之间没有语义闭包**：discovery result 不自动成为 capability，capability 不自动
   成为 reliance，policy allow 不自动成为 Commitment，operation success 不自动成为目标
   Effect 或 Principal Acceptance。组件都存在时，错误可能集中在这些“不蕴含”的交界处。
4. **事实与权威分散**：不同主体只掌握自己的局部状态、private context、撤销权和验收权。
   一个中心若没有获得这些事实或权威，强模型也只能猜；若它能合法获得并完整解决，则中心
   方案应直接采用。
5. **世界持续变化**：静态 catalog、历史 receipt、旧合同和旧模型可能在 key、环境、目标、
   主体意愿或关系变化后失效。已有组件若缺少跨组件失效传播，单项正确仍会组合出 stale action。
6. **组合本身尚未被设计或验证**：组织拥有全部零件，不等于有统一 truth owner、状态转换、
   bytes binding、恢复和验收闭环。把成熟零件正确串联、收敛并消除重复事实，就是正式研究和
   工程成果。
7. **成本、激励和采用阻止落地**：完整披露可能侵犯隐私，精细验证可能吞噬任务价值，多方
   可能不愿接入同一平台，维护者可能停更，格式和 trust root 可能不可迁移。技术上可行但净值
   为负，也不算解决。
8. **问题可能已在局部分布被解决，只是没有被复现**：人类经纪、强平台、专用集成或内部制度
   可能已经解决某些场景。研究必须寻找这些正例并重建其条件，不能把“我们没看到”写成
   “世界上没有”。

因此后续不能用“他们都有，为什么没解决”作为新机制存在性的修辞证明。它是一个待分解的
诊断问题：

> 是组件能力不足、前提缺失、接口断裂、authority 不可集中、动态失效、组合未建立、净值
> 不成立，还是其实已有局部解但没有被识别和迁移？

每个实际任务都要允许最后一种答案。若现有组合已经完整解决，研究成果就是把它的条件、连接、
停止规则、失败恢复和复现方法准确沉淀下来；只有在同分母任务上仍有可观察残余时，才进入
adapter 或新机制研究。

## 七、七条母线各自必须拥有多 Agent 研究体系

七条母线不是交给七个单 Agent 各写一份报告。每条母线都应形成自己的研究单元，至少包含
异质职责：

1. **问题重建 Agent**：反复读取 V1/V2、历史正例、失败和漂移，防止表面词汇替代原问题；
2. **开放发现 Agent**：跨标准、论文、开源实现、产品和邻近学科寻找可用方案，尤其寻找能
   使当前路线不再必要的方案；
3. **建设性求解 Agent**：组合已有能力，提出新结构、算法、adapter、Router 或最小机制；
4. **反例/攻击 Agent**：寻找条件错配、显而易见结论、同源真值、不可迁移和负组合效应；
5. **任务与实验 Agent**：把方案放进实际任务、模拟和独立变体，定义可观察结果；
6. **线内综合 Agent**：保留冲突，形成当前最佳方案、未解问题和下一轮高价值分支。

具体 Agent 数量可随问题调整，但不能把一个 Agent 的单一路径当作一条母线的研究。
七条母线还要在各自提交之后进行跨线综合，不能在前期被同一答案污染。

## 八、研究必须由实际任务持续牵引

理论、模拟和机制研究不能脱离任务自我循环。下一轮首先建立实际任务组合，而不是先建立漂亮
本体。任务可以先使用公开材料、历史真实任务的去标识重建和高保真模拟，不要求立即招募真人，
但必须来自现实可识别的问题结构。

每个任务冻结：

- 原始需求与不可接受底线；
- 环境、参与主体和信息状态；
- 什么算解决，不只是什么算输出；
- 七条母线各自承担或不承担什么；
- 每个方法单独和组合后的覆盖率、错误、失败与新负担；
- 留出变体和迁移任务。

结果需要允许：

| 方法 | 任务要求覆盖 | 端到端成功 | 关键遗漏 | 组合负担 |
|---|---:|---:|---|---|
| A | 90% | 待测 | 某项边界 | 低 |
| A+B | 95% | 待测 | 某项状态 | 中 |
| A+B+C | 93% | 待测 | 新冲突 | 高 |

百分比不能主观填写。要求集合、权重、成功判据和裁决方式必须在看到结果前冻结，并同时保存
未加权逐项结果。组合的目标是解决任务，不是假定组件越多越好。

除了完整端到端方案，也鼓励产生边界犀利的小机制、小系统和小网络：只要它准确解决一个
具体问题，能够复现并可接入更大方案，就是重要成果。

## 九、前期研究如何避免“形式正确但没有价值”

前期采用发现优先，而不是规格优先：

1. 先从 V1/V2、实际任务、异常、失败和最新外部方案重开问题；
2. 同时生成多个竞争性问题解释和解决路径；
3. 奖励发现新变量、新组合、新机制、新反例和更简单的完整解；
4. 只有当一个区别已经显示会改变任务结果时，才把它正式化为对象、合同或 schema；
5. 合同、哈希、治理和自动校验只保护已经值得保留的研究对象，不能成为发现工作的主产出；
6. 对“一看就知道成立”的结果，必须继续追问它使我们获得了什么此前没有的解决能力；没有
   新能力则归入常识、背景或 CI，不作为主要研究成果；
7. 每一轮都要主动记录本轮错误、错误来源、触发信号和下一轮防复发机制。

## 十、本次错误的防复发门

下一轮启动前必须检查：

- 目标是否仍然是解决 V1/V2 的问题，而不是寻找通爻独立增量；
- `ADOPT / COMPOSE` 是否被明确登记为通爻正向方案成果；
- 是否先理解技术前提，再决定 RAG、A2A、ARD 或任何技术是否进入方案；
- 每条母线是否具有线内多 Agent 研究体系，而不是一个 Agent/一份报告；
- 是否有实际任务组合、逐项要求和可复现评分；
- 是否奖励建设性新方案与组合，而不只奖励反驳和合规；
- 是否列出前期已知错误以及本轮为什么不会重复；
- 是否允许组合方案完整解决后直接成为最终方案，不再强求新机制。

这份校正不预设哪种现有技术最终有效。它校正的是：现有技术或组合一旦解决原问题，就是通爻
协议自身的成功，而不是通爻价值的消失。
