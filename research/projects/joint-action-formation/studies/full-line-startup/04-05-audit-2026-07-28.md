## 04：CAPABILITY_REALIZATION

### 当前真实状态

五项历史能力不是同一证据状态：

| capability | 当前审计状态 | 仍缺的现实证据 |
|---|---|---|
| `CAP-CAP-001` 环境索引能力 | `PRESERVED / HIGH` | 跨环境、账户、版本迁移的样本仍少 |
| `CAP-CAP-002` 前瞻 holdout | `PARTIAL / MEDIUM` | 当前系统未把 prospective holdout 强制为高风险 claim 的 Gate |
| `CAP-CAP-003` 独立 readback | `PRESERVED / HIGH` | 本地技术域证据不能外推商业履约 |
| `CAP-CAP-004` 恢复与有效期 | `TRANSFORMED / HIGH` | 跨关系 expiry、漂移与恢复 readback 不完整 |
| `CAP-CAP-005` 组合容量资格化 | `PARTIAL / MEDIUM` | 跨伙伴组合、共享稀缺资源与版本漂移未现实验证 |

因此这条母线不是“没有研究”，而是已经有一个有信息量的负结果与两个结构缺口：前瞻预测
仍不可靠，组合容量尚未闭合。

### V2 scoped question

> 在冻结 operation、executor、source/environment version、account/approval path、
> resource state、oracle、expiry 与 recovery 后，一个派生 Capability Claim 能否比
> “静态声明 + 标准 eval/CI + IAM + health/readiness + telemetry”这一最强现成组合，更准确
> 地预测未见任务的首次执行结果、漂移后失效和恢复；若不能，它是否只应是现成信号的派生
> 视图而非独立机制？

这条问题保护的是“发现了组件”与“当前可依赖地兑现指定 operation”的差异，不研究能力
如何产生，也不从 capability 推出 authority。

### 现成方案 disposition

建议：`EXTEND_EXISTING_STACK`，不是 `GAP_CONFIRMED`。

一手材料确认这些构件分别覆盖部分问题：

- [Kubernetes probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/) 明确区分
  startup、liveness 和 readiness：分别控制启动检查、失败重启和是否接收流量；官方也警告
  错误 liveness probe 会造成级联故障。它证明成熟平台已有生命周期 probe，但不预测任意
  held-out operation、账户权限、源码 provenance 或目标域后置状态；
- [SLSA provenance](https://slsa.dev/spec/v1.2/provenance) 定义可验证的 artifact
  来源、时间与产生方式；它能关闭部分 source/version 缺口，不证明 artifact 在当前
  executor、resource 和 policy 下可执行；
- [OpenTelemetry](https://opentelemetry.io/docs/) 提供 traces、metrics、logs 的生成、
  收集和导出；其 metrics 是运行时测量，traces 是请求路径，logs 是事件记录。它改善
  observability 与历史证据，不自动给出未来 task readiness；
- [GitHub deployment environments](https://docs.github.com/en/actions/concepts/workflows-and-actions/deployment-environments)
  可以要求 approval、限制 branch、运行 deployment protection rule，并在 Gate 通过后才
  向 job 提供 secrets；这是现成人工 Gate 强基线，不等于目标域 Effect 或一般能力；
- IAM/policy、task eval/CI、resource scheduler、workflow/retry/compensation 仍分别承担
  允许、测试、容量和恢复的一部分，必须作为组合基线而不是弱化对照。

它们没有天然合并为对一个精确 operation 的前瞻性保证，但通爻也没有证据说明必须新增一套
正式能力事实。更保守的当前设计是：

> 权威事实仍由 source/version、policy decision、reservation、operation、target readback
> 和 recovery event 分别拥有；Capability Claim 与 Assurance Case 是带 freshness 的派生
> 视图。

因此缺口比“没有能力协议”更窄：是否值得保留一个跨这些来源、带 freshness 和 Defeater 的
前瞻派生视图，以及这个视图能否在未见任务上减少错误，而不是只把成熟平台信号重新包装。

### 最强反例

> 一个成熟平台把版本锁定、CI/holdout、IAM dry-run、resource quota/reservation、
> readiness probe、canary、SLO、target readback 和 rollback 组合起来；它不引入
> Capability Claim 新对象，却以更低治理成本达到相同或更好的首次预测、漂移阻断与恢复。

如果这条组合基线获胜，`CAP-CAP-001/003/004` 的现实差异仍需保留，但应由 adapter 与派生
查询重建；CRA 不应被登记为第二个正式现实。

另一个反例是安全 abstention：全部返回 `Unknown` 可以消除 false-capability，却没有覆盖率
和行动能力，不能算更好的能力机制。

### 最小判别门

建议冻结 `E-CAP-01-PROSPECTIVE-REALIZATION`：

1. 在任何 probe 或修复前冻结不少于两个 task family 的 held-out operations；至少包含：
   错误 source provenance、权限/approval 差异、resource contention、dependency/version
   drift、revocation 和 recovery；
2. 三个比较臂获得相同 task 与首次执行机会：
   - `STATIC`：安装状态、自报与历史成功；
   - `MATURE-COMPOSITE`：eval/CI + IAM + readiness/health + telemetry + workflow；
   - `DERIVED-CLAIM`：精确绑定 operation、environment、authority、resource、freshness、
     oracle、expiry、recovery 与 Defeater；
3. claim 必须在首次尝试前 seal；修复后的成功单独登记为 intervention；
4. oracle 使用 action-level executor result、authoritative postcondition 和独立 readback，
   不接受 producer 文本或外层 exit code 闭合；
5. 同时报出 coverage、first-attempt accuracy、false-capability、false-incapability、
   abstention、probe/人工成本、漂移检测延迟与恢复正确率；
6. 增加组合容量冲突：两个单点 claim 竞争同一资源，只有真实 reservation 成功的一条允许
   晋升为可承诺路径。

最低晋升标准不应沿用小样本的随意多数。运行前必须冻结样本数、置信区间和最小实质差异。
若 `DERIVED-CLAIM` 只复述成熟组合、没有减少任何 held-out 错误，则对象身份降级；若仅
reservation 带来增益，则增益归 `Reservation Gate`，不能归整个 CRA。

### 建议 V2 target / claim / hypothesis

- 建议 ID：`LINE-04-CAPABILITY-REALIZATION-V2`
- target：`EXISTING_SOLUTION_COMPOSITION`
- scoped claim：`SC-CAP-PROSPECTIVE-REALIZATION`
- hypothesis：`E-CAP-01-PROSPECTIVE-REALIZATION`
- capability scope：`CAP-CAP-001`—`CAP-CAP-005`
- 建议状态：`ACTIVE`
- 启动边界：先做本地 manifest、冻结 holdout、基线实现与 drift/revocation/recovery
  replay；没有独立任务或足够样本时只返回 `NOT_RUN/INSUFFICIENT_INPUT`，不得把 harness
  工具绿灯登记为能力成立。

### 不可影响主张

无论正负，本线不能改变：

- Principal 或 Agent 是否有权执行；
- Commitment、Effect、Adoption、Acceptance、Settlement；
- PFE 是否形成新能力或新路径；
- 某个模型、Agent 或组织的一般能力；
- 联邦、中心或通爻整体的现实净价值。

本线结果最多更新“冻结条件下对指定 operation 的前瞻兑现主张”。

## 05：AUTHORITY_NORMS

### 当前真实状态

历史五项能力中，`CAP-AUTH-001`—`004` 在能力矩阵中均为
`PRESERVED / HIGH`；`CAP-AUTH-005 Standing` 为 `PARTIAL / MEDIUM`。这说明表示和设计
谱系保存得较好，不说明真实 Principal 能理解、维护或认领这些对象。

当前最承重的未知不是“系统能不能再写一个 Mandate JSON”，而是：

1. 成熟 access-control、delegation、credential 与 approval stack 是否已经无损覆盖所需
   决策；
2. 若没有，差异来自跨关系语义，还是只是现有 policy 没配置好；
3. 显式 Mandate 是否能被真实 Principal explain-back、修订和撤销，而不制造更高认知成本；
4. 没有最终签字权的受影响方怎样被发现并取得 challenge/recourse，而不冒充签字权。

### V2 scoped question

> 在同一 authenticated Entity 和相同执行能力下，成熟的 RBAC/ABAC/ReBAC + scoped token/
> credential + approval workflow + audit log，能否无损阻止角色串联、purpose/data-use
> 越界、旧版本 stance 继承、撤销后执行和伪 Acceptance；若不能，最小缺失状态究竟是
> versioned Mandate、RelationVersion/Stance、Standing，还是一个 adapter 约束？

这条问题刻意不问“Mandate 是否听起来更完整”，而问它是否改变实际 permit/deny/escalate/
challenge/revoke 决策。

### 现成方案 disposition

建议：`ADAPTER_FIRST / EXTEND`，不是 `NEW_AUTHORITY_ONTOLOGY`。

本轮一手核验把现成覆盖收得更实：

- [NIST RBAC](https://csrc.nist.gov/Projects/Role-Based-Access-Control) 已标准化
  user、role、permission、operation、object、角色层级与 separation of duty；这直接覆盖
  大量“同一 Entity 内不同角色不能互相代行”的基础需求；
- [NIST SP 800-162 ABAC](https://csrc.nist.gov/pubs/sp/800/162/upd2/final) 用主体、
  对象、动作和环境属性作访问决定；目的、风险、时间或数据用途只要成为可靠属性，就不是
  Mandate 独有表达；
- [Cedar](https://docs.cedarpolicy.com/auth/authorization.html) 把请求明确表示为
  principal、action、resource、context，采用 default deny、permit/forbid 合成和诊断；
  [OPA](https://www.openpolicyagent.org/docs) 接收任意结构化输入并将 policy decision
  与 enforcement 解耦。Cedar 同时明确要求应用提供全部相关 entity、context 与 policy，
  因而它不会自动发现正确 Principal、Authority Locus 或缺失受影响方；
- [Google Zanzibar 原论文](https://research.google/pubs/zanzibar-googles-consistent-global-authorization-system/)
  已证明统一关系数据模型和配置语言可以在大规模服务上存储并评价 ACL，且对 ACL 与对象
  变化保持因果顺序；[OpenFGA](https://openfga.dev/docs/concepts) 将 authorization model
  与 relationship tuples 作为正式输入，并支持 model version、contextual tuples 与
  ReBAC 查询。这是 `RelationVersion/Authority graph` 必须面对的强反例；
- [RFC 9396](https://www.rfc-editor.org/info/rfc9396/) 的
  `authorization_details` 可用 JSON 表达细粒度授权，官方支付示例已包含金额、币种、
  creditor 与 account；所以“scope 太粗，Mandate 才能表达金额/对手方”不再成立；
- [RFC 8693](https://www.rfc-editor.org/info/rfc8693/) 明确覆盖 security token 的
  impersonation 与 delegation；[Macaroons 原论文](https://research.google/pubs/macaroons-cookies-with-contextual-caveats-for-decentralized-authorization-in-the-cloud/)
  用 chained MAC 与 caveats 支持可衰减的分布式委托，并可限制何时、何地、由谁、为何目的
  使用。范围、期限、目的与再委托也不是 Mandate 的独有能力；
- [W3C VC 2.0](https://www.w3.org/TR/vc-data-model-2.0/) 定义 issuer、holder、
  verifier 与防篡改 claims 交换；规范明确指出 credential 可验证不等于其中 claim 的真值
  已被评价，因此它不能替代业务真相、当前授权充分性或 Acceptance；
- [GitHub deployment environments](https://docs.github.com/en/actions/concepts/workflows-and-actions/deployment-environments)
  是一个现成 approval/enforcement 例子：保护规则通过前 job 不进入 runner、secrets 不
  交付。人工 Gate 不是通爻特有机制。

这些构件已经覆盖 `CAP-AUTH-001/002` 的大部分 enforcement substrate。通爻可能保留的
差异只应是它们没有共同拥有、且不能由一个清楚 adapter 重建的关系语义，例如：

- Stance 对精确 `RelationVersion/content hash` 的引用与 material-change 失效；
- authority locus 与 capability/technical account 的分离；
- purpose、data derivative、counterparty、budget、redelegation 与 acceptance authority
  的联合闭包；
- 无签字权受影响方的 challenge/representation/recourse Standing；
- Commitment 与实际 Reservation 分离。

如果成熟 policy + workflow + contract/audit 组合能无损表达这些差异，应直接采用，不保留
第二套竞争的正式授权现实。

一手核验后的残余缺口主要不在 access decision 的表达力，而在：谁负责产生并认领 policy
所需事实；material relation change 如何使旧 Stance 失效；第三方 Standing 如何被发现；
Commitment/Reservation/Effect/Acceptance 如何不被一次 `Allow` 吞并；以及真实 Principal
能否以可接受成本理解和维护这些边界。

### 最强反例

> 一个普通企业 IAM/IGA 系统用 RBAC + ABAC/ReBAC、短期 scoped token、审批工作流、合同
> 版本、resource reservation 和 append-only audit，在不引入 Mandate、Authority Locus、
> Stance、Standing 新对象的情况下，正确处理全部测试；使用者也更容易理解和维护。

若它在同一 action、版本、撤销、第三方 challenge 与认知成本条件下不劣，新增规范对象应
合并为 policy schema、workflow state 或 adapter。

第二个强反例是 object-capability 路线：若可衰减、可委托、带 caveat 的 capability 已经
把对象、动作、期限、对手方与再委托限制编码并强制执行，那么 Mandate 不能仅靠“范围化、
可撤销”证明独立价值。它必须在目标/目的、RelationVersion、原生认领、Standing 或
Acceptance 上产生额外判别。

### 最小判别门

建议冻结 `E-AUTH-01-ADAPTER-SUFFICIENCY`，先做 expressivity/enforcement，不把真人接受
混入同一次运行：

1. 构造一个 authenticated Entity 内能力完全相同的多个角色与 Authority Locus：
   日程、预算、数据、安全、品牌和最终 Acceptance；
2. 冻结至少以下 adversarial transitions：
   - 合法技术 token，但目的或数据用途越界；
   - 日程角色试图签品牌/预算承诺；
   - `v2 no-training` stance 被错误套到 material-change `v3 training`；
   - Mandate/token 撤销与并发 in-flight operation；
   - Commitment 存在但 reservation 失败；
   - 无签字权受影响方提出 material data-use challenge；
   - 同一模型换账户、同一账户换模型，授权结论不应随 capability 漂移；
3. 公平比较：
   - `MATURE-STACK`：RBAC/ABAC/ReBAC + scoped delegation + approval + contract/version +
     reservation + audit；
   - `MANDATE-ADAPTER`：相同底层 stack，增加最小 AuthorityLocus/Mandate/
     RelationVersion/Stance/Standing 映射；
4. 预注册每步 `PERMIT / DENY / REQUIRE_APPROVAL / STALE_VERSION / CHALLENGE_ALLOWED /
   REVOKED / RESERVATION_REQUIRED`，执行后再由独立 oracle 对 policy decision、实际
   operation 和 postcondition 分别 readback；
5. 报告 false allow、false deny、stale-version acceptance、revocation propagation、
   challenge coverage、重复事实数量、policy/state size、人工确认次数与维护成本；
6. `MANDATE-ADAPTER` 只有阻止成熟栈无法表示的 held-out 旁路，且没有创造第二事实源，
   才支持保留最小新增状态。

真人 `Mandate explain-back` 是下一项独立 hypothesis，不能由上述机器策略测试替代。它至少
需要参与者在不看原文时复述：自主动作、人工 Gate、金额/时间/数据/对手方限制、expiry、
revocation 和仍需本人 Acceptance 的结果；material item 漏答必须触发修订。当前没有真人
输入，因此这一子主张保持 `DEFERRED`，不是失败。

### 建议 V2 target / claim / hypothesis

- 建议 ID：`LINE-05-AUTHORITY-ADAPTER-SUFFICIENCY-V2`
- target：`EXISTING_SOLUTION_COMPOSITION`
- scoped claim：`SC-AUTH-VERSIONED-ADAPTER-GAP`
- hypothesis：`E-AUTH-01-ADAPTER-SUFFICIENCY`
- capability scope：`CAP-AUTH-001`—`CAP-AUTH-005`
- 建议状态：`ACTIVE`
- 启动边界：只启动本地 policy/transition fixture、现成方案一手复核与 adapter gap
  测试；`E-AUTH-02-MANDATE-EXPLAINBACK` 为 `DEFERRED`，直到取得真人同意、材料与独立
  评审；任何“Mandate 是原创/必要对象”结论在一手来源刷新和强基线运行前为 `BLOCKED`。

### 不可影响主张

无论结果如何，本线不能：

- 把认证、VC 或 policy permit 提升为 Principal Commitment/Acceptance；
- 把执行成功提升为 Effect、Adoption、Settlement；
- 因成熟 RBAC 足够而删除 Standing、版本失效或受影响方问题，除非同前提重建其正例与
  removal failure；
- 因 Mandate adapter 通过就证明真人理解、自由认领、合法性或公平；
- 改变能力兑现、PFE formation、NAC、拓扑或完整通爻价值主张。

本线只能决定：哪些 authority distinctions 已由现成 stack 无损承担，哪些最小差异值得
继续作为 scoped state 或 adapter 研究。

## 启动结论

| 母线 | V2 启动判断 | 允许立即进行 | 暂不允许宣称 |
|---|---|---|---|
| 04 能力兑现 | `ACTIVE / SCOPED` | 冻结 holdout、成熟组合基线、首次预测、drift/revocation/recovery 与组合容量冲突 | 一般 Agent 能力、稳定商业履约、CRA 必要性 |
| 05 权威规范 | `ACTIVE / SCOPED` | policy transition fixture、adapter sufficiency 与重复事实审计 | Mandate 原创/必要、真人理解、合法性、Acceptance |
