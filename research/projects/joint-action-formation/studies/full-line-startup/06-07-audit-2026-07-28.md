作用域：`LINE-06-REALITY-EFFECT`、`LINE-07-RUNTIME-EVOLUTION`

## 结论

两条线都可以立即开始，但只能以有界实验启动，不能把“LineContract 已标记 `ACTIVE`”解释成
相关机制、真实主体接受、生产效力或长期净价值已经成立。

| 线 | 本轮决定 | 可立即运行的部分 | 当前证据上限 |
|---|---|---|---|
| 06 现实效力 | `ACTIVE` | 用冻结的目标权威、独立 readback 和 Acceptance 来源，比较成熟事务/事件组合与最小语义 Gate | `BLOCKED`：真人 Principal Acceptance、现实结算、跨域长期净价值 |
| 07 运行与演化 | `ACTIVE` | 在冻结的已形成关系图上注入五类漂移，比较局部重开与“不可变合同 + 监控 + 人工 amendment” | `BLOCKED`：真实长期运行净值、自动 Router、真实关系上的重开精度 |

这不是两条“新机制”已经立项。06 的默认目标是判断一个跨权威语义 Gate 是否仍有必要；07 的
默认目标是判断显式依赖和 Defeater 是否比普通版本化工作流更有判别力。若强基线无损覆盖且
成本更低，两条线都应缩小为 adapter、验证器或运行规范。

在该组场景重建 17/17。它支持的是“ActionAttempt 与目标 Effect 不能默认合并”这一技术主张，
不支持真人 Acceptance、商业结果或跨域普遍性。R5C 支持 adoption、revoke、offline 与 recovery
的技术路径，同时明确没有人类 Acceptance 证据。

按用户指令，本轮外部核验改用环境自带网络通道，只采用一手标准、官方文档与原论文。核验结果：

- [CloudEvents Primer](https://github.com/cloudevents/spec/blob/main/cloudevents/primer.md)
  提供跨系统事件的共同 envelope 与上下文元数据，并明确把事件语义、持久化、授权和运行时
  处理排除在规范目标之外。它可直接承担事件传输表示，但不能单独证明目标域 Effect、
  Adoption、Principal Acceptance 或 Settlement。
- Martin Fowler 的原始
  [Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html) pattern
  以事件序列保存应用状态变化，支持重建、时点查询和 replay；原文也明确指出外部查询/写入
  会使 replay 复杂化，代码和时间规则变化可能变得混乱。因此 event history 可承担应用内
  谱系，不自动成为外部目标域 witness。
- Garcia-Molina 与 Salem 的
  [Sagas 原论文](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)
  将长事务拆成可交错的子事务，并以 compensating transaction 修正部分执行。原论文同时明确：
  补偿是语义撤销，不保证数据库回到原状态，其他事务还可能已经看见中间结果。因此 Saga 是
  强补偿基线，但补偿完成不能自动等于 Effect 已消失、Adoption 已撤回或 Principal 已接受。
- Temporal 官方仓库的
  [History Service 架构说明](https://github.com/temporalio/temporal/blob/main/docs/architecture/history-service.md)
  说明单个 Workflow Execution 的 History Events 足以恢复该 workflow 的 mutable state 和
  tasks。这是 durable replay 的强基线；其恢复对象仍是 workflow execution state，不是外部
  target、Mandate 或 Acceptance 的权威事实。
- [Camunda 流程版本说明](https://docs.camunda.io/docs/components/best-practices/operations/versioning-process-definitions/)
  和
  [process instance migration 文档](https://docs.camunda.io/docs/components/concepts/process-instance-migration/)
  覆盖旧版本继续运行、实例 identity/history 保留、活动元素映射与迁移校验；官方也明确列出
  迁移限制，并警告迁移可形成引擎自己不能发现的非预期状态。它是 07 必须击败的 workflow
  version/migration 强基线，不是安全 scoped reopen 的现成证明。
- [AWS Step Functions Versions and Aliases](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-cd-aliasing-versioning.html)
  提供不可变 state-machine version、revision 和 alias 路由，是“冻结旧版、逐步路由新版”的
  强版本基线；版本号和执行绑定本身仍不判断规范前提是否继续成立。
- [RFC 7009](https://datatracker.ietf.org/doc/html/rfc7009) 标准化 OAuth access/refresh
  token 撤销，并指出撤销传播可能延迟、相关 token/authorization grant 是否级联撤销取决于
  server policy。它直接承担 credential/token lifecycle，但不会自行计算哪些 Relation、
  Evidence、Effect 或 Acceptance 因此失效。
- [OpenTelemetry Signals](https://opentelemetry.io/docs/concepts/signals/) 将 traces、metrics、
  logs 等定义为描述系统活动的 telemetry signals。它是监控、告警和因果排查强基线，不是
  Authority、Effect、Acceptance 或 relation continuity 的事实源。

这些核验把 06/07 的缺口进一步缩小：现成方案已经覆盖事件历史、durable replay、版本快照、
流程迁移、补偿、token 撤销和遥测。候选研究只能主张它们尚未自动覆盖的**跨权威语义晋升**
与**跨规范状态依赖后果**，不能再把上述通用能力列为通爻原创。

## 06 REALITY_EFFECT

### 1. 真实状态

- **形式状态**：现行 `LINE-06-REALITY-EFFECT / v0` 标记为 `ACTIVE`，但
  `problem_ref` 仍指向 Problem v0；它没有自动获得 Problem v2 的精确 LineContract。
- **证据状态**：`CAP-EFF-001` 至 `CAP-EFF-005` 有不同程度的历史技术证据，其中
  ActionAttempt/Effect 分离、目标域 readback、负状态和 replay identity 的局部证据较强；
  人类 Acceptance 与长期净价值仍是开放问题。
- **表示状态**：当前最佳理解不是建立 Effect、Adoption、Acceptance、Settlement 四个平行
  事实根。Operation/ActionAttempt/Effect receipt 可以是正式事件链；Adoption、Acceptance
  与 Settlement 可以由带来源、权威和版本引用的 Stance 或派生状态承担。
- **启动判断**：`ACTIVE`，但仅限于跨权威语义重建和误晋升判别实验。任何现实写入、真人
  Acceptance 或真实结算仍为 `BLOCKED`。

### 2. Scoped question

> 在执行者、目标状态权威、采用者、Acceptance authority 和结算权威不保证重合的
> `RelationEpisode` 中，现有事务、事件、回执、补偿和人工验收机制能否以一套可追溯映射，
> 无误地重建 ActionAttempt → Effect → Adoption → Acceptance → Settlement 的必要差异；
> 若不能，最小的跨权威 Gate 还必须验证什么，才能阻止 producer/transport 状态被晋升为
> 现实完成，同时不复制目标域事实？

不在本问题内：

- 不重新证明 relation formation、Capability、Mandate 或 Commitment；
- 不把 CloudEvents envelope、消息 ACK、退出码、producer `PASS` 或模型判断当 Effect；
- 不由系统替 Principal 接受结果；
- 不要求每个单权威、低风险事务都暴露五层独立对象。

### 3. 现成方案 disposition

总体 disposition：**`ADOPT_AND_EXTEND`，并允许退化为纯 adapter。**

| 现成能力 | 处理 |
|---|---|
| 单权威数据库事务、幂等键、目标状态 readback | `ADOPT`：在同一权威域内承担 attempt/effect、重复抑制和恢复，不另造平行事实源 |
| CloudEvents event envelope | `ADOPT`：承担跨系统事件的可互操作传输表示；不从 envelope 推出语义或规范状态 |
| Event Sourcing | `ADOPT_AS_STRONG_BASELINE`：承担应用内历史、重建、时点查询和 replay；外部交互仍须目标 witness，不能由 event log 自证 |
| Saga / 补偿事务 | `ADOPT_AS_STRONG_BASELINE`：承担多步部分失败和语义补偿；补偿不保证回到原世界状态，也不自动撤回 Adoption 或建立 Principal Acceptance |
| 工作流回执、审批和人工验收 | `ADOPT`：若同一平台已经保存精确版本、拒绝、撤回和权威来源，可直接承担 Adoption/Acceptance |
| 通爻专用五段效力链 | `NO_DEFAULT_NEW_ROOTS`：只在跨权威映射不能由上述组合无损承担时，保留最小 Gate/validator |

真正可能未被现成组合自动覆盖的，不是“缺少事件对象”，而是**跨权威晋升规则**：谁可以把
ActionAttempt 晋升为 Effect，谁可以把 Effect 解释为 Adoption，哪个 Principal/Authority
Locus 可以接受精确版本，以及撤销后哪些后续状态失效。

### 4. 最强反例

一个单一强平台同时拥有：

1. 权威事务提交结果和目标数据库 readback；
2. 幂等 operation identity 与不可覆盖的版本历史；
3. 明确的 adoption 状态；
4. 对精确结果版本的人工审批、拒绝和撤回；
5. 结算与补偿规则。

如果该平台在同等输入、失败注入、权威和维护成本下对所有关键案例零误晋升，并且外部 adapter
只需映射其 receipt，那么独立“现实效力机制”没有新增机制价值。06 应缩小为：

- 一个互操作映射规范；
- 对目标权威和 Acceptance authority 的配置校验；
- 一个防止 producer/transport 状态误晋升的 verifier。

这个反例不会否定 ActionAttempt、Effect、Adoption、Acceptance 的现实差异；它只否定必须由
通爻新增专用事实根或运行时来保存这些差异。

### 5. 最小判别门

#### 冻结输入

- 两个 authority domain：执行域与目标域；至少一个案例中两者不重合；
- 固定 `operation_id`、目标对象、目标版本、readback query 和允许的状态转换；
- 独立的 Acceptance authority 及其所接受的精确 Effect/Adoption 版本；
- 同一组输入、权限、readback、失败注入和恢复机会给予候选 Gate 与强平台基线；
- 保存原始 attempt、目标 readback、Acceptance Stance、撤销和 replay receipt。

#### 必跑案例

1. **Attempt 成功但无 Effect**：执行器返回成功，目标域未改变或写入不可读；
2. **Effect 已发生但未 Adoption**：目标状态改变，但目标工作流未采用或明确拒绝采用；
3. **Adoption 已发生但未 Acceptance**：技术路径已消费，Principal 拒绝或保持 Unknown；
4. **接受后被击败**：Acceptance 绑定 v1，目标回滚、证据失效或 Principal 对未来适用性撤回；
5. **同一 Operation replay**：超时后重试，不得产生重复 Effect、第二 adoption identity 或重复结算；
6. **单权威压缩案例**：强平台可安全合并状态时，候选 Gate 不得强制增加无判别力对象。

#### 通过条件

- 关键案例中 producer/transport/attempt 到 Effect 的错误晋升为 0；
- Effect 到 Adoption、Acceptance、Settlement 的错误晋升为 0；
- 每个正、负、Unknown 和 revoked 状态都能回到相称权威、对象和版本；
- replay 不造成重复外部效力或重复结算；
- 撤销保留历史事实，只阻断其仍然适用的后续推断；
- 相对强平台基线，新增 Gate 的误判下降足以抵偿集成、验证和维护成本。

#### 降级条件

强平台基线无损通过全部案例且总成本更低；或候选 Gate 只能重复目标数据库和审批系统已有事实；
或离开 Harness/R5C 的同构场景后不能可靠定位目标权威。满足任一项时，不晋升新机制。

### 6. 建议的 V2 target / claim / hypothesis

以下仅是候选，不修改正式 registry：

- **target**：`TGT-V2-EFFECT-INTEROP-GATE`
  - 研究一个最小跨权威验证/映射 Gate，而不是新的世界状态数据库。
- **claim**：`CLM-V2-EFFECT-AUTHORITY-PRESERVATION`
  - 在执行、目标状态、采用、接受或结算权威不重合时，各层差异必须能从权威来源、对象和版本
    重建；上游成功不能替下游权威创建状态。单权威平台若无损保存这些差异，可以内部压缩表示。
- **hypothesis**：`H-V2-EFFECT-GATE-01`
  - 在至少两个权威域且存在异步采用/人工接受的任务中，最小语义 Gate 相对 producer/transport
    终态和仅事务回执基线会减少错误完成，同时不重复目标事实；在单权威低风险事务中，强平台
    基线应持平或更优，Gate 自动旁路。

### 7. 不可影响主张

本线任何结果均不得：

- 支持或反驳 NAC、发现规模、PFE、CRA、formation operator 或问题构成主张；
- 从目标 Effect 推出 Capability、Mandate、Commitment 或正确代表；
- 从技术 Adoption 推出真人 Principal Acceptance；
- 从一次 Acceptance 推出永久接受、商业价值、无后悔或 Settlement；
- 从合成 readback 推出生产部署、现实付款或长期有效；
- 用 06 的成功激活 07 的 scoped reopen、Router、中心/联邦选择或系统级净价值。

### 8. 启动决定

**`ACTIVE`**：立即运行冻结的六案例本地判别实验。  
**`BLOCKED`**：真人 Acceptance、现实目标写入、真实 Settlement、跨域长期净价值。  
**`DEFERRED`**：在最小判别门击败已核验的 Event Sourcing、Saga、durable workflow 与强平台
组合前，不注册通爻专用效力机制，不宣称这些现成方案存在未覆盖缺口。

## 07 RUNTIME_EVOLUTION

### 1. 真实状态

- **形式状态**：现行 `LINE-07-RUNTIME-EVOLUTION / v0` 标记为 `ACTIVE`，但同样仍指向
  Problem v0；不存在已登记的 V2 runtime mechanism。
- **历史能力状态**：
  - Problem/Design/Engineering IR 分离、Context Compiler、Evidence Closure 有局部实践；
  - 稳定子图编译有技术路径，但真实重复复用净价值未测；
  - Defeater/依赖闭包重开有实现线索，但现实 precision、漏开和误开率未测；
  - Router 冷启动、真实输入路由和中心/联邦强基线比较仍未证明。
- **启动判断**：`ACTIVE`，限于已形成关系的漂移分类和局部重开判别。真实长期治理效益、
  自动 Router 与生产连续性为 `BLOCKED`。

### 2. Scoped question

> 给定一个已经形成、带精确 `RelationVersion`、Authority、Evidence、Effect 与依赖引用的
> 关系，显式 dependency/Defeater 模型能否区分模型升级、授权撤销、账户离线、证据失效和目标
> 改变，计算出安全的最小阻断/恢复/重开闭包；它是否相对“不可变版本合同 + 普通监控 +
> 人工 amendment”和成熟版本化工作流降低了不必要重开，而没有增加陈旧关系继续执行的风险？

不在本问题内：

- 不研究关系最初如何发现或形成；
- 不把进程存活、日志存在、版本号递增或 workflow replay 成功当作关系仍有效；
- 不在没有显式依赖和 Unknown fallback 时宣称可以安全局部重开；
- 不从本线推出自动 Router 或联邦优越性。

### 3. 现成方案 disposition

总体 disposition：**`ADOPT_AND_EXTEND`，现成运行能力优先，扩展只限跨规范依赖缺口。**

| 现成能力 | 处理 |
|---|---|
| 不可变版本合同 / 配置快照 | `ADOPT`：承担已批准版本和历史，不允许原地改写 |
| OpenTelemetry / 普通监控、告警、健康检查 | `ADOPT_AS_STRONG_BASELINE`：负责 traces、metrics、logs 和运行异常观测；不自动推出规范有效性 |
| Temporal durable history / replay | `ADOPT_AS_STRONG_BASELINE`：给予从 workflow history 恢复 execution state 的完整能力；外部 target/authority 有效性另验 |
| Camunda process version / migration | `ADOPT_AS_STRONG_BASELINE`：给予旧版继续运行、identity/history 保留、显式映射和迁移校验；把官方列出的错误状态与限制纳入反例 |
| AWS Step Functions immutable versions / aliases | `ADOPT_AS_BASELINE`：给予不可变 workflow snapshot、execution-version 绑定和渐进路由 |
| Event Sourcing | `ADOPT_AS_STRONG_BASELINE`：给予事件历史、状态重建和 retroactive replay；外部副作用与代码/时间逻辑变化单独评分 |
| Saga / 补偿工作流 | `ADOPT_AS_STRONG_BASELINE`：给予 backward/forward recovery 和语义补偿；不要求补偿回到原始世界状态 |
| RFC 7009 token revocation | `ADOPT`：作为 OAuth credential/authorization-grant 生命周期权威输入；传播延迟和 server-specific cascade policy 必须显式进入事件 |
| 人工 amendment、重新审批、退出 | `ADOPT_AS_STRONG_BASELINE`：在低漂移或高耦合关系中可能更安全、更便宜 |
| 通爻 Defeater + scoped reopen | `EXTEND_ONLY_IF_DISCRIMINATING`：只研究跨规范状态依赖和最小重开是否仍有未覆盖差异 |

潜在缺口不是“工作流不会重试”，而是不同漂移的**规范后果不同**：

- 可恢复账户离线可能只阻断当前 execution；
- Mandate 撤销会阻断未来授权适用性；
- 证据过期可能让依赖它的 assertion 回到 Unknown；
- 目标变化可能使原 Acceptance 不再适用于新版本；
- 模型升级本身不必重开关系，除非它改变了承诺能力、风险或批准前提。

07 只有在这种依赖后果不能由成熟工作流与人工 amendment 无损表达时，才有扩展价值。

### 4. 最强反例

对于低漂移、依赖稀疏或高后果关系，使用：

1. 不可变、已批准的关系/工作流版本；
2. 普通健康监控与授权状态检查；
3. 任何承重变化都停止相关 workflow；
4. 人工生成新版本、重新审批后恢复；
5. 旧版本、事件和补偿历史保持只读。

如果它在同等故障分布中没有更多 unsafe continuation 或漏重开，而总维护成本、误重开和认知
负担更低，那么持续关系 runtime kernel 没有独立价值。尤其在依赖高度耦合或隐藏依赖很多时，
“局部重开”可能只制造虚假精确；安全答案应退化为更广阻断或人工重审。

这个反例不否定版本、Defeater、退出和恢复差异；它否定的是必须由一个自动关系内核持续计算
这些差异。

### 5. 最小判别门

#### 冻结输入

- 一个合成但完整的已形成 `RelationVersion`，包含 Principal、Authority、Mandate、Capability、
  Evidence、Operation、Effect、Acceptance 与明确 dependency edge；
- 一份隐藏依赖集，仅在事后评分使用，用于测量候选对未声明依赖的鲁棒性；
- 相同事件流、监控信号、人工预算和恢复能力给予：
  1. scoped-reopen 候选；
  2. 不可变合同 + 普通监控 + 人工 amendment；
  3. 上述已核验的成熟 workflow/event-history/version/migration 基线；
- 所有旧版本、决定、失败和恢复 receipt 均不可覆盖。

#### 必跑漂移

1. **模型升级**：输出分布改变，但 Mandate 和目标不变；
2. **Mandate 撤销**：权威来源明确撤销未来行动；
3. **账户离线与恢复**：暂时不可执行，随后同一账户/或替代账户恢复；
4. **证据失效**：到期、被反证或来源不可再验证；
5. **目标改变**：Principal 接受对象从 v1 改为 v2；
6. **隐藏依赖**：图中遗漏一条真正承重依赖；
7. **高耦合/低漂移对照**：分别检验“全局重审更安全”与“runtime 纯属额外成本”的区域。

#### 每次运行必须返回

- 哪些节点立即 `BLOCK`、哪些保持 `VALID`、哪些回到 `UNKNOWN`；
- 计算出的重开闭包及每条 edge 的理由；
- 旧 Acceptance 作为历史事实保留，但对哪个未来版本不再适用；
- 恢复是同一 relation 的 continuation、new version，还是必须退出；
- 需要哪个 Principal/Authority Locus 重新决定；
- 与两个强基线相比的错误继续、漏重开、误重开、延迟、人类判断、披露和维护成本。

#### 通过条件

- 不发生已撤销 Mandate、失效证据或错误 target 下的 unsafe continuation；
- 对冻结的显式依赖，必要重开 recall 达到 100%；
- 对无关节点的误重开显著少于“任何变化全局重审”；
- 遇到隐藏依赖时进入 Unknown/扩大阻断，不伪造局部精确；
- 所有历史版本与责任谱系可读，恢复不覆盖失败；
- 在中等漂移、依赖可声明的目标分布上，全生命周期净成本优于强基线；
- 在低漂移或高耦合分布上允许强基线获胜并自动降级。

#### 降级条件

- strong baseline 在 unsafe continuation、漏重开和恢复时间上不劣，且成本更低；
- dependency graph 的维护成本或隐藏依赖率使局部重开长期不可信；
- 候选只能通过全局重新授权才能安全恢复；
- 只证明 workflow 能 replay，而不能证明 authority/evidence/target 仍有效；
- Router 依赖 fixture 预先编码正确答案，无法从真实材料冷启动。

### 6. 建议的 V2 target / claim / hypothesis

以下仅是候选，不修改正式 registry：

- **target**：`TGT-V2-DEPENDENCY-DEFEATER-REOPEN`
  - 研究关系依赖、Defeater 和重开计划的最小表示与安全退化条件，不建立包办监控、workflow
    和治理的总 runtime。
- **claim 1**：`CLM-V2-CONTINUITY-IS-LINEAGE`
  - 关系连续性取决于相关 Authority、Evidence、依赖和目标版本仍然适用，并保留历史谱系；
    进程、日志、workflow run 或版本号本身不是充分条件。
- **claim 2**：`CLM-V2-SCOPED-REOPEN-CONDITIONAL`
  - 只有在承重依赖显式、Defeater 来源可验证且 Unknown 能安全扩大阻断时，局部重开才是
    可主张能力；高耦合或隐藏依赖条件下应退化为更广重审。
- **hypothesis**：`H-V2-SCOPED-REOPEN-01`
  - 在中等漂移、依赖稀疏且可声明的关系中，dependency/Defeater planner 相对不可变合同 +
    监控 + 人工 amendment 会减少无关重开而不增加 unsafe continuation；在低漂移或高耦合
    分布中，强基线应更优，候选机制必须旁路或扩大阻断。

### 7. 不可影响主张

本线任何结果均不得：

- 证明原关系曾正确形成、Principal 曾正确授权或最初 Acceptance 有效；
- 改写历史 Acceptance；Defeater 只能改变其当前/未来适用性；
- 支持 NAC、发现规模、PFE、Capability formation、CRA 或 authority formation；
- 从 scoped reopen 的合成精度推出生产连续性、长期净值或真人治理接受；
- 从一个 runtime 案例晋升自动 Router、中心优于联邦或联邦优于中心；
- 用局部失败降级 06 的 Effect readback、Harness 的异构 IR 或其他母线主张；
- 把监控、日志、checksum、进程存活或版本递增当成 relation continuity。

### 8. 启动决定

**`ACTIVE`**：立即运行冻结关系图上的七组本地漂移注入和强基线比较。  
**`BLOCKED`**：真实关系长期运行、真人 amendment/重新接受、生产恢复、系统级净价值。  
**`DEFERRED`**：自动 Router、完整关系 runtime kernel、任何中心/联邦拓扑晋升；一手核验
已经证明通用 history/replay/version/migration/compensation/revocation/telemetry 能力存在，
在最小判别门击败这些强基线前，不注册同名通爻机制。

## 两线共同的启动护栏

1. 06 建立的是目标状态与 Acceptance 的可追溯边界；07 只能消费精确版本引用，不能重新解释
   谁产生了 Effect 或谁有权接受。
2. 07 的 Defeater 可以使 06 的某个 Effect/Acceptance 对未来行动不再充分，但不得删除或改写
   该历史事实。
3. 两条线都必须给予平台、中心事务系统、现成技术组合和人工协调真实优势；不能用简化玩具
   基线制造必要性。
4. 第一次启动应只生成候选结果和原始 receipt，不得自动登记机制、晋升主张或改变其他母线状态。
5. 若实验只能重复 R5.2/R5C 已知结论而没有区分现成强基线，应停止同质运行，转向一手
   prior-art 核验或真实低风险关系设计。
