# Wave 025 runner V1.4 修复后独立验收

## 验收结论

**原独立审计 B1/B2/B3：全部 ACCEPTED。**

修复后的 runner 已解除这三个代码级 G 前置 blocker：

- B1：feature spec/profile cross-binding 错配在 batch root 创建前 fail closed；
- B2：预置 D1 canary 的 T runtime template 在任何 slot/container 产生前 fail closed；
- B3：把全部 D0 predecessor receipts 替换成原反例中的六个伪造对象、并重算后续哈希后，
  close 只能得到 ABORTED，reveal 被拒绝。

独立 happy-path 也没有被修复破坏：12/12 fake slots 完成；已完成 batch 的 resume 不改写 slot
receipt；成功 close/reveal 且全部 reconstruction checks 为 true；27 个指定 pre-reveal
表面中 exact D0/D1 private value 为 0 命中。

这不等于真实 G 已经完成。当前 pretty V1 feature spec 仍因非 canonical 被真实拒绝，canonical
V2 release 尚未在本验收中提供；本轮也没有运行真实 Docker。结论是：

> 三个原 blocker 已解除，可以从 runner 修复角度进入下一项 G 前置集成；在 canonical V2
> 自洽材料到位和真实 Docker smoke 完成前，整体状态仍不是 REAL_G_COMPLETED。

## B1 — ACCEPTED

### 原攻击

保持 frozen feature spec 的 schema 不变但改变 canonical bytes，不同步 public registry；
原版本仍会 prepare 成功。

### 独立重放

在 self-consistent test input 基础上，仅向 canonical feature spec 加入一个新字段：

    independent_mutation = same-schema-different-bytes

保持 public/private registry 与 executable profile 不变后调用 prepare。

结果：

    rejected = true
    error = public control registration does not bind frozen feature spec bytes
    batch_exists = false

另一路只把 frozen executable profile 的 profile_id 改为
INDEPENDENT-WRONG-PROFILE，结果：

    rejected = true
    error = frozen executable profile_id does not match control registries
    batch_exists = false

### 判定

ACCEPTED。public registry 的 feature hash 已与同一 batch 的 exact frozen feature entry
交叉比较；executable profile 的 profile_id 也与 public/private registry 交叉比较。错误发生
在 batch root 创建前，没有留下伪 precommit。

### 边界

这只证明当前 runner 的 cross-binding gate。它不证明 feature spec 的科学含义正确，也不证明
executable profile 已实际执行。

## B2 — ACCEPTED

### 原攻击

在 run 前预置 mode 正确的 batch.runtime/templates/t-isolated，并放入当前 private registry
的一个真实 D1 token 文件。原版本会复用该 template，4/4 T 读到 canary 且 12/12 仍为
COMPLETE。

### 独立重放

本轮按 runner 要求分别以 0700 创建 runtime root 与 templates root，再用当前登记的 R-role
D1 token 建立受污染 t-isolated。随后调用 run。

结果：

    rejected = true
    error = runtime template closed inventory mismatch: .../templates/t-isolated
    slot_entry_count = 0
    fake_container_count = 0

### 判定

ACCEPTED。受污染 template 在任何 slot evidence 或 fake container 产生前被 closed-inventory
gate 拒绝。runner 还会在使用每个未完成 slot 前再次验证 template exact bytes/mode/inventory；
T collector receipt 的二次防线要求 challenge tree 只有固定三项、visible_canaries 为空，并
拒绝当前 private D0/D1 instance 及登记的派生表示。

### 边界

fake Docker 没有模拟真实 bind-mount 竞态。当前验收证明的是预置/普通恢复误改会被 host-side
检查拒绝，不证明在“校验后、daemon 实际 mount 前”不存在恶意同权限进程的 TOCTOU 替换。
该更强威胁不属于本地 trusted-controller seal 的既定保证。

## B3 — ACCEPTED

### 原攻击

完成一个 12-slot fake run 后，把 4 个 D0 provenance 中的 receipts 全部替换为：

    [{junk: registered-marker}, {}, {}, {}, {}, {}]

再重算每个 provenance commitment、host-launch hash 与 slot-receipt hash。原版本会得到
CLOSED。

### 独立重放

本轮对修复后新字节执行完全相同的变换，不减少任何攻击步骤。

结果：

    forged_d0_count = 4
    close_state = ABORTED
    complete_slots = 12
    private_d0_provenance_commitment.valid = false
    failure = D0 predecessor receipt 1 command receipt fields mismatch
    reveal = rejected
    reveal error = ABORTED/incomplete batch is terminal and cannot reveal

### 判定

ACCEPTED。修复没有停留在“再加一个 hash”：close 会要求恰好六份 command receipt，并验证
exact receipt fields/schema、command sequence、return code/stderr、单调时序、三个 inspect
preimage、container identity、labels、image、user、mount、marker argv、pre-start/completed
state，以及 create/start/rm stdout。原伪造 preimage 已不能获得 CLOSED。

### 边界

这仍依赖受信任 controller 和 fake Docker 返回的 inspect bytes。拥有同一证据目录写权并能
一致伪造全部 raw daemon/host preimage 的恶意进程，不在本地 seal 的保证内。本验收也没有把
fake inspect 当成真实 daemon 证明。

## Happy path — ACCEPTED

独立新建一个 12-slot fake batch，并执行：

    prepare -> anchor -> run -> run(resume) -> close -> reveal

观察结果：

- 首次 run：12 slots，infrastructure_counts = {COMPLETE: 12}；
- 第二次 run：仍返回 12 slots COMPLETE；
- 第二次 run 前后全部 slot-receipt.json SHA-256 映射逐项相等；
- close：CLOSED，expected_slots = complete_slots = 12；
- reveal：REVEALED，reconstruction_complete = true；
- assignment、padding、public ID、strict balance、opaque IDs、mapping、order、private registry、
  private D0 provenance 的 reconstruction checks 全部为 true；
- fake container state 最终为 0。

这证明修复没有让正常 preformal fake smoke 或“已有完整 receipt 前缀”的 resume 路径失效。
它没有模拟进程在真实 Docker candidate 运行中途崩溃；started-but-no-terminal-receipt 按既有
设计仍应 fail closed，而不是自动重跑。

## Fake Docker 证据边界

本轮没有运行真实 Docker。fake Docker 能支持的判断是：

- runner 的 CLI/receipt/template/control 流程在该替身语义下可运行；
- 三个已知软件逻辑反例现在被 host-side gate 拒绝；
- happy path、resume、close/reveal 的字节闭合没有被修复破坏。

它不能证明：

- 真实 daemon/kernel 强制了 read-only mount/rootfs、UID/GID、capability、namespace、
  network、tmpfs；
- Docker Desktop/daemon 没有 TOCTOU、event 丢失或 inspect 差异；
- 真实 image 内 /bin/sh、chmod、sync、/bin/cat 的行为等同于替身；
- 真实 G 的 D0/D1 信号强度、T 假阳性、运行成本或 3200-slot formal 结果。
