# Wave 025 runner V1.4 独立审计

## 结论

**G 前置集成状态：NOT_READY_FOR_G。**

当前 runner 已经真实消费现有 public/private registry 的字段结构，能从 private registry
取得 D0/D1 每个 role 的实例，也会拒绝把已揭示、仅供 preformal smoke 的 D1 用于 formal
batch。指定的 pre-reveal 公开表面未发现 exact D0/D1 值泄露。

但是，三个可运行的最小反例表明，当前绿灯不能支持进入 G：

1. runner 允许 frozen feature spec 与 public registry 声明绑定的 feature spec 完全不同；
2. runner 会无校验复用早已存在的 runtime template，使 T 读到 D1 控制信号却仍被判为
   COMPLETE；
3. close/reveal 虽对 D0 provenance 做字节 commitment 与 preimage 重建，但 close 对所谓
   exact predecessor command receipts 只验证“至少 6 项且某处出现 marker”。六个伪造对象
   同样能够得到 CLOSED。

本审计没有运行真实 Docker，没有修改 runner 实现文件。

## BLOCKER

### B1. public registry 没有绑定实际 frozen feature spec

runner 会硬编码检查 public registry 中的 feature_spec_sha256 等于 8398...236a，但不会检查
这个值是否等于本次 precommit 实际冻结的 feature_spec_sha256。

最小反例直接使用现有 test harness 的 canonical surrogate：

    prepare_succeeded = true
    frozen feature spec SHA-256 =
      113f2fa73dd1546a445eea0c069e3e39a21fd1ec2415b49f23f14628577e6d62
    public registry declared SHA-256 =
      8398fb773dca1f7da1edd9a5dcef742f27db7ee954fc9f90de8de56713f1236a
    equal = false

这不只是测试 surrogate 太弱，runner 的真实验收逻辑就允许这种错配。profile_id 也只与硬编码
字符串比较，没有与 frozen executable attack profile 的 exact bytes/内部标识交叉绑定。

必要修复：public registry 声明的 feature/profile 必须与同一份 precommit 中已验证 frozen
entry 的 exact SHA-256 及规范标识相等；用一个真实错哈希的负向测试证明 fail closed。

### B2. 未封存的 runtime template 可以把控制信号带入 T

prepare_runtime_templates 对已存在的 batch.runtime/templates/t-isolated 和每 slot template
直接复用，没有检查目录 inventory、file bytes、mode、mtime 或与 precommit 的绑定。这一路径
在新 run 前的预置、崩溃后恢复或同权限误改时都可触发。

反例在 T template 中预置现有 private registry 的 R-role D1 canary 文件，然后运行同一批
12-slot fake smoke：

    run state = RUNNING_COMPLETE_NOT_CLOSED
    infrastructure_counts = {COMPLETE: 12}
    T slots containing the D1 canary = 4 / 4
    T slot classification = COMPLETE (all four)

原因是 T audit 只搜索 D0_MARKER_BASENAME，不拒绝当前 D1 token，更不证明 T challenge
template 是 exact 白名单 inventory。“T 没有 residue mount”不等于“T 没有 control ingress”。

必要修复：runtime root/templates 要么 exclusive-create 并在冲突时拒绝，要么在每次使用前
逐字节验证 exact inventory。T 还必须拒绝当前 private registry 中所有 D0/D1 instance，并
增加上述预置/恢复反例。

### B3. D0 “exact provenance”只有字节闭合，没有命令语义闭合

正常路径的链条存在：

    0600 d0-private-provenance.json
      -> per-slot hash/length/count summary in host-launch
      -> complete set + Merkle root in closed.json
      -> exact private provenance preimages in reveal.json

但 validate_d0_private_provenance 对 predecessor_exact_command_receipts 只要求 list 长度不小于
6，并且 marker 在其任意字符串中出现。它没有验证 receipt schema、六步命令、参数、镜像、
mount、container labels/ID/state、return code、inspect 原始返回或时序。

最小反例把每个 D0 provenance 的 receipts 改为：

    [{junk: registered-marker}, {}, {}, {}, {}, {}]

然后按现有格式重算该 provenance commitment、host-launch hash 与 slot receipt。对 4 个 D0
slot 全部如此处理后，现有 close 仍返回：

    close_state = CLOSED
    complete_slots = 12

这个反例不是要求本地 seal 抵抗拥有同目录写权的恶意进程，而是证明 close 对自己声明验收的
“exact command receipts”没有做最低语义验证。

必要修复：对六份 receipt 实施 exact schema/order/command/returncode 校验，解析两份 inspect
stdout 并复核 name、labels、image、user、mount、marker argv、stopped/exit state，再将这些
受验字节纳入 close/reveal。保留上述伪造 receipt 为回归反例。

## SHOULD_FIX

### S1. canonical V1 blocker 判断正确，但当前释放路径不完整

README 指出的现实 blocker 是真的：

- 当前 feature-spec/FEATURE-SPEC.json raw SHA-256 为
  8398fb773dca1f7da1edd9a5dcef742f27db7ee954fc9f90de8de56713f1236a；
- 它不是 runner canonical JSON bytes；
- 将同一 JSON value canonicalize 后，长度由 22559 变为 18759 bytes，SHA-256 变为
  6f8b2685063b10c7103c2c61aef75f09696e7dc90a05d7ccc0e23117bec5f46c；
- 两份 registry candidate 本身都是 canonical bytes，且绑定前一个 raw V1 hash。

因此原始 V1 文件不能直接通过 V1.4 frozen-input 检查。但 README 所说的“等待 canonical V2
feature-spec 并重生 registry”还需要 runner 自身升级：当前 FROZEN_INPUT_SPECS 仍只接受 V1
schema，registry ID/status/hash/profile 也是硬编码的 preformal V1 值。仅生成 V2 文件不会
自动受理。

### S2. runner 能拒绝 reused D1 formal，但也无法接受 fresh formal registry

mode == formal 对现有 PREFORMAL_CANDIDATE_NOT_BOUND_REUSES_REVEALED_D1 会 fail closed，这一点
已确认。但 validator 同时硬编码要求该 preformal registry ID、status、binding state 和
reused D1 provenance，然后对所有 formal 无条件拒绝。当前没有 fresh formal registry 的受理
分支。

这对 preformal G smoke 不是单独 blocker，但在 formal 3200-slot 前必须修复，并用两个相反测试
锁定：reused -> reject；fresh registered formal -> admit。

### S3. registry 的 NOT_BOUND 语义需与 precommit 对齐

public/private candidate 在内容中声明 NOT_BOUND_TO_PROFILE_OR_PRECOMMIT，但 prepare 随后将
public exact bytes 放入 frozen inputs，并把 private exact commitment 写入 precommit。如果该
状态表示“生成时尚未绑定”，文档应明确它是 provenance state，而不是当前 batch state；如果
它表示当前状态，则 prepare 之后已与事实矛盾。

## CONFIRMED

### C1. actual registry 结构确实被消费，不是替代 schema

runner 实际读取 public candidate 的顶层字段与 families[]，以及 private candidate 的
role_labels、families[].role_mappings、material_provenance 和
per_family_canonical_sha256。两份 candidate 也都通过其实际 JSON Schema。

但 runner 实现是手写字段校验，并不读取两份 schema 文件；因此“schema 通过”与“runner 验收
通过”是两个需要同时维护的 truth surface。

### C2. 指定的 pre-reveal 公开表面未发现 exact private instance

在一个完整 12-slot fake run 后、close/reveal 前，对下列 26 份文件扫描 private registry 中
四个 exact D0/D1 实例：

- public-plan.json；
- precommit.json；
- 12 份 slot-receipt.json；
- 12 份 host-launch.json。

结果为 0 个 exact-value hit。precommit 只暴露 private registry 的 raw hash/长度、
schema/status、role label 与 per-family hash；D0 host-launch 只暴露 private provenance
hash/length/count 摘要。六份 predecessor exact command receipts 与 exact marker 留在 0600
runtime journal，成功 close 后才由 reveal 发布。

这个结论仅覆盖题目指定的四类表面。D0/D1 实例本来就必须出现在各自 candidate-visible
collector evidence 中，否则正控无法成立；这不应被误报为 role mapping 在 reveal 前公开。

### C3. D0 commitment -> close -> reveal 的字节链条成立

对未修改的正常 fake smoke，close 会要求每个 D0 slot 存在 0600 provenance，重算 per-slot
hash，与 host-launch 摘要比较，并将全集 commitment 写入 closed.json。reveal 重读 exact
preimage，与 close 比较，然后发布 preimage 与 commitment。现有 happy-path 测试证明了这个
字节重建。

它不能消除 B3：哈希闭合一个伪造的 preimage，仍然只是对伪造字节的忠实承诺。

### C4. fake Docker 不能证明真实 daemon/内核边界

fake Docker 证明的是 runner 发出了期望的 CLI 形状，且测试替身按自身逻辑回显
inspect/events/files。它不会证明真实 Docker daemon 确实强制 read-only mount/rootfs、
UID/GID、capability、namespace、network、tmpfs 和 event ordering，也不会证明真实 image 内
/bin/sh、chmod、sync 与 /bin/cat 的语义。

因此 fake smoke 只能作为进入真实 G smoke 的前置，不能替代 G。

## 进入 G 的最小门槛

1. 修复 B1，证明 public registry 的 feature/profile 声明与同一 precommit 的 exact frozen
   bytes 交叉绑定；
2. 修复 B2，对 runtime template 做 exclusive-create 或 exact inventory 校验，并让 T 拒绝
   所有当前 D0/D1 instance ingress；
3. 修复 B3，对 D0 predecessor receipt 做 exact 结构与语义验证；
4. 把三个最小反例加入回归测试，然后再运行全套 fake smoke；
5. 完成 canonical V2 及其实际 runner/registry 受理路径后，才运行真实 Docker G；
6. G 必须保留真实 daemon inspect/events/raw channels，并与 fake 结果区分报告。
