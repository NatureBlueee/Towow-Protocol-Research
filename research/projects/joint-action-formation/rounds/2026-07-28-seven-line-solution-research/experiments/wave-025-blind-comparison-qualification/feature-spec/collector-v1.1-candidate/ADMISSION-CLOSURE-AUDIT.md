## Result

The implementation now exposes two different outcomes and does not call either one formal validation:

- `CANDIDATE_NON_G_ADMISSION_PASS_WITH_UNVERIFIED_CODES`: local/non-G structural and semantic smoke;
- `CANDIDATE_G_INPUT_ADMISSION_PASS`: the stricter **input-admission gate** obtained only after exact
  package verification and a controller-sealed material preimage.

Both always return `formal_admission=false`. No G batch or formal population was run. This document is the
implementer's test result, not independent acceptance.

## Independent blockers and implementation choices

### 1. Runtime package/source binding

Both producer and Python CLI require an exact `PACKAGE-MANIFEST.candidate.json` SHA-256 supplied outside
the package invocation. Before loading the historical collector or parsing a receipt they verify:

- manifest canonical compact JSON plus one LF;
- exact six-file runtime set, byte lengths and hashes;
- historical collector source and historical V1 schema byte lengths and hashes;
- the self-contained release schema's structural core equals the frozen historical V1 schema.

Missing manifest produces `PACKAGE_MANIFEST_MISSING`. Appending a syntactically harmless comment to the
candidate producer produces `PACKAGE_FILE_MISMATCH` in both producer verification and the Python CLI.

Current runtime manifest:

```text
SHA-256 bfddb4f4ef990a54660868c54a348033822adedc3eb0683f30a5174863594a7a
byte length 1313
```

This prevents ordinary omission/drift under the stated trusted-controller threat model. It is not a defense
against a malicious same-authority process rewriting code and every external seal input.

### 2. Controller-sealed material preimage

The old self-supplied binding no longer has a G pass meaning. G mode requires:

- a canonical controller material preimage in an external root;
- its exact SHA-256 as a separate trusted controller input;
- `controller_domain=EXTERNAL_READ_ONLY_TO_WORKER`;
- role, slot and run identity;
- exact package manifest, receipt, config, subject, environment, challenge snapshot, process snapshot and
  runner execution-evidence bindings;
- an exact challenge-root relative path inside that controller domain.

The validator strictly parses raw collector-input bytes, rejects duplicate members/non-JSON, and requires
the parsed object to equal `receipt.input_contract.parsed`. It reconstructs the live challenge inventory,
canaries and stat tree, compares the external snapshot byte-for-byte at object level, then requires
`receipt.directory_trees.challenge` to equal the reconstructed tree.

Changing a preimage but retaining its old external SHA returns `CONTROLLER_SEAL_MISMATCH`. Even after
re-signing all synthetic files, a non-JSON config returns `RAW_JSON_INVALID`, and forged challenge-tree
metadata returns `CONTROLLER_CHALLENGE_TREE_MISMATCH`.

The executable layer cannot prove that the SHA actually came from a worker-inaccessible controller. That is
a required external authority/precondition, not an observed fact.

### 3. Executable schema and canonical release bytes

`COLLECTOR-RECEIPT-V1.1-ADMISSION.candidate.schema.json` is now self-contained. It is mechanically generated
from the frozen V1 schema, with only release metadata changed. Independent `Draft202012Validator(schema)`
instance validation works offline, and the CLI actually validates the same parsed raw receipt with this file.

The policy and both schemas are generated by `build_release_artifacts.py`; all three pass the same Node
raw-canonical checker used for receipts:

### 4. Process and error branches

When `process_view.available=true`, G requires a raw process snapshot. Null returns
`G_PROCESS_SNAPSHOT_REQUIRED`. Any public process/self error projection produces a closed machine unknown
code and G rejects with `G_PROCESS_SNAPSHOT_INCOMPLETE`; status is never derived from human text prefixes.

G also rejects hostname, identity, uptime, tree and process error/unavailable branches that cannot be
independently reconstructed. The narrower non-G validator now rejects:

- depth-six trees and a directory at the collector's depth boundary;
- process error paths other than the actually read `cmdline` or `status` leaf;
- `/etc/hostname` errors attributed to another path;
- tree missing-entry errors whose operation is not `lstat`;
- tree post-entry directory errors whose operation is not `scandir`.

The timing probes retain their exact fixed name/path/syscall checks.

### 5. Canary domain and resource admission

G does not interpret an unscanned large file as canary absence. Every challenge regular file must be at most
65536 bytes. A 65537-byte file containing a canary is rejected by both independent Python reconstruction and
the JavaScript producer preflight with `G_CANARY_FILE_OVERSIZE`.

Before calling the historical base collector, producer G mode now:

- caps environment count and every environment key/value string;
- stats the subject and `/etc/hostname`;
- verifies canonical proc PID grammar/population;
- scans challenge canaries with the full row cap;
- walks challenge/cwd/out/tmp/self-fd using incremental directory reads, applying node/depth/error caps;
- reads challenge files only after the 65536-byte size check.

After collection it repeats the tree-domain fingerprint and complete canary scan. Any change rejects. The
controller preimage additionally requires read-only challenge and worker-nonwritable-controller assertions
from externally sealed runner evidence.

This removes the previous G interpretation of post-materialization caps as preallocation safety. It still
depends on the stated read-only/stable mount and trusted-runner assumptions; resistance to a malicious process
with the same file authority is explicitly outside this candidate.

## Remaining preconditions and Unknown

1. A trusted controller must actually create the preimage SHA and keep that authority domain unwritable by
   the worker. The validator checks the preimage; it cannot establish the operating-system authority fact.
2. The runner must actually mount challenge read-only and produce truthful execution evidence. The current
   candidate validates a sealed execution-evidence object and its bindings; it does not independently inspect
   kernel syscalls or network namespaces.
3. Exact challenge stat equality requires the controller snapshot to observe the same mounted filesystem
   identity as the collector. A copied directory with different inode/device/uid is intentionally rejected.
4. Same-permission malicious peer resistance remains out of scope, as requested.
5. The candidate has not been independently re-reviewed after these implementation changes.
6. G, the 3200-slot population, V2S extraction and scientific qualification remain `NOT_RUN`.

Therefore the implementation is ready for another independent red-team pass. It does not itself change
`POST_FIX_REJECTED_FOR_FORMAL_AND_EVIDENCE_BEARING_G`, adopt the candidate, or authorize G.
