## 0. 阅读规则

本附录回答的不是“写了多少、跑了多少”，而是每一波为什么启动、实际上改变了什么认识、哪些结果后来被推翻或缩窄，以及它在完整产品问题中处于什么位置。

这里使用以下证据标记：

- `SOURCE_AND_DESIGN`：来源扫描、问题重建或实验设计；没有运行结果。
- `LOCAL_SYNTHETIC`：冻结的本地合成世界结果；不外推现实频率、真人行为或生产表现。
- `POST_ORACLE_DIAGNOSIS`：看到评价约定后做的诊断；可以解释失败原因，不能作为新盲分。
- `ROOT_ATTACK_RECHECKED`：主研究者直接复现反例或重放修复边界；不是独立实现或新盲证据。
- `EXTERNAL_THEORY_RETURN`：外部模型提供的竞争解释或实验建议；不是本地实验的独立证明。
- `NOT_RUN`：只有规范、truth、evaluator 或 runner，没有候选实际运行。

测试数量、文件数量、哈希和 seal 只在说明可复核性或暴露伪成功时记录，不作为成果本身。真正的研究结果是任务结果、反例、可保留的有界能力、被撤销的主张，以及它们改变的产品行为。

## 2. Wave 001 — 七线候选方案与责任断点扫描

### 为什么启动

在开始构造专有机制之前，先回答七条母线分别可以怎样解决、哪些组合值得进入同任务比较、最早会在哪里失去责任。更承重的前置任务是检查 T1–T6 是否真的能运行，避免在答案泄漏、只有规格或根本不是任务的材料上制造覆盖率。

### 实际做了什么

- 逐线把发现、关系形成、条件形成、可依赖性、Authority、Effect/Acceptance、复用与重开的候选能力串成一条端到端候选链。
- 对每条线记录输入前提、能提供的局部能力、明确不负责的事实、维护/迁移风险和首个责任断点。
- 将 T2、T3、T1/T4/T6/T5 的实际资格问题写入任务校正，不进行覆盖率评分。

### 关键正结果

这一波产生的有效成果不是选出赢家，而是识别出两个最承重接口：

1. query、角色和动作形成之前，局部私有世界怎样产生一个值得询问的机会；
2. ActionAttempt 之后，如何跨不同 Authority domain 防止把事件依次误升为 Effect、Adoption、Acceptance 和 Settlement。

同时得到一条可检验的整体候选路径：端侧触发和最小投影负责把局部可能性变成可路由输入；关系/workflow/Authority/执行与 readback 各守自己的事实边界；变化时根据依赖重开。这个组合如果能在同一任务与留出变体中首尾闭合，本身就是解决方案，不需要另造同能力对象。

### 关键负结果与证据级别

- 证据级别：`SOURCE_AND_DESIGN`。
- 没有运行合格 task instance，没有 coverage，没有证明任一组合解决 V1/V2。
- 来源中关于规范版本、生态活跃度和维护状态是 2026-07-28 扫描时的来源陈述；本附录不把它们当作 2026-08-01 重新核验的当前事实。
- “组件列表覆盖很广”不等于端到端成立；局部合同之间的非蕴含跨越仍需任务证据。

### 对产品与原问题的意义

Wave 001 把产品方向从“先造一个统一机制”改成“先让完整任务经过多个事实 owner，并只对真正断裂的跨越继续构造”。它还确定了简单任务必须允许直接旁路，不能为了统一叙事强制进入复杂关系链。

### 后来如何被校正

Task Truth Correction 001 固化了本波发现的任务资格问题。后续 Waves 006–009 又证明：即使组件接口在文字上看似齐全，只要 candidate 能自报 truth、持有别人的 key、改写日志或借同名字段跨越，仍会产生伪闭环。因此 Wave 001 的组合图只能保留为候选结构，不是产品完成证据。

## 3. Wave 002 — 首轮隔离运行与组合比较

### 为什么启动

Wave 001 只有候选和断点。Wave 002 要第一次在同一个冻结合成分母上比较“公共目录/索引”“本地主体最小投影”及二者组合，并用经答案隔离的 T2 前态检验：一个被拒绝的 v1 是否能在不偷渡结果的情况下推进到合法下一步。

### 实际做了什么

- 在 T1-HW-20260728-A 上运行 A、B、A+B，统一 latent truth、八项要求与 scorer。
- 将 T2 原材料拆成 solver 可见前态与 evaluator 持有的 oracle；通过四轮最小披露构造 material-change 后的 v2 candidate。
- holder、coordinator、solver、evaluator 使用不同 Codex 实例，但都来自同一 provider；这提供执行隔离，不提供模型多样性。

### 关键正结果

- G1：A 为 `0/8`，B 为 `1/8`，A+B 为 `5/8`。组合恢复了一个未预制公共 card 的机会，处理了动态撤销，并正确区分 offline=`UNKNOWN`、明确拒绝=`REFUSE`、封闭总体负证据=`ABSENT` 和 policy 下不可发现。
- 组合相对单项确有互补增益：目录负责已经表达的路由信号，本地投影保留当前状态、拒绝和披露约束。
- T2 最佳输出没有声称 pilot 已成功，而是保留 v1 `REJECTED`，形成 `REL-T2-V2-CANDIDATE`，明确 bounded probe 尚未运行、当前 capability 为 `UNKNOWN`，测试授权不延伸成正式 pilot 授权，Effect/Adoption/Acceptance/Settlement 均未发生。

### 关键负结果

- A 把同 facet 的 SEEK/SEEK decoy 当成互补机会，并继续使用失效 offer。
- B 虽能保真表达局部状态，但没有路由与双向 probe，机会召回为零。
- A+B 仍缺 reciprocal completion、方向验证、合法 disclosure receipt 和关系 handoff。
- T2 的高分只说明文本候选忠实守住了“下一步”状态边界；真实 probe 没有运行，业务能力与现实价值仍未知。

### 证据级别与未证明

- 证据级别：`LOCAL_SYNTHETIC`，并带同一 provider 的执行隔离。
- 未证明现实发现率、真人披露意愿、生产可靠性、真实 capability、商业价值或完整关系形成。
- 同模型 evaluator 和对抗实例没有发现偷渡，不等于独立模型或现实主体复核。

### 对产品与原问题的意义

产品不能把“搜索到条目”当成发现完成。至少还需要方向、当前版本、披露许可、互惠确认和进入关系构成的 handoff。另一方面，产品也不能把“条件已经写清”当成 probe 已执行；Unknown 必须保留到真实执行证据出现。

### 后来如何被校正

Wave 003 将 G1 的剩余断点具体化为 reciprocal probe 与 versioned handoff；Wave 003/004 又发现 HW-B 曾把 authorization 冒充 execution。T2 的“下一步候选”从未被追溯升级为现实任务完成。

## 4. Wave 003 — 从局部发现到候选关系的构造

### 为什么启动

Wave 002 已经显示：目录和本地投影互补，但二者之间缺少一个可验证转换。Wave 003 因而聚焦怎样把局部可能性推进成“有边界、可撤销、双向确认、可进入关系构成但尚非承诺”的候选，同时加入简单任务旁路、真实 probe 状态和联合投标迁移。

### 实际做了什么

1. 提出并细化组合链：

   `local trigger → task-relative projection → routing → receipt-backed reciprocal probe → versioned candidate handoff`

2. 在 T5 简单任务上三次修订 evaluator：
   - V1 曾让只写 `PLATFORM_DIRECT`、零动作的候选获得满分，结果无效；
   - V2 仍让 authority、写入、cache、泄漏和成本依赖 candidate 自报，也无效；
   - V3 只允许 hash-bound、由 evaluator 解释执行的受限 transducer，并由 readback 和 trace 重建结果。
3. 为 T2 构造五分支 probe simulator：成功、环境不匹配、运行中撤销、producer 完成但 buyer witness 缺失、幂等重试；再用 bridge 限定每个结果能推进到哪一层。
4. 运行 T1-HW-B 候选并发现缺少 controller/receipt issuer；truth owner 一度手写 completion JSON，复核后撤回并删除。
5. 冻结 T4 三主体联合投标世界，运行本地 method-neutral baseline，形成非承诺候选并接受 mutation/migration 评价。

### 关键正结果

- T5 在修复后的冻结作用域内，平台直接路径和受限 identity adapter 都能完成 `6/6`；零动作标签候选为 `INVALID`。这支持“简单任务直接完成、必要时只加薄适配”的产品行为。
- T2 simulator 证明五种 probe 结果可以被机械分开：成功只资格化精确 operation；环境错配只重开 environment binding；撤销要求新授权；缺 buyer witness 不能形成 reliance；重试不增加新执行。
- T4 baseline 保持 `CANDIDATE_NOT_COMMITMENT`，没有伪称签署、提交或城市 Effect；它暴露了 risk allocation、audit scope、预算变化、签署撤回、probe failure 和重复提交等未闭合点。

### 关键负结果

- T1-HW-B 虽找对三个机会且无 decoy wakeup，却把 holder 的 `AUTHORIZED / NOT_FORWARDED / NOT_PERFORMED` 冒充已完成 route/probe，正确状态是 `FAIL_1_OF_8 / BLOCKED_BY_MISSING_CONTROLLER`。
- T4 只得到 `0.60 / PARTIAL`，mutation 未闭合、migration 未运行；“所有已披露条件满足”写得过强。
- T5 V1/V2 是 evaluator 失败史，不得引用为平台能力证据；V3 也只覆盖固定平台和白名单 transducer，不是通用 adapter 验证器。

### 证据级别与未证明

- T5 V3、T2、T4：`LOCAL_SYNTHETIC`。
- T1-HW-B：明确失败；手写 completion 已撤回。
- 未证明真实采购/支付、跨平台迁移、真实 probe、真实签署、业务 Effect、真人 Acceptance 或长期恢复。

### 对产品与原问题的意义

Wave 003 首次给出产品状态机的关键禁令：`authorization ≠ execution`、`probe success ≠ relation`、`candidate ≠ commitment`、`delivery ≠ Effect/Acceptance`。同时确立了简单任务的 collapse path 和复杂任务的候选 handoff 结构。

### 后来如何被校正

## 5. Wave 004 — 本地 controller 闭合与跨线含义

### 为什么启动

Wave 003 的 T1-HW-B 暴露出“发现正确但没有真正执行者”的缺口。Wave 004 要让 holder authorization 经受信 controller 实际进入 recipient store，由磁盘 readback 生成 receipt，并检查这条局部链对 G2–G7 分别意味着什么。

### 实际做了什么

- 实现 direct、derived onward 和 reciprocal counterparty exchange 的本地 controller。
- 增加幂等、同 key 不同 payload、contract change、pending recovery、audit tamper、recipient store deletion 和 central-collection 冒充 counterparty exchange 等攻击。
- 将 Wave 004 的能力按 G2–G7 拆开，明确每条线可继承什么、仍缺什么、下一实验应怎样判别。

### 关键正结果

在受信本地合成边界中，以下链可以工作：

`local trigger/projection → compatibility/policy → holder authorization → controller execution → recipient readback → candidate handoff`

exact replay 不新增 event；same key/different payload、changed-contract replay 与 pending recovery 会被拒绝；删除 recipient store 或篡改 audit outcome 不再返回旧 `EXECUTED`；reciprocal completion 需要两个 recipient store 的独立 readback。

### 关键负结果

- HW-B V2 真执行后仍只有 `4/8`，因为 evaluator 依赖三项未公开的表示约定。
- V3 在看到这些约定后达到 `8/8`，其意义只是 `POST_ORACLE_DIAGNOSIS`：剩余差距可以由表示合同解释，不是 blind pass。
- scorer 的表示语义不是“外层格式”小问题；如果未公开语义决定通过与否，它就是方法环境的一部分，必须事前冻结。
- 仍缺 holder/recipient 独立签名、relay delegation、不同权限域撤销与恢复、candidate 无权改写的外部 anchor，以及新的留出世界。

### 证据级别与未证明

- 证据级别：controller 链为 `LOCAL_SYNTHETIC / ROOT_ATTACK_RECHECKED`；V3 为 `POST_ORACLE_DIAGNOSIS`。
- 未证明跨 Authority 现实、恶意同权限写入抵抗、真实 delegation、现实业务 Effect 或新 blind generalization。

### 对产品与原问题的意义

本波说明一个 controller 可以编排多个局部事实，却不能因此拥有关系、Authority 或 Effect 的真值。产品应保留逐段 owner、receipt 和失败状态；外层统一体验不能压成一个“已形成关系”总状态。

### 后来如何被校正

Wave 005 将 holder、controller、recipient、anchor 分到四个签名域；Wave 006/007 又证明“分进程、签名、日志、seal”如果仍可被 candidate 访问或由同一策略生成，也会制造伪独立。因此 Wave 004 结论始终停在受信本地 controller 边界。

## 6. Wave 005 — 新留出 truth 与跨 Authority receipt kernel

### 为什么启动

Wave 004 已经触及本地 controller 的上限：缺少真正分域的签名、recipient ACK、relay onward authorization 与外部 anchor；同时 HW-B 已经被看过，不能再作为盲晋升证据。Wave 005 因而分两条线：构造全新 HW-C truth/evaluator，以及实现跨 Authority receipt kernel。

### 实际做了什么

- HW-C 使用 11 个物理隔离 local packet，事前公开 depth、reciprocal orientation、terminal status 和 receipt/ACK/anchor 验证语义，冻结 falsifier；没有生成 candidate。
- receipt kernel 将 holder、controller、recipient、external anchor 分成四个本地 Ed25519 域；direct 需要 recipient ACK + anchor，derived 需要 first recipient onward authorization，reciprocal 需要双方 commit ACK；同时加入 revocation、key rotation/expiry、idempotency 和 crash recovery。
- 为每个 packet 的 fresh isolated solver 准备严格白名单 runner，但外发 synthetic packet 到精确 provider 需要用户授权；安全审查拒绝了未获授权的运行。

### 关键正结果

- 新留出世界的 truth/evaluator 与候选路径在文件和输入上完成隔离设计，避免继续在 HW-B 上 post-oracle 修补。

## 7. Wave 006 — 共享任务集成与对抗性失效

1. **G2 原比较无效。** evaluator 没有读取真正的 relation evidence，A/B/C 的任务行为相同，winner 由硬编码成本决定。它不能证明 delivery receipt 已足够，也不能证明 RelationVersion 没有材料性。

## 11. Waves 001–009 的累计结论

### 已经沉淀下来的真实进展

1. **任务材料资格本身是承重变量。** T2 的答案泄漏、T3 的任务误认、T6 缺 base trace 都曾足以使后续评价失真。
2. **简单任务应直接完成。** T5 支持 platform-direct/collapse path；不能为统一架构强制制造关系、Authority 或协议对象。
3. **发现不是一次搜索。** 局部触发、最小投影、当前版本、披露许可、方向、互惠 probe 和 handoff 分别解决不同问题；零披露不可区分时必须保留 Unknown。
4. **关系、Authority、能力、执行和结果互不蕴含。** `proposal/ACK/explain-back` 不等于 stance；Allow 不等于 Commitment；workflow receipt 不等于 reservation；probe success 不等于 capability；ActionAttempt 不等于 Effect；Effect 不等于 Acceptance。
5. **controller 可以编排，不能代签。** Principal、Authority、Target、beneficiary/Acceptance 必须保留各自当前 head、拒绝和原生 readback。
6. **形成不能用单标签解释。** closure、new token、model/policy change、task invariance 和 trace validity必须正交表达；强中心或 workflow 在相同条件下完成任务是产品正结果。
7. **失败恢复依赖真实 dependency。** exact replay、material change、撤销、hidden dependency 和 Acceptance refusal 需要不同处理；没有观察就不能假装最小重开已知。
8. **评价系统自身会制造伪成功。** label-based cost、candidate-owned logs、truth-correlated case ID、持有全部 key、同一 parser 换名、post-oracle 修补和预填 world label 都实际发生过，并改变了后续实验架构。

### 到 Wave 009 仍没有完成的事

- 没有一个真实、具体、可拒绝、带 owner/Target/Acceptance 的任务 specimen。
- 没有一条从模糊/不完整输入开始，经过共同提案、能力资格化、Authority/Reservation、Commitment、真实执行、Target Effect、各方 Acceptance，再到变化后重开的完整 RelationEpisode。
- HW-C 没有运行；QHM-2 没有运行；T6 没有合格 base-run；X1/X2 没有运行。
- 没有现实主体授权、真实物理或法律 Effect、真人 Acceptance、生产部署、跨故障域安全、长期漂移或净价值证据。
- 没有证明某个特殊协议、拓扑或 formation-specific 方法是必要的；也没有证明开放现实中的全部残余都能由当前本地组合闭合。

### 对“当时为什么做、原本要去哪里”的最终定位

Waves 001–009 原本不是为了积累 evaluator、receipt、seal 或代码，而是在逐步取得完成一个 RelationEpisode 所需的真实性边界：先找出入口断点，再让候选经过 controller、Authority、Effect 与 reopen，最后在同一任务上首尾闭合。研究的合理演进本应是：

`局部断点被识别 → 构造并攻击局部解决链 → 将可保留能力接入同一 episode → 运行异质迁移 → 把稳定路径沉淀为产品行为`

实际偏差是：Wave 006 之后大量注意力被用于修复评价与证据基础设施；这些修复确实阻止了多类假成功，却没有及时回到一个完整、具体的 episode。因而本附录保留两项同时为真的判断：

- 这些波次产生了重要、可复用的状态边界、反例和局部解决能力；
- 它们没有完成原始产品问题，后续不能再用更多局部绿灯代替完整 episode。
