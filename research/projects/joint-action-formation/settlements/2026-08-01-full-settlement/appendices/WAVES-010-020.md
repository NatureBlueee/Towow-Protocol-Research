# Waves 010–020 研究沉淀

日期：2026-08-01  
作用域：Wave 010–020  
性质：历史结果沉淀；不改变 Problem、LineContract、MechanismProfile 或任何正式证据状态

## 1. 这十一轮究竟推进了什么

Wave 010–020 不是十一轮同一强度的“完整实验”。它们实际形成了一条很清楚、但中间多次偏离又被纠正的演进链：

```text
X1→X2 完整 episode 设计
→ 七条母线分别建立可判别的局部 kernel
→ 用 CE-001 把七线放入同一任务合同
→ 发现七套局部产物并不属于同一次运行
→ 建立第一个共同 world 纵切
→ 用 causal twin 修正“终态等于本 arm 造成”
→ 建立统一 arm view、隐藏场景控制和 Target ledger
→ 逐个完成 ACK 丢失、平台直达、撤销重开、条件形成、迁移恢复的有界案例
```

这条链中真正值得保留的成果不是测试数量、文件哈希或凭据数量，而是下列现实判别能力逐步出现了：

- 能区分一条候选是在前态中已经可发现，还是由 episode 内的行动首次创造出来；
- 能区分 `TaskOutcomeSatisfied`、`AuthorizedExecutionCommitted` 与 `EffectAttributableToArm`；
- 能在 ACK 丢失后，用 Target 的精确状态决定 reconcile 还是 safe retry；
- 能在统一 Authority 的平台内直接完成任务，而不强造跨主体关系；
- 能在资源撤销后只重开受影响部分，并重新发现替代方；
- 能用各 owner 的真实 act 首次形成目的、委托、承诺、预留和批准条件；
- 能在受控进程终止后，迁移未结义务、阻止旧 runtime 重放，并恢复 Acceptance 与 finality；
- 同时保留一个更承重的负结论：这些案例仍是已知 Q、已知 owner 类型、有限 action grammar 下的本地合成 RelationEpisode 证据，不是 V1/V2 开放形成和 RelationEcology 的完整答案。

以下逐 Wave 记录为什么启动、实际做了什么、正负结果、证据等级、对产品和原问题的意义，以及明确没有证明什么。

## Wave 010：从分线结果转向 X1→X2 完整闭环，但只完成设计与局部夹具

### 为什么启动

Wave 009 已经给出若干分线正例和两个外部研究返回，但原提议中的 `66/72` 只是运行预算草案：分母未冻结、X1 到 X2 会丢失 typed non-success、若干 paired motif 并不正交，五层后置状态还可能被一个 controller 代签。Wave 010 因而试图把前半程候选形成与后半程执行闭合放回同一个冻结任务，而不是继续积累彼此不接的局部结果。

### 实际做了什么

- 建立 X1 的设计候选：从 `IntentAtCoordinationInterface` 出发，分别保留 G1、G2、G3、G5 的 owner truth、局部判定和 transition receipt。
- 建立 X2 输入合同候选：要求机械接收每个 arm 自己的 finalized X1 output，再处理 G4、attempt-time G5、G6 和 G7。
- 建立 M01 paired episode freeze bundle。独立审查只接受它作为“可进入后续 scoreable-pair 冻结流程的候选”，没有 scoreable episode、runner 或方法运行。
- 建立 owner commitment 与 process allowlist 门，但真实 owner 身份、签名和强制隔离均未闭合。
- 另行运行 G4 reliance 和 G6/G7 的本地手写夹具，用于把 stale head、hidden dependency、wrong-object Acceptance、Effect/readback 和 reopen 问题变成可执行反例。

### 关键正结果

- X1 结果代数开始无损保留 `BOUNDED_UNREACHABLE`、`SAFE_EXIT`、拒绝与 Unknown，不再只保存成功 handoff。
- G4 v2 能在有限手写世界中区分 declaration/readiness、exact-operation probe、current head、resource、recovery evidence 和不可查询依赖；保守组合避免了受检验 unsafe case 的 false reliance，但会漏掉 hidden-valid case。
- G6/G7 夹具保留了两个仍然成立的逻辑反例：workflow/outbox/event delivered 不推出外部 Effect/Acceptance；在合法 transcript 相同而隐藏依赖状态相反时，没有新增观察就不能同时得到零误继续与零无谓阻断。

### 关键负结果

- X1/X2 主线没有运行。M01 仍是冻结候选，X2 没有 actual ingress。
- G4 v1 的 strong-center “等价”来自直接复用同一函数，recovery 只是字符串匹配；v2 撤回这两项主张，也没有再运行 strong center 或真实恢复。
- G6/G7 的 `7/7` 来自 private truth direct-copy、共享 decision implementation、硬编码 closure 和不完整 gate。独立攻击能用 stale head、wrong-object Acceptance 和错误 reopen action 击穿它，因此只保留为“伪满分怎样形成”的失败历史。

### 证据级别

`DESIGN_CANDIDATE + SCOREABLE-PAIR FREEZE CANDIDATE + LOCAL SYNTHETIC DEVELOPMENT KERNEL`。

### 对产品与原问题的意义

这轮确立了一个仍然正确的产品骨架：入口产生的每个候选必须携带自身完整谱系进入执行闭合，不能共享一份手写成功世界；Effect、Acceptance、拒绝、Unknown 和 reopen 必须由各自 owner/Target 的事实决定。它没有完成产品 episode，但明确了后续不能怎样拼接。

### 明确未证明

- 一个完整 X1→X2 episode 已发生；
- 任一方法在公平同任务上胜出；
- 真实 Authority、Effect、Acceptance、恢复或迁移；
- owner query 在现实中准确、及时、可负担；
- V1/V2 或完整产品已解决。

## Wave 011：把七条母线分别做成可攻击的局部判别器

### 为什么启动

Wave 010 暴露了三类反复出现的假成功：truth 被直接送给方法、不同方法只是同一函数改名、评价器把多种现实压成一个标签。Wave 011 的目标是让 G1–G7 各自先具备足够锐利的局部语义、owner 边界和反例，再考虑集成。

### 实际做了什么

- G1：建立 provenance discriminator，区分 public/t0 lawful evidence、t1 operator-created qualification、refusal 和 policy-undiscoverable；invalidity gate 优先于 recall。
- G2：建立 owner evidence + open-schema discriminator，分离 constituted、understood、claimed、authorized、activated，并保留 private column、opposition、stale 与 refusal。
- G3：建立六 world quantifier discriminator，分开旧 closure、operative condition、kernel change、task change、证据有效性与六类 reachability；明确 `C=SAT` 可以与 episode 内 `NEW_TOKEN` 共存。
- G4：把单一 `safe_to_rely` 拆成 P0/P1 prediction，以及 `Y_success/Y_resolution/Y_effect/Y_acceptance`；实际执行 response loss、readback、reservation、revoke 和 wrong-object 状态转换。
- G5：建立 Authority strata、owner process、race、target fence、Standing、material closure 与 migration 判别器；保留“技术权限相同但 Authority 不同”的 U/P 反例。
- G6：建立 12 组 role/causality pairs，分开 raw occurrence、Authority、episode binding、`CountsTowardQ`、recovery、Adoption、Acceptance、Settlement 和一致 cut。
- G7：建立 18-world replay，实际执行 owner query、intent persistence、commit fence、response loss、readback、reopen、capsule export/import、old-runtime fencing 和 reconciliation。

### 关键正结果

- 七线的局部 kernel 第一次获得了更精确的现实语义：签名不等于理解，权限不等于 Authority，真实损害不能因“不计入当前 Q”而被删除，正确拒绝可以 resolution 成立但 task success 不成立。
- G3 的六个世界中，多种路径在相同公开输入上给出同一动作，未观察到专用 planner 的独有贡献；重点转向量词与反事实是否正确。
- G5 明确表明合法统一 Authority 的中心路径可以完整闭合其适用子域；在 Authority 未统一时，管理员权限不能代替 owner act。
- G6 的三个不同实现能在有限 fixture 中重建全部承重差异，说明 occurrence/provenance、qualification/authority、obligation/control 三层表示足以阻止受检验的语义折叠。

### 关键负结果

- G1 的高 recall 方法仍因 wrong Authority、forbidden disclosure 或 same-source alias 失败；recall 不能抵消硬边界。
- G4 的主要组合和同权限中心仍有 false reliance；14-world pilot 只能说明 evaluator 有分辨力，不能说明 G4 已解决。
- G7 是本轮最有信息量的负结果：18 worlds × 6 paths 中只有 23 条 exact pass；public-identical hidden-edge revoked world 产生 factual unsafe continuation。表现最好的 mature composite 仍失败于真实 cold-vs-repeat、hidden dependency、完整失效传播和跨 runtime portability。
- 各线 world、runner 和 owner surfaces 仍然不同；这一轮没有组成一次共同 episode。

### 证据级别

`LOCAL SYNTHETIC LINE-SPECIFIC DISCRIMINATORS`。部分使用不同进程与不同实现，但仍属于同一工作区、同一合成研究流，不是现实主体或跨环境复现。

### 对产品与原问题的意义

Wave 011 贡献的是产品内部必须保留的判别面，而不是七个最终模块。它告诉后续产品：不能用一个统一 `SUCCESS` 覆盖 discovery、relation、reachability、reliance、Authority、Effect 和 evolution；这些差异必须在同一个 episode 中通过明确接口连接。也正因为各线已经足够锐利，下一步不应继续横向扩充同类 kernel，而应建立共同任务世界。

### 明确未证明

- 七线已经组合；
- 任何完整策略解决了一次 RelationEpisode；
- 真人理解、授权、Acceptance 或现实 Effect；
- hidden dependency 可被模型猜出；
- migration 已跨真实 runtime/故障域保持语义；
- V1/V2 或产品整体完成。

## Wave 012：建立 CE-001 共同任务合同，但七线实际产物仍不可合并

### 为什么启动

Wave 011 已证明继续分别增强七线会产生更多局部绿灯，却不能回答产品是否完成一个任务。Wave 012 因而选择“社区工作坊临时供电恢复”作为 CE-001，冻结同一个 Q、Target、owner 类型、Authority strata、时间线和 E0–E6 案例，试图让 G1–G7 在一次 RelationEpisode 内闭合。

### 实际做了什么

- 冻结 `Q@v1`：90 分钟内为 Circuit C7 提供连续至少 45 分钟、3kW±5%、满足安全/噪声、不得影响其他线路的结果，并要求 requester/venue 对 exact Effect 分别作出 Acceptance。
- 明确 O_Q、O_V、O_R、O_S、O_P、O_E 的事实所有权，以及 U/D/P 三种 Authority strata。
- 定义 E0–E6：平台直达、既存多 owner、条件形成、ACK 丢失双世界、撤销替代、不可行拒绝、迁移恢复。
- 为 G1–G7 分别实现 CE-001 局部组件；它们比 Wave 011 更严格地绑定 episode/Q/object/operation，并逐轮修复 owner process、签名、Target readback、task substitution、wrong object、currentness 和 response replay 等假闭包。
- 建立 integration preflight：只检查局部 envelope 是否有资格进入组合，不计算合同成功。
- 建立 actual artifact binding audit：检查七线稳定产物是否真的来自同一个 world/run/case/Q/object/operation/owner registry/target registry。

### 关键正结果

- 第一次把完整任务级成功链写成明确合同：`Q → applicable path → owner acts → current Authority → Target consumption → exact occurrence → 双 Acceptance → O_P finality → history continuity`；这一链在本轮尚未作为一次共同 run 执行。
- 七条线明确禁止把本线局部结论直通为合同结论，合同 evaluator 必须从 owner/Target 原生日志重算。
- G1–G7 各自对 CE-001 坐标形成了可运行的局部 evidence envelope；G6 还实际运行八个本地合成 case，并保留 wrong-target raw Effect、双 Acceptance、O_P finality 和 recovery readback 的差异。
- 作用域审计诚实指出：CE-001 只能检验给定 Q、owner 类型、owner API 和有限 action grammar 的 RelationEpisode，不能承担开放形成和 RelationEcology 的完整主问题。

### 关键负结果

- `integration-binding-audit` 明确返回 `NOT_JOINABLE_CURRENT_ARTIFACTS`：七线没有共同 episode manifest、run root、owner registry 或 target registry；G4 缺少可由另一进程消费的持久输出；G6 没有引用 G5 的实际产物；G7 的 Effect/Acceptance/finality 引用也不来自 G6 actual report。
- 手写的 qualified E1/E6 envelopes 只能证明 preflight 会拒绝哪些假闭包，不能证明真实组合运行。
- CE-001 已经预给 owner 类型、动作语法和主要故障，很多困难被研究者预编译成 workflow；即使完成，也不能直接外推到无标签开放世界。
- 一度提出的 switchback ecology 仍把 lifecycle stage 写成课程大纲，被降为 conformance 候选，没有冻结成主实验。

### 证据级别

`FROZEN TASK CONTRACT + RUNNABLE LOCAL LINE COMPONENTS + NON-JOINABLE INTEGRATION AUDIT`。完整 CE-001 run 为 `NOT RUN`。

### 对产品与原问题的意义

Wave 012 是从“七个研究对象”转向“一个产品任务”的关键转折。它给出了产品组合时不可缺的共同坐标和合同级 success chain，也用不可合并审计证明：字段相似、结构合格、各线分别运行，都不等于产品解决了一次 episode。它同时把原问题分成两个尺度：CE-001 可以推进 RelationEpisode；开放形成、重复编译、资源竞争和生态迁移仍需另一类任务。

### 明确未证明

- 七线在同一实际 run 内闭合；
- 任一完整策略完成 E0–E6；
- CE-001 的物理供电、现实 Authority、真人 Acceptance 或付款；
- 开放角色/伙伴/行动形成；
- RelationEcology、长期复用或产品整体完成。

## Wave 013：第一个真正共同 world 的 E1/E5 纵切

### 为什么启动

Wave 012 最重要的失败是七线产物不属于同一次运行。Wave 013 不再分别跑七线，而是在同一个冻结 world/run 中启动六个 owner、一个 Target 和一个 A4 executor，先只做最小纵切：E1 exact success 与 E5 bounded refusal。

### 实际做了什么

- 建立共同 `episode_manifest`、共同 world root、同一 Q/object/operation、统一 owner/Target registry。
- A4 从实际 owner/Target 返回决定执行或拒绝；七个 line fragment 都引用同一 run 的原生日志。
- E1 实际执行 Authority query、Target execute/readback、O_Q/O_V Acceptance 和 O_P finality。
- E5 实际读取 non-delegable refusal，在 frozen no-alternative truth 下有界停止，且没有 Target occurrence、Acceptance 或 finality。
- 先后修复三种严重答案泄漏：明文 `case_id`、可字典反查的 private manifest hash、child 继承 parent `--case` argv。最终使用独立随机 arm binding token 和双视图边界。
- 保留第一次 actual bundle 的真实失败：E1 曾被 evaluator 判为 unsafe Effect，E5 曾被判为 invalid refusal；修正 Authority consumption、deadline 和 alternative oracle 后才形成当前结果。

### 关键正结果

- E1 在一个共同本地合成 world 中得到 exact task success、correct resolution 和 safe handling。
- E5 在同一产品骨架下得到 bounded refusal、correct resolution、safe handling，同时明确 `ExactTaskSuccess=false`。
- 结果由 Target request、occurrence/samples、signed readback、owner Acceptance 和 finality 的内容父引用串起，不再由七个局部结果事后拼接。

### 关键负结果

- 早期两批绿色运行分别因明文标签和 hash/argv 可恢复答案而降级；它们不能用于“方法自己辨认分支”的主张。
- 当前只运行 A4，且只覆盖 E1/E5。共同 world 成立不等于完整八案或多路径比较成立。
- 终态满足仍不能证明 Effect 是 A4 造成的；这一残余直接触发 Wave 014 causal twin。

### 证据级别

`ROOT-ACCEPTED LOCAL SYNTHETIC COMMON-WORLD VERTICAL SLICE`，作用域仅 E1/E5、A4。

### 对产品与原问题的意义

这是本序列第一次真正接近产品运行单位：同一个 episode 中，入口、owner act、Authority、Target Effect、Acceptance、finality 和拒绝都由同一 run 连接。它证明产品闭环应围绕共同 world 和原生日志构建，而不是围绕研究线文件构建。

### 明确未证明

- E0/E2/E3A/E3B/E4/E6；
- 多种完整路径在同一 world 下的公平比较；
- A4 对 Effect 的因果贡献；
- 现实电路、现实组织 Authority、真人 Acceptance、财务 finality；

## Wave 014：causal twin 证明“相同终态”不能自动归因给当前 arm

### 为什么启动

Wave 013 已经能验证任务终态，但仍可能出现一种根本假成功：A4 发出请求后，另一个 Helper 直接造成相同 Target 状态，outcome-only evaluator 仍把成功归给 A4。Wave 014 专门构造两个相同终态、不同直接提交者的 causal twin。

### 实际做了什么

- 两个实际多进程世界在 A4 发出 exact signed commit 前保持相同 A4-visible prefix。
- `W_G` 由 Router 转发 A4 请求；`W_F` 抑制 A4，请 Helper 用自己的签名请求完成等价状态。
- Target 原子提交凭据记录 direct actor、request、pre/post state/version、commit id，并签出绑定 `last_commit_id` 的 authoritative readback。
- legacy evaluator 只看状态投影；causal evaluator 验证 Target commit/readback 和 actor provenance。

### 关键正结果

- 两世界 Target state projection 相同，legacy evaluator 都报成功。
- causal evaluator 正确得到：`W_G` 的 A4 贡献成立；`W_F` 任务状态成立，但属于 `MATCHING_STATE_EXTERNAL_CAUSE`，不能计作 A4 的 exact success。
- 由此稳定分开三个产品坐标：`TaskOutcomeSatisfied`、`AuthorizedExecutionCommitted`、`EffectAttributableToArm`。
- 在受信本地数字 Target 边界内，原子 mutation receipt + authoritative readback 已足以解决 direct actor attribution。

### 关键负结果

- 这不是全局 but-for causation；Helper window 仍在 Router 观察 A4 请求后开启。
- alpha-shape 相同不等于时间、调度和流量侧信道不可区分。
- Target root 若恶意，或同权限进程协调改写，当前证据边界不覆盖。

### 证据级别

`ROOT-ACCEPTED LOCAL SYNTHETIC CAUSAL TWIN`，只覆盖数字 Target 原子提交边界的直接 actor 归因。

### 对产品与原问题的意义

## Wave 018：资源撤销后的局部重开、替代方重发现与恢复到任务价值

## Wave 020：受控进程终止后的迁移、旧 runtime fencing 与后置条件恢复

### 为什么启动

Wave 015 的 E6 probe 只有本地 launcher/capsule/fence 骨架，尚未把 Target ledger、owner current heads、Acceptance、finality 和 crash cut 接入同一次恢复。Wave 020 检验：source 已唯一产生 exact Effect、但尚未 Acceptance/finality 时终止，另一个 runtime 能否不重放 Effect地接管未结义务。

### 实际做了什么

- source 实际完成一个 exact C7 digital occurrence/readback，写入 durable history、signed capsule 和 marker，且 cut 时 O_Q/O_V/O_P 原生 store 中 Acceptance/finality 均为零。
- controller 观察 durable marker 后外部终止 source；随后迁移到不同 PID/runtime/key/state 的 epoch 2 runtime。
- migrated runtime 只允许 import、verify Target、完成 postconditions；不允许 execute。
- 第一代 controller 在 durable SQLite 持久化 epoch 2 后非零退出；第二代 controller reopen 同一 fence store，再启动 old runtime restart。
- old runtime 实际 reopen source-state DB，用 source key 对预冻结 challenge 签名，并以 epoch 1 请求 execute；外部 durable fence 拒绝。
- baseline 从 Target receipt/readback 对账既有 Effect，再取得 O_Q/O_V Acceptance 和 O_P finality。
- removal world 在 cut 后不向 migrated runtime 提供 durable Target evidence；它保持 `BOUNDED_UNKNOWN/UNRECONCILED_EFFECT`，零 replay、零 Acceptance、零 finality。

### 关键正结果

- baseline 只有 source epoch 1 的一次 accepted execute；migrated runtime 没有第二次 Effect。
- source history prefix 被逐项保留，migrated history 只追加 recovery events。
- old epoch 在 controller 重启后仍被持久 fence 拒绝，不依赖旧 controller 内存。
- Acceptance/finality 是 crash cut 后 owner-native heads 的 append-only extension。
- removal 反事实表明 Target receipt/readback 是安全恢复后置条件的必要证据；缺失时系统既不猜成功，也不盲目 replay。

### 关键负结果

- 第一轮实现和旧 artifact 被独立 red-team 整体拒绝：worker 参数漂移导致 baseline 跑不完；冻结包缺 formal databases；object/operation 绑错；WAL header 可假装 DELETE；old restart 只是新进程角色扮演；restart schedule 未预冻结；pre-crash absence 只有 source 自报；removal 中 migrated runtime 仍能偷读 full capsule。
- root fresh run 又发现短字符串扫描会随机把 opaque token 里的 `e6` 当标签泄漏，以及 migrated view 中的 `REMOVE/target_store_removed` 本身就是反事实 oracle。修复这些问题后才生成最终接受 suite。
- crash 是预注册、受控的 process termination；不是不可预告物理掉电或机器毁损。

### 证据级别

`ROOT RED-TEAM ACCEPTED SCOPED LOCAL SYNTHETIC CONTROLLED-TERMINATION E6`。

### 对产品与原问题的意义

这轮给出了产品的迁移恢复链：先从 Target 对账 Effect，而不是从 source workflow 猜；用 capsule 搬运未结义务和历史前缀；用持久 epoch fence 阻止旧 runtime；重新读取 owner heads；最后只恢复 Acceptance/finality。缺关键 Target 证据时，产品保持 bounded Unknown，而不是选择重复执行或伪造完成。

### 明确未证明

- 不可预告 physical hard crash；
- 物理 Effect、法律 Authority、真实跨机 transport 或 OS 级 noninterference；
- 恶意同目录 writer resistance；
- 生产长期可靠性、跨实现和跨域普遍性；
- V1/V2 或完整产品完成。

## 2. 截至 Wave 020 的统一判断

### 已经沉淀成“我们怎么做”的部分

对于已进入产品边界、Q/Target/必要 owner 可表达的任务，当前可以给出一条具体求解链，而不是只给研究名词：

```text
识别是否可由平台直接完成
→ 若需要多主体，形成可修改 proposal 并取得各 owner act
→ 在 commit 前读取 current Authority / reservation / safety heads
→ 用 Target ledger 执行唯一 mutation
→ ACK 不明时先查 exact status，再 reconcile 或 freshness-gated retry
→ 用 Target-native readback确认 Effect
→ 分别取得必要 Acceptance 与 finality
→ 撤销时只重开受影响依赖并重新发现替代方
→ runtime 终止时先对账 Effect、迁移未结义务、fence 旧 runtime、恢复后置条件
→ 任一承重证据缺失时保留 refusal / bounded Unknown，而不是伪造成功
```

Wave 013–020 已经分别给出这条链若干节点和组合段的实际本地合成运行证据。Wave 017 说明最简单子域应直接完成；Wave 019 说明缺失条件可以通过 owner interaction 真实形成；Wave 018 和 020 说明变化后可以恢复而不改写历史；Wave 014–016 说明 Target truth 和 causal/status readback 是执行层的承重基础。

### 仍没有完成的原始问题

截至 Wave 020，仍不能说产品已经解决最初完整问题，原因不是局部机制数量不够，而是以下闭包尚未出现：

1. CE-001 仍没有把 E0–E6 和多种完整策略放进同一个统一 runner，形成一份完整 episode-level portfolio 结果。
2. 已完成的 case 都是本地数字或本地合成世界；物理 Effect、现实组织 Authority、真人 Acceptance 和长期价值没有进入同等证据链。
3. CE-001 预先给了 Q、owner 类型、动作语法和案例故障，不能检验开放情境中怎样发现 episode、提出未知角色/伙伴/动作、决定应创造什么条件。
4. RelationEcology 的重复编译、多个 episode 的资源竞争和外部性、伙伴退出后的生态替代与长期成本，仍未由同一产品系统运行。
5. 多数 root acceptance 验证的是受信本地 controller/process 边界；它们不是恶意同权限者或生产威胁模型下的保证。

因此，Wave 010–020 的准确总定位是：

> 它们把完整 RelationEpisode 的若干承重问题，从叙事和局部标签推进成了可组合、可攻击的本地运行段；其中平台直达、Target mutation truth、ACK 丢失恢复、撤销局部重开、条件形成和受控迁移已经获得有界正结果。但完整产品 episode、开放形成、现实 Effect/Acceptance 与 RelationEcology 仍未闭合。

### 这些结果怎样约束后续工作

- 后续不得回到七线各自扩充同类 fixture；新的局部工作必须直接进入同一个完整 episode 或解释它关闭哪个真实断点。
- 不得用测试数量、文件哈希、receipt 数量、schema 合法或 frozen package 代替任务结果；它们只用于定位、复核和防止证据被换包。
- 不得把 CE-001 的局部成功外推到开放世界，也不得因开放世界未完成而抹掉 E0/E2/E3/E4/E6 的有界正结果。
- 产品必须把 direct path、owner formation、Target execution、Acceptance、refusal、reopen 和 migration 纳入同一条件化路由，而不是让用户面对七条研究线。
- 下一步若继续 CE-001，唯一有价值的目标是完成同一个 episode family 的组合运行与第二任务迁移；若转向开放形成，必须使用不预给角色、伙伴、路径和 lifecycle stage 的输入。
